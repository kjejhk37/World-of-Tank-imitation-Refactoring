# Brainstorming: 타이틀 씬 이식 / Scene 전환 매커니즘

## Details

### 원본 TitleScene 분석 (../WOT/WOT, Develop 브랜치)

`pageNum`(0/1/2)으로 나뉘는 화면 3개짜리 상태머신 — 별도 씬이 아니라 한 씬 안에서 렌더링 분기로 처리됨.

- `pageNum==0`(메인): 배경 + 로고(페이드인 효과, `WOT_UIFade` 상속) + 버튼 3개
- `pageNum==1`(튜토리얼): 팝업 이미지 + 튜토리얼 그림 6장(클릭마다 다음 장) + 한 글자씩 타이핑되는 안내 텍스트(`WOT_AnimeFonts`) + "타이틀로" 버튼
- `pageNum==2`(종료 확인): 확인 텍스트 + 예/아니오 버튼 2개
- 버튼(`WOT_Button`): 이미지 3장(기본/hover/select) 조합 + 마우스 좌표를 픽셀 사각형과 비교하는 직접 히트테스트 (ImGui 아님)
- 배경음악(`Audio::Get()`), 즉시모드 폰트 렌더(`Font::Get()->RederText`)

지금 프로젝트와의 대응:

| 원본 요소 | 지금 있는 것 | 상태 |
|---|---|---|
| 배경 이미지 | `ImageUI` | 재사용 가능 |
| 버튼(이미지 3장+히트테스트) | `ButtonUI`(ImGui) | 다름 — ImGui 방식으로 재설계 필요 |
| 로고 페이드인 | 없음 | 신규(이번 사이클 제외) |
| 튜토리얼 타이핑 텍스트 | 없음 | 신규 서브시스템(이번 사이클 제외) |
| 배경음악 | 없음 | 신규 서브시스템(이번 사이클 제외) |

### 현재(포팅된 프로젝트) Scene 시스템 분석

- `Scene`(추상): `Start/Update/End` + Entity 목록만. **렌더링 메서드 없음** — 원본과 달리 렌더링 책임이 완전히 빠져 있음(3D는 `InstanceSnapshot`, 2D UI는 `main.cpp`가 렌더 스레드에서 직접 소유 — `IntroScene` 사이클의 스레드 안전성 결정).
- `SceneManager`: `Create/Add/Remove/Update` — 여러 씬 등록·동시 활성화를 이미 지원. 원본과 달리 싱글턴이 아니라 `GameManager`가 소유(DI).
- `GameManager`: 지금은 `IntroScene` 하나만 등록. 원본 `GameManager`(GameManager/GameManager.cpp)도 확인해보니 개별 오브젝트 병렬 갱신 역할이 아니라, 전역 서브시스템 초기화 + 매 프레임 `SCENE->Update()/Render()`를 호출하는 얇은 오케스트레이터였음. 실제 개별 오브젝트(탱크 등) 관리는 `WOT_TankManager`처럼 특정 씬(`GamePlayScene`) 내부 매니저의 몫.
- 갭: `SceneManager` 자체는 문제 없음. 실제로 빠진 건 "지금 활성 씬이 뭔지 보고 `main.cpp`가 어떤 위젯 세트를 그릴지 결정하는 연결 고리".

## Trade-offs

**`SceneManager`를 싱글턴으로 바꾸는 것 (원본과 동일하게)**
- 장점: 원본 구조와 일치, `GameManager`가 매번 `SceneManager&`를 들고 다닐 필요 없이 어디서든 `SceneManager::Get()`으로 접근 가능.
- 단점: 전역 가변 상태라 단위테스트 간 격리가 어려워짐(이 프로젝트는 `단위테스트_도입` 사이클에서 전 영역 테스트를 원칙으로 삼음 — 테스트마다 리셋 로직 필요). 지난 사이클(2026-08-11)에서 의도적으로 DI로 바꿨던 결정을 되돌리는 것.
- 결정: 이 레포의 목적 자체가 "WOT 레퍼런스를 리팩토링해서 새로 만드는 것"이므로, 구조를 원본과 다르게(혹은 다시 원본처럼) 가져가는 건 프로젝트 취지에 맞다는 사용자 판단 → **싱글턴으로 진행**, 테스트 트레이드오프는 감수.

## Q&A Log

- Q: 현재 Scene 시스템(Scene/SceneManager/GameManager)을 어떻게 파악하는지?
  A: `Scene`은 렌더링 없이 로직만, `SceneManager`는 Create/Add/Remove/Update로 여러 씬 관리 가능(DI 소유), `GameManager`는 지금 IntroScene 하나만 등록. TitleScene 이식의 실제 갭은 SceneManager가 아니라 "활성 씬 → main.cpp 위젯 전환 연결"이 없다는 것.
- Q: SceneManager 자체엔 문제 없어 보이는데?
  A: 맞음 — SceneManager(Create/Add/Remove/Update)는 수정 불필요. 갭은 main.cpp가 GetActiveScenes()를 안 쓰고 있다는 것뿐. 필요한 작업은 GameManager가 TitleScene도 등록하는 것 + main.cpp가 활성 씬에 맞는 위젯 세트를 그리는 로직 추가로 좁혀짐.
- Q: 이번 사이클 스코프를 어디까지?
  A: SceneManager를 자세히 다지고, TitleScene/LoadingScene은 형태(스텁)만 간단히 — 실제 콘텐츠(로고 페이드/튜토리얼/종료 확인/오디오)는 제외.
- Q: SceneManager를 싱글턴으로, Update/Add(시작)/Remove(종료)/Create(생성)/소멸을 정의하는 것에 대해?
  A: 동의. 개별 오브젝트 병렬 연산(원 발언의 "GameManager 내부 병렬 연산")은 나중에 GameManager를 실제로 개발할 때 별도로 다룸 — 이번 사이클 범위 아님.
  → 원본 GameManager(GameManager.cpp)를 확인해보니 이것도 병렬 연산 담당이 아니라 전역 서브시스템 초기화 + 매 프레임 SCENE->Update()/Render() 호출하는 얇은 오케스트레이터였음. 실제 오브젝트 병렬 처리는 WOT_TankManager 같은, 특정 씬 내부의 매니저 몫.
- Q: SceneManager가 싱글턴이 되면 GameManager는 없어지나, 아니면 SceneManager::Get()을 호출하는 얇은 래퍼로 남나?
  A: 삭제. `InstanceUpdateWorker`가 `SceneManager::Get()`을 직접 호출한다.
- Q: "씬별 스냅샷 중 SceneManager가 고른다"는 설계가 graphics/platform과 얘기해야 할 만큼 큰 변경인가, 구조적으로 가능한가?
  A: 확인 결과 `projects` 저장소 내부(`SceneManager` + `SceneSnapshotBuilder`)만으로 완결된다. `InstanceSnapshot`(graphics)은 씬 개념을 모르는 평평한 `{vector<Matrix4x4>}` 구조체이고, `DoubleBufferPublisher<T>`(platform)도 T가 뭔지 모르는 범용 전송 수단이라 계약 변경이 필요 없다. graphics와 얘기해야 하는 건 별개 주제(WOTGameManager 내부의 실제 오브젝트 병렬 갱신 방식)이고, 이번 스냅샷 선택 로직과는 무관.
- Q: `WOTScene`/`WOTGameManager`는 이번 사이클에서 실제로 만드는 것인가?
  A: 아니오 — 패턴 설명용 예시. 대신 앞으로 WOT 고유 게임 콘텐츠 클래스는 전부 `WOT` 접두사를 붙이는 네이밍 컨벤션으로 확정.
- Q: `UnitTestScene`을 이번 사이클에서 만드는가?
  A: 만든다 — `SceneManager`의 기본 생명주기(Create/Add/Remove/Update)뿐 아니라, 새로 추가하는 "스냅샷 선택" 로직까지 이 더미 Scene으로 단위테스트에서 검증한다.
- Q: 스텁 씬(Title/Loading)에 전환을 눈으로 확인할 최소 표시를 둘지?
  A: 라벨 텍스트 하나씩 남긴다(어느 씬이 떠 있는지 구분용).
- Q: 스텁 씬 간 전환을 무엇으로 검증/확인할지?
  A: `platform/logging`(`Log::Info`, 이미 구현된 `ConsoleLogSink`)을 재사용해 씬 전환 시점마다 로그를 찍는다. `main` 타겟이 `add_executable(main src/projects/main.cpp)`로 `WIN32` 플래그 없이 선언돼 있어 이미 콘솔 서브시스템 앱이라 별도 콘솔 할당(AllocConsole) 없이 그대로 콘솔에 출력된다.
- Q: 스텁 씬 간 전환은 무엇으로 트리거할지?
  A: 버튼 클릭으로 간단하게 구현한다(타이머/키 입력 대신).

## 요약

- 이번 사이클의 실제 갭은 `SceneManager` 기능 부족이 아니라, "지금 어떤 씬이 떠 있는지를 보고 `main.cpp`가 그릴 위젯 세트와 3D 스냅샷 대상 씬을 고르는 연결 고리"가 없다는 것이다.
- 목적을 "씬 전환 매커니즘 정비 + TitleScene/LoadingScene 최소 스텁"으로 재정의했다.
- `SceneManager`를 싱글턴으로 바꾸고 `GameManager`는 삭제하며, 스냅샷은 `SceneManager`가 지정한 현재 씬 하나만 반영한다.
- 모든 변경은 `projects` 저장소 안에서 끝나며 `graphics`/`platform`에 요청할 항목은 없다.
- 브레인스토밍은 Step 3(전략서)로 넘어갈 수 있는 상태다.

## 사용자 결정 사항

1. 목적 재정의 — "TitleScene 이식"이 아니라 "여러 씬을 전환하는 매커니즘을 정비하고, TitleScene/LoadingScene은 그 매커니즘을 검증할 최소 스텁으로 둔다".
   → 원본 TitleScene의 실제 콘텐츠 구현은 이번 사이클 범위에서 빠진다.
2. `SceneManager`를 원본과 같은 싱글턴으로 전환한다. Create(등록)/Add(화면에 올리기)/Remove(화면에서 내리기)/Update에 더해 "활성 씬 중 어느 씬의 스냅샷을 가져올지 선택"하는 책임까지 갖는다.
   → 2026-08-11 게임로직 이식 사이클에서 DI로 바꿨던 결정을 되돌린다. 단위테스트 간 격리를 위해 테스트마다 리셋 로직이 필요해지는 트레이드오프를 감수한다.
3. 기존 `GameManager` 클래스는 삭제하고 `InstanceUpdateWorker`가 `SceneManager::Get()`을 직접 호출한다.
   → 원본 `GameManager`도 병렬 연산 담당이 아닌 얇은 오케스트레이터였으므로 역할 손실이 없다.
4. `SceneSnapshotBuilder`는 활성 씬 전체를 합치는 대신 `SceneManager`가 선택한 씬만 반영한다.
   → `InstanceSnapshot`(graphics)과 `DoubleBufferPublisher<T>`(platform)는 씬 개념을 모르므로 두 저장소의 계약 변경이 필요 없다.
5. `WOTScene`/`WOTGameManager`는 이번 사이클에 만들지 않는다. 앞으로 WOT 고유 게임 콘텐츠 클래스에는 전부 `WOT` 접두사를 붙인다.
   → 네이밍 컨벤션이 이후 사이클에도 적용된다.
6. 개별 오브젝트 병렬 연산 설계는 이번 사이클 범위 밖이며, `WOTGameManager`를 실제로 개발하는 미래 사이클로 이연한다.
   → graphics 세션과의 병렬 갱신 방식 논의도 그때 진행한다.
7. 더미 씬 `UnitTestScene`을 만들어 `SceneManager`의 생명주기와 스냅샷 선택 로직을 단위테스트로 검증한다.
   → 테스트 전용 Scene 구현체가 하나 추가된다.
8. `TitleScene`/`LoadingScene`은 최소 스텁으로 두고, 어느 씬이 떠 있는지 구분할 라벨 텍스트를 하나씩 둔다.
   → 화면 콘텐츠 작업량이 라벨 하나 수준으로 줄어든다.
9. 스텁 씬 간 전환은 버튼 클릭으로 트리거하고, 기존 `Log::Info`와 `ConsoleLogSink`로 전환 이벤트 순서를 콘솔에 출력해 검증한다.
   → `main` 타겟이 이미 콘솔 서브시스템이라 `AllocConsole` 같은 추가 설정이 필요 없다.
10. 로고 페이드인, 튜토리얼 페이지, 종료 확인 페이지, 배경음악은 이번 사이클에서 제외한다.
    → 커밋 리포트에 범위 밖 항목으로 명시한다.
