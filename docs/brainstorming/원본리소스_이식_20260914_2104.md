# Brainstorming: 원본 리소스 이식

## Details

### 1. 원본 리소스 실제 구성 (원본 `WOT` Develop 브랜치 `3b497a3` 기준, 읽기 전용 확인)

확장자별 파일 수는 다음과 같다.

- 텍스처: `.png` 160, `.dds` 2, `.jfif` 1
- 사운드: `.mp3` 7, `.ogg` 10, `.wav` 11, `.flac` 3
- 모델: `.mesh` 25, `.mats` 22, `.mat` 86
- 데이터: `.csv` 22, `.srt` 13, `.map` 2
- 리소스가 아닌 파일: `Sound/Easteregg/desktop.ini` (Windows 탐색기가 만든 폴더 설정 파일), `Textures/Test.jfif` (이름상 테스트용 이미지)

원본 폴더 구조의 문제점은 다음과 같다.

- 같은 모델의 파일이 종류별로 흩어져 있다 — `Tank01_Body`는 메시가 `Models/Meshes/`, 머티리얼이 `Models/Materials/Tank01_Body/`, 텍스처가 `Textures/Model/Tank01/`에 있다.
- 지형 데이터가 `Models/LandscapeMaps/`(모델 폴더)에, 지형 텍스처는 `Textures/Landscape/`에, 스카이박스도 `Textures/Landscape/`에 섞여 있다.
- 사운드는 배경음악·효과음·안내 음성이 `Sound/` 한 폴더에 섞여 있다.
- 이름 규칙이 섞여 있다 — `PascalCase`(`Tank01_Body`), 소문자(`garage`, `bark1`), 공백과 괄호(`Trims_DM (2).png`), 오타(`Fance.wav`, `Rock_Fance.wav`), Blender 자동 번호(`Marche_Opacity.001.mat`).
- `TextData/Tables/`에 배틀 씬 배치표와 `SelectScene_` 접두사가 붙은 선택 씬 배치표, 탱크 수치표가 한 폴더에 섞여 있다.

바이트 단위로 완전히 같은 파일이 4쌍 있다.

- `Textures/Model/Buildings/Houses/AtticFloor_DM.png` = `FloorsPlanks_DM.png`
- `Textures/Model/Tank01/Tank01_Caterpillar_{DM,NM,SM}.png` = `Textures/Model/Tank03/Tank03_Caterpillar_{DM,NM,SM}.png`

원본 코드와 파일 내용이 폴더 구조에 묶여 있다.

- `Transform.cpp`: `"TextData/Transforms/" + tag + ".srt"`
- `ModelReader.cpp`: `"Models/Materials/" + name + "/" + name + ".mats"`
- `ModelExporter.cpp`: `"Models/Meshes/" + name + ".mesh"`, `"Textures/Model/" + name + "/" + fileName`
- `.mats` 바이너리 파일 내부에도 `Models/Materials/Bush01/lambert1.mat` 같은 경로 문자열이 들어 있다.
- `ModelAnimator.cpp`는 `Models/Clips/...clip`을 읽지만 원본 저장소에 `Models/Clips` 폴더는 없다.

→ 폴더 구조를 새로 정리하면 이 경로들은 모두 새 구조와 어긋난다. 사용자 결정에 따라 원본 경로가 아니라 **새 구조를 기준으로 프로젝트 쪽 로더를 리팩토링**한다. 그 리팩토링을 위해 "원본 경로 → 새 경로" 대응표를 반드시 남긴다.

### 2. 새 폴더 구조 초안

확정된 구조 원칙은 다음과 같다.

- **원칙 1 — 최상위는 리소스 용도(ui / audio / models / terrain / environment / effects / data)로 나눈다.**
- **원칙 2 — 3D 모델은 종류 단위로 묶는다**: `models/meshes/`, `models/materials/`, `models/textures/`로 나누고, 각 폴더 안에서 탱크(`tanks/`)와 배경 오브젝트(`props/`)를 구분한다. 여러 모델이 공유하는 텍스처(집 3채 공유 텍스처)는 `models/textures/props/houses/`에 자연스럽게 한 번만 둔다.
- **원칙 3 — 이름은 소문자 snake_case**, 번호는 두 자리(`tank_01`, `loading_01`), 공백·괄호·Blender 자동 번호(`.001`)는 쓰지 않는다.
- **원칙 4 — 텍스처 맵 종류는 뜻이 드러나는 단어 접미사로 구분**한다: 원본 `_DM` → `_diffuse`, `_NM` → `_normal`, `_SM` → `_specular`.
- **원칙 5 — 리소스가 아닌 파일은 뺀다**: `Sound/Easteregg/desktop.ini`, `Textures/Test.jfif`(원본 코드에서 이름으로 참조되는 곳 없음 — `Material.cpp`의 파일 선택 창 확장자 필터에만 `.jfif`가 등장). 완전 중복 파일 4쌍은 둘 다 남기고 `manifest.csv`에 중복 사실을 기록한다.

### 3. 파일 "내용"은 바꾸지 않는다

- 이번 사이클은 폴더·파일 **이름과 위치**만 바꾼다.
- `.mats` 내부 경로 문자열, CSV 헤더 오타(`PoxY`), 이미지·음원 자체는 수정하지 않는다.
- 이유: 로더가 없어 바이너리 수정 결과를 검증할 수 없고, 내용 변경은 해당 로더를 이식하는 사이클에서 로더와 함께 해야 검증된다.
- 대신 `manifest.csv`에 "내부에 원본 경로가 박혀 있음" 같은 주의 사항을 파일별로 적는다.

### 4. 리소스 저장소 구성

- 이름 후보: `WOT-assets` (비공개).
- 이 저장소에서의 submodule 경로 후보: `assets/` — 빌드 산출물에서 이미 `assets/models`, `assets/textures`라는 이름을 쓰고 있어 대응이 자연스럽다.
- 기존 `tests/fixtures/`(cube.obj, intro_logo.png 등)는 직접 만든 테스트용 파일이라 공개 저장소에 그대로 둔다.
- `platform`/`graphics` 저장소는 변경이 없다. 리소스 submodule은 `projects`(이 저장소)만 참조한다.
- 원본 이력은 가져오지 않고, 기준 커밋 `3b497a3`의 스냅샷을 새 구조로 옮긴 결과를 첫 커밋으로 만든다. 커밋 메시지와 `README.md`에 원본 저장소와 커밋 해시를 적는다.

### 5. 이번 사이클에서 공개 저장소 쪽 변경 범위

- 리소스 submodule 추가(`.gitmodules` + 포인터 커밋).
- README에 "리소스는 비공개 저장소라 포함되지 않음, `--recursive` clone 시 리소스 submodule만 실패하는 것은 정상" 안내 추가.
- CMake 복사·리소스 없을 때의 빌드 동작은 포함하지 않는다.

## Trade-offs

**원본 구조 보존 vs 새 구조로 정리 → 새 구조로 결정**
- 새 구조 장점: 리팩토링된 프로젝트다운 구조가 되고, 모델 단위로 파일을 찾고 관리하기 쉽다.
- 새 구조 단점(감수): 원본 코드와 `.mats` 내부 경로가 전부 어긋난다. 로더가 없어 지금은 깨졌는지 검증할 수 없고, 로더를 이식하는 사이클마다 대응표를 보고 경로 처리를 새로 설계해야 한다.

**모델 단위 묶기 vs 종류 단위(meshes/ materials/ textures/) → 종류 단위로 결정**
- 모델 단위 장점: 한 모델의 파일이 한 폴더에 있어 추가·삭제·확인이 쉽다. 요즘 엔진 에셋 구성과 비슷하다.
- 모델 단위 단점: 여러 모델이 공유하는 텍스처(집 3채 공유 텍스처, tank_01과 tank_03의 동일한 궤도 텍스처)를 어디에 둘지 따로 정해야 한다.
- 종류 단위 장점: 원본 구조와 가까워 대응표가 단순하다.
- 종류 단위 단점: 한 모델을 다루려면 세 폴더를 오가야 한다 — 지금 원본의 불편함이 그대로 남는다.

**완전 중복 파일 정리 → 둘 다 두기로 결정**
- 하나만 남기기: 용량이 줄지만 모델 단위 폴더의 독립성이 깨지고(`tank_03`이 `tank_01` 폴더를 참조), 나중에 한쪽만 바꾸고 싶을 때 다시 분리해야 한다.
- 둘 다 두기: 모델 폴더가 독립적이다. 중복 사실은 `manifest.csv`에 기록한다.

**CMake 연동 → 이번 사이클 제외로 결정**
- 이번 사이클이 C++/CMake 변경 없이 작고 명확해진다.
- 리소스를 실제로 쓰는 시점의 사이클 범위가 그만큼 늘어난다.

## Q&A Log

- Q: 비영리 순수 포트폴리오인데도 저작권 문제가 있나?
  A: 있을 수 있다. 저작권 침해는 이익 여부와 무관하게 복제·배포 자체로 성립하고, 공개 GitHub 저장소는 배포에 해당한다. 원본을 통째로 올리는 경우 공정이용 주장도 불리하다. 원본 리소스는 다른 팀원들이 추가한 것이라 팀원 동의 문제도 따로 있다.
- Q: 소스를 git에 올리지 않고 특정 드라이브에 올리는 정도면 가능한가?
  A: 가능하다. 본인만 접근하는 개인 보관은 배포가 아니므로 위험이 크게 줄어든다. 다만 드라이브는 변경 이력과 코드 버전별 리소스 고정이 안 되어, "git으로 저장"이라는 목적에는 비공개 git 저장소가 더 맞다.
- Q: 리소스만 private 저장소로, 코드는 public으로 두고 submodule로 다운로드를 막는 방식은?
  A: 가능하며 결정되었다. public 저장소에는 포인터만 저장되고 권한 없는 사람은 리소스 submodule을 받지 못한다. `.gitmodules`에 비공개 저장소 이름이 보이는 점, 타인의 `--recursive` clone이 해당 submodule에서 실패하는 점, CI에서 별도 인증이 필요한 점은 감수한다.
- Q: 기준 버전은?
  A: 원본 Develop 브랜치 마지막 커밋(`3b497a3`) 기준으로 진행한다.
- Q: 정리 방식·이름과 경로·원본 이력·저장 방식·CMake 연동은?
  A: 폴더 구조 자체를 새로 정리한다. 이름과 경로는 정리만 잘 되어 있으면 그 구조에 맞춰 프로젝트 리팩토링을 이어간다. 원본 이력은 필요 없다. 저장은 일반 git. CMake 연동은 하지 않고 필요한 시점에 다음 작업으로 진행한다.
- Q: 모델 묶는 방식·텍스처 접미사·제거 대상·분류·저장소 이름과 경로는?
  A: 모델은 종류 단위로 묶는다. 텍스처 접미사는 단어(`_diffuse`/`_normal`/`_specular`)로 바꾼다. 제거 대상은 권장대로(`desktop.ini`, `Test.jfif` 제거, 중복 4쌍은 유지 + 기록). 초안 트리의 분류는 문제없다. 저장소 이름 `WOT-assets`, submodule 경로 `assets/`로 한다.

## 요약

- 원본 리소스를 **새 폴더 구조로 정리**해 비공개 `WOT-assets` 저장소(일반 git, 원본 이력 없이 스냅샷)에 넣고, 이 저장소의 `assets/`에 submodule로 추가한다.
- 새 구조: 최상위를 용도별(ui/audio/models/terrain/environment/effects/data)로 나누고, 3D 모델은 종류 단위(`meshes/`/`materials/`/`textures/`)로 묶고, 이름은 소문자 snake_case, 텍스처 접미사는 `_diffuse`/`_normal`/`_specular`로 통일한다.
- `desktop.ini`, `Test.jfif`는 빼고, 완전 중복 파일 4쌍은 유지하되 `manifest.csv`에 기록한다.
- 파일 내용(`.mats` 내부 경로, CSV 헤더 등)은 수정하지 않고, 원본 경로 → 새 경로 대응표(`manifest.csv`)를 남겨 이후 로더 리팩토링의 기준으로 삼는다.
- CMake 연동은 이번 사이클에서 하지 않는다 — C++/CMake 변경이 없는 사이클이다.
- 남은 확인 사항이 없어 사용자 승인 시 Step 3(전략서)에서 파일 단위 대응표를 확정한다.

## 사용자 결정 사항

1. 원본 리소스 이식을 보류 중인 `타이틀씬_이식` 사이클보다 먼저 진행한다.
   → 이 사이클이 끝난 뒤 `타이틀씬_이식`을 재개한다.
2. 목적은 리소스 정리와 git 보관이며, 리소스를 읽는 코드(파서·오디오·로딩)는 포함하지 않는다.
   → 이번 사이클에서 C++ 코드 변경은 없다.
3. 범위는 원본 리소스 전체(`Textures`, `Sound`, `Models`, `TextData`)다.
   → 지금 읽을 수 없는 형식(.mesh/.mats/.mat/.srt/.map/.mp3/.ogg/.wav/.flac)도 보관한다.
4. 리소스는 비공개 git 저장소에 두고 공개 코드 저장소가 submodule로 참조한다.
   → `.gitmodules`에 비공개 저장소 이름 노출, 타인의 `--recursive` clone 부분 실패, CI 인증 필요를 감수한다.
5. 리소스 출처와 팀원 동의는 확인을 기다리지 않고 진행하되, 비공개 리소스 저장소를 공개로 바꾸기 전 필수 조건으로 남긴다.
   → 이번 사이클에서 리소스 저장소는 비공개로 유지한다.
