# Summary

- 진입점은 `wWinMain`이 아니라 `int main()`으로 확정한다 (사용자 결정: 추후 DirectX 외 OpenGL도 고려).
- 이번 태스크의 범위는 "순수 스텁"으로 한정한다 — `main()`이 존재하고, CMake로 `main.exe`가 빌드/실행되는 것까지만 확인한다. 창 생성, DirectX/OpenGL 초기화는 다음 태스크로 미룬다.
- 디렉토리 구조는 최소한으로만 잡는다 — `src/main.cpp` + 최상위 `CMakeLists.txt`. 전체 구조 설계는 별도의 "디렉토리 리팩토링" 태스크에서 다룬다.
- 콘솔 창이 함께 뜨는 문제(서브시스템)는 지금 단계에서는 허용하고, 창 생성 태스크 시점에 재검토한다.

# Details

## 1. 진입점: `int main()` (확정)

사용자가 이미 결정한 사항.

- 이유: DirectX 전용이 아니라 추후 OpenGL도 고려하는 API 중립적 구조를 원함.
- `wWinMain`은 Win32/DirectX에 종속적인 진입점이라, OpenGL(GLFW 등)과 병행하기에 부자연스러움.
- `int main()` + 콘솔 서브시스템으로 시작하면, 창 생성은 이후 태스크에서 Win32 API(`CreateWindowW` 등)나 GLFW 같은 라이브러리로 직접 처리 가능 — API 중립성 확보.

## 2. 이번 태스크의 구현 범위: 순수 스텁

목표(`목표` 섹션)가 다음 두 가지이므로, 범위를 여기서 넘지 않는다.

- `[ ]` 진입점 `main.cpp` 확보
- `[ ]` `main.cpp`를 빌드한 `main.exe` 확보

즉 `main()`은 아무 로직 없이 `return 0;`만 하는 상태로 두고, "CMake 빌드 → `main.exe` 생성 → 실행 시 정상 종료(exit code 0)"까지만 확인한다.

창 생성이나 그래픽 API 초기화는 포함하지 않는다 — 범위가 커지면 이번 태스크의 목적("기초 빌드 구조 확보")이 흐려지고, 다음 태스크(창/그래픽 API)와 책임이 섞인다.

## 3. 디렉토리 구조: 최소한으로

지금 구조를 다 잡지 않고, 다음만 만든다.

```
World-of-Tank-imitation-Refactoring/
  CMakeLists.txt
  src/
    main.cpp
```

- CLAUDE.md의 리팩토링 범위에 "디렉토리/프로젝트 구조 정리"가 이미 별도 항목으로 있음 — 그 태스크에서 `include/`, `assets/` 등 최종 구조를 논의하는 게 맞다.
- 지금 최종 구조까지 미리 잡으면, 이후 구조 리팩토링 태스크와 범위가 겹치고 되돌릴 작업이 생긴다.

## 4. 빌드 도구 확인 필요 (사용자 확인 요청)

- CMake generator: Visual Studio(MSVC) generator를 쓸지, Ninja를 쓸지 — 로컬에 설치된 도구에 따라 결정.
- C++ 표준 버전 (예: C++17 / C++20) — 이후 코드 스타일에 영향을 주므로 지금 정해두는 게 좋음.

# Trade-offs

| 항목 | 선택 | 장점 | 단점 / 리스크 |
|---|---|---|---|
| 진입점 | `int main()` | OpenGL 등 API 중립적, 콘솔 로그 출력이 쉬움(디버깅 용이) | 최종 배포 시 콘솔 창이 같이 뜸 → 창 생성 태스크에서 `WIN32` 서브시스템 전환 필요 (해결 가능한 리스크, 지금 당장 처리하지 않음) |
| 범위 | 순수 스텁만 | 태스크가 작고 명확함, 빌드 파이프라인만 먼저 검증 | 실제로 "동작하는" 것을 보려면 다음 태스크(창 생성)까지 기다려야 함 |
| 디렉토리 구조 | 최소(`src/`만) | 지금 결정할 게 적음, 되돌릴 위험 없음 | 최종 구조가 나중에 바뀌면 `CMakeLists.txt` 경로 일부 재수정 필요 (경미) |
| 단위 테스트 | 이번 태스크는 생략 | `return 0`만 하는 함수는 테스트할 로직이 없음 | CLAUDE.md의 "모든 기능에 단위 테스트 작성" 원칙과 형식상 충돌 — 로직이 없다는 이유로 명시적으로 예외 처리 |
