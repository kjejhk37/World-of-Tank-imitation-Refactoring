# Stage 1 — Quality Inspection

## SOLID Principles

- **SRP (Single Responsibility Principle, 단일 책임 원칙)**: 클래스/함수는 "변경되어야 할 이유"를 하나만 가져야 한다는 원칙. 책임이 두 개 이상 섞이면, 한쪽 이유로 코드를 고칠 때 다른 쪽 책임까지 의도치 않게 깨질 위험이 커짐.
  → `LaunchConfigParser`(파싱), `LaunchConfigStore`(저장), `RendererFactory`(생성), `IRenderer`/`DirectXRenderer`/`OpenGLRenderer`(초기화 스텁) 각각 단일 책임 유지. 문제 없음.

- **OCP (Open/Closed Principle, 개방-폐쇄 원칙)**: "확장에는 열려있고, 수정에는 닫혀있어야 한다"는 원칙. 새로운 동작을 추가할 때 기존 코드를 고치지 않고, 새 코드를 덧붙이는 것만으로 확장할 수 있어야 이상적.
  → `RendererFactory::Create`의 `switch`는 새 백엔드 추가 시 팩토리 내부 수정이 필요해 이 원칙을 엄밀히는 100% 만족하진 않음 — 다만 Strategy 문서에서 이미 인지하고 합의된 트레이드오프(백엔드 종류가 유한하고 팩토리 패턴에서 흔히 받아들여지는 절충)라 결함으로 보지 않음.

- **LSP (Liskov Substitution Principle, 리스코프 치환 원칙)**: 부모 타입(인터페이스)을 사용하는 코드는, 그 부모를 상속한 어떤 자식 타입으로 바꿔 끼워도 동작이 깨지지 않아야 한다는 원칙. 자식 클래스가 부모가 약속한 동작(계약)을 어기면 위반.
  → `DirectXRenderer`/`OpenGLRenderer`가 `IRenderer`를 문제없이 대체 가능. 둘 다 동일한 계약(`Initialize()`/`Shutdown()`)을 지키므로 위반 없음.

- **ISP (Interface Segregation Principle, 인터페이스 분리 원칙)**: 클라이언트가 쓰지도 않을 메서드까지 억지로 구현하게 만드는 "뚱뚱한 인터페이스"를 피하고, 꼭 필요한 메서드만 모은 작은 인터페이스로 쪼개야 한다는 원칙.
  → `IRenderer`는 `Initialize()`/`Shutdown()` 2개뿐 — 클라이언트가 필요한 만큼만 노출. 문제 없음.

- **DIP (Dependency Inversion Principle, 의존성 역전 원칙)**: 상위 모듈(정책/흐름을 결정하는 쪽)이 하위 모듈(구체적인 구현)에 직접 의존하지 않고, 둘 다 추상화(인터페이스)에 의존해야 한다는 원칙. "구체 클래스를 직접 new 하지 말고, 인터페이스 뒤로 숨겨라"에 가까움.
  → `main`은 `RendererFactory`(추상 반환 타입 `IRenderer`)에만 의존, 구체 클래스(`DirectXRenderer`/`OpenGLRenderer`)는 팩토리 내부에만 알려짐. 문제 없음.

## Library Isolation

- GoogleTest는 `tests` 타겟에만 링크 (`CMakeLists.txt`), `main`/`app_lib`은 무의존 — 확인됨. 문제 없음.

## Unit Tests / Comment Rules — 발견된 이슈 (전부 해소 완료)

- `[RESOLVED][MEDIUM]` `RendererFactory::Create`(src/renderer/RendererFactory.cpp)에 대한 단위 테스트가 없음 — enum→구체 클래스 매핑 로직이 GoogleTest로 검증되지 않고, `main.exe` 수동 실행으로만 간접 확인됨.
  **해소 방안**: `tests/RendererFactoryTest.cpp` 추가. `IRenderer`가 다형 타입(가상 소멸자 보유)이므로 `dynamic_cast`로 반환된 실제 타입을 검증.
  ```cpp
  TEST(RendererFactoryTest, CreatesDirectXRendererForDirectXBackend) {
      LaunchConfig config{RendererBackend::DirectX};
      auto renderer = RendererFactory::Create(config);
      ASSERT_NE(renderer, nullptr);
      EXPECT_NE(dynamic_cast<DirectXRenderer*>(renderer.get()), nullptr);
  }
  // OpenGL 케이스도 동일하게 추가
  ```
  `DirectXRenderer.h`/`OpenGLRenderer.h`는 내부 wrapper 클래스라 include해도 Library Isolation 위반 아님.

- `[RESOLVED][LOW]` `LaunchConfigStore::Init`/`Get`(src/config/LaunchConfigStore.cpp)에 대한 단위 테스트가 없음 — Init 후 Get이 같은 값을 반환하는지 자동으로 검증되지 않음.
  **해소 방안**: `tests/LaunchConfigStoreTest.cpp` 추가.
  ```cpp
  TEST(LaunchConfigStoreTest, GetReturnsWhatWasInitialized) {
      LaunchConfigStore::Init(LaunchConfig{RendererBackend::OpenGL});
      EXPECT_EQ(LaunchConfigStore::Get().backend, RendererBackend::OpenGL);
  }
  ```
  전역 저장소라 테스트 간 상태가 공유됨 — 각 테스트가 시작 시 반드시 `Init()`을 직접 호출해 자기 값으로 덮어쓰고 시작하면(사전 상태에 의존하지 않으면) 실행 순서와 무관하게 안전함.

- `[RESOLVED][LOW]` `src/config/LaunchConfig.h`의 `struct LaunchConfig`에 CLAUDE.md가 요구하는 전체 주석(작성자/설명/입력/출력/비고/작성일)이 없음 — 한 줄 설명만 있음.
  **해소 방안**: 함수용 Input/Output 항목을 구조체에 맞게 "필드" 관점으로 바꿔서 다음과 같이 채움.
  ```cpp
  // Author: Claude
  // Description: argv 파싱 결과를 담는 불변 값 모음. LaunchConfigStore를 통해 프로세스 전역에서 읽힌다.
  // Input: (해당 없음 — 데이터 구조체)
  // Output: (해당 없음 — 데이터 구조체)
  // Notes: 필드가 늘어나도 이 struct 하나만 확장하면 되고, 소비자(RendererFactory 등)의 시그니처는 바뀌지 않는다.
  // Date: 2026-07-15
  struct LaunchConfig { ... };
  ```

- `[RESOLVED][LOW]` `src/main.cpp`의 `int main(int argc, char** argv)`에 주석이 없음 — 이전 순수 스텁 버전 때는 사용자가 "작성 가치 없음"으로 DEFERRED 처리했지만, 지금은 파싱/예외 처리/팩토리 호출을 포함한 실질적 오케스트레이션 로직이 생겨서 재검토가 필요해 보임.
  **해소 방안**: 다음 수준의 코멘트 블록 추가.
  ```cpp
  // Author: Claude
  // Description: 진입점. argv를 파싱해 LaunchConfigStore를 초기화하고, RendererFactory로 렌더러를 생성해 초기화한다.
  // Input: argc, argv (OS가 전달하는 실행 인자)
  // Output: 종료 코드 (0: 정상, 1: 인자 파싱 실패)
  // Notes: LaunchConfigStore::Init은 반드시 이 함수 안에서, 다른 스레드가 뜨기 전에 1회만 호출되어야 한다.
  // Date: 2026-07-15
  int main(int argc, char** argv) { ... }
  ```
  → 실제로 위 코멘트 블록을 `src/main.cpp`에 적용함.

- `[RESOLVED][LOW]` `tests/LaunchConfigParserTest.cpp`가 `std::invalid_argument`를 사용하면서 `<stdexcept>`를 직접 include하지 않음 — 현재는 `<gtest/gtest.h>`를 통해 간접적으로 포함되어 컴파일되지만, 이는 우연에 의존하는 것이라 IWYU(Include What You Use) 관점에서 취약함.
  **해소 방안**: 파일 상단에 `#include <stdexcept>` 한 줄 추가. 가장 간단하고 확실한 수정.
