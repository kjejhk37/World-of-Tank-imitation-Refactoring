# WOT 릴리스 파이프라인 및 로드맵

`platform → graphics → World-of-Tank-imitation-Refactoring(WOT)` 3개 저장소를 git 소스 공유 방식에서 DLL 기반 릴리스 소비 방식으로 전환하기 위한 전체 파이프라인과, 그 안에서 WOT 저장소가 맡는 역할을 정리한 문서.
같은 내용이 형제 저장소에도 각자의 관점으로 기록되어 있다 — `platform/docs/architecture/릴리스_파이프라인_전략.md`, `graphics/docs/architecture/릴리스_파이프라인_전략.md`.
`platform_graphics_projects.md`, `게임로직_구조_현황.md`와 동일하게 사이클 종료 후에도 archive하지 않고 이 위치에 영구 보관하며, 파이프라인 관련 논의가 진행될 때마다 갱신한다.
최초 작성: 2026-08-13.

---

## 결론

- 지금은 세 저장소 모두 "릴리스 버전"이 없는 상태다 — WOT은 platform·graphics를 git submodule 소스로 직접 참조한다.
- 핵심 문제는 개발 편의성이 아니라 **검증**이다: platform/graphics가 독립적으로 검증·릴리스되지 않은 채로 WOT에 소스로 얹히기 때문에, WOT에서 문제가 생겨도 platform/graphics/WOT 중 어디가 원인인지 구분할 수 없다.
- 해결 방향은 platform을 DLL로 버전 태그를 붙여 릴리스하고, graphics는 그 특정 버전을 고정해서 소비하고 자신도 릴리스하며, **WOT은 platform·graphics 두 릴리스 버전을 고정해서 소비하는 최종 소비자**가 되는 구조다. WOT 자신은 DLL화하지 않고 소스(제품) 상태로 남는다.
- 최초 릴리스가 아예 없는 지금은 1회성 "부트스트랩 사이클"로 릴리스 인프라를 구축하는 게 목표이고, 이후에는 아래 정상 개발 사이클로 넘어간다.

## 배경 — 지금 방식의 문제

- WOT이 platform·graphics 소스를 git submodule로 직접 참조하고 있어, 하위 저장소 코드가 바뀌면 검증 없이 WOT 빌드에 그대로 흘러들어간다.
- WOT에서 버그가 발생해도 platform 문제인지 graphics 문제인지 WOT 통합 문제인지 구분할 근거가 없다 — 이번 파이프라인 도입의 직접적인 동기.
- 릴리스 단계 없이 바로 WOT 개발로 들어갔기 때문에 발생한 특이 케이스이며, 최초 릴리스 기준선을 한 번 만들고 나면 반복되지 않는다.

## 계층 컨셉 (참고: `platform_graphics_projects.md`, `게임로직_구조_현황.md`)

WOT이 지켜야 할 경계는 이미 `docs/architecture/platform_graphics_projects.md`에 확정되어 있고, 이 문서는 그 경계를 바꾸지 않는다 — 그 경계를 지킨 상태로 어떻게 "릴리스 버전 기준으로" 개발할지만 다룬다.

- **platform**: 검증된, 완전히 추상화된 최소 단위 기능/데이터 라이브러리. graphics/WOT 어느 쪽도 몰라야 한다.
- **graphics**: platform을 사용해 특정 그래픽스 API를 캡슐화하는 렌더링 계층. WOT을 몰라야 한다.
- **WOT(projects)**: platform과 graphics를 모두 사용해 이 프로젝트의 실제 동작·콘텐츠를 구현하는 최하위 계층. platform, graphics 어느 쪽도 WOT에 의존해서는 안 된다(역방향 금지).

## 전체 파이프라인 구조

```
[platform] --DLL(+header+lib+pdb), semver 태그--> [graphics] --DLL(+header+lib+pdb), semver 태그--> [WOT]
   자체 CI: merge마다 테스트 통과 필수                  platform 특정 버전 고정 + 자체 테스트         platform+graphics 특정 버전 고정, 소스로 남음(최종 제품)
```

WOT은 이 체인의 최상단 소비자다 — platform/graphics가 각자 릴리스 파이프라인을 갖춘 뒤에야 WOT도 "버전이 고정된 상태에서 개발"로 전환할 수 있다.

## 릴리스 채널: nightly(개발용) vs stable(정식)

- **nightly/prerelease**: platform/graphics가 각자 main에 merge할 때마다 자체 테스트를 통과하면 자동으로 prerelease 버전을 발행한다. WOT은 평상시 개발 중에는 이 nightly 채널을 계속 추적하며 통합 개발을 진행한다.
- **stable**: 출시가 임박하면 WOT은 nightly 추적을 멈추고 platform·graphics의 특정 stable 버전(semver 태그)에 고정(pin)한다. 이 시점부터 WOT에서 발생하는 문제는 "WOT 통합 문제"로 확신할 수 있다.
- WOT은 어떤 platform·graphics 버전을 정확히 쓰고 있는지 lockfile/manifest 형태로 기록해, 문제 재현과 원인 분리가 항상 가능하도록 한다.

## 기능 구분 프로세스 — 추상화된 기능 vs 프로젝트 특화 기능

- 새 기능이 필요할 때, `platform_graphics_projects.md`의 핵심 질문("이 타입/기능의 모양을 누가 결정하는가")으로 먼저 분류한다.
  - 누구든 재사용 가능한 일반 원칙 → platform.
  - 특정 렌더링 파이프라인의 계약 → graphics.
  - 이 프로젝트(WOT)의 콘텐츠·규칙·의사결정 → WOT.
- platform/graphics로 분류된 기능은 해당 저장소가 추상 기반(제네릭 메커니즘/인터페이스)으로 제공하고, WOT은 이를 **상속받아 구현**해 프로젝트 특화 동작을 완성한다 — WOT 전용 콘텐츠가 platform/graphics로 새어 들어가지 않도록 한다.
- 이 경계 판단은 WOT 세션 혼자 정하지 않는다. 관련 저장소(platform/graphics) 세션과 문서(브레인스토밍/전략 문서 또는 각자의 이 architecture 문서)를 주고받으며 토의하고, 필요하면 ChatGPT 등 외부 의견도 참고해 각 저장소의 컨셉이 흐트러지지 않는지 확인한 뒤에만 병합·버전을 올린다.

## 부트스트랩 사이클 vs 정상 개발 사이클

- **부트스트랩(현재, 1회성)**: platform → graphics → WOT 순서로 최초 stable 릴리스를 만들고, 각 저장소의 CI 게이트·semver 태깅·nightly/stable 채널을 구축한다. 이 흐름은 릴리스 기준선이 없는 지금만 필요한 특이 케이스다.
- **정상 개발 사이클(부트스트랩 이후 반복)**:
  1. 기능 필요사항 확인(기획).
  2. 프로젝트 내부(WOT) 개발 vs platform/graphics 개발 검토 — 위 기능 구분 프로세스를 기준으로 판단한다.
  3. 각 위치를 개발하며 프로젝트를 완성하는 과정을 반복 — platform/graphics는 이미 구축된 nightly/stable 파이프라인 위에서, WOT은 nightly 추적 후 필요 시 stable로 고정하는 흐름으로 진행한다.

## 로드맵

1. platform 최초 stable 릴리스 → graphics 최초 stable 릴리스 순서로 부트스트랩을 완료한다.
2. WOT의 git submodule 소스 의존을 릴리스 아티팩트(패키지 또는 배포 zip) 소비로 전환한다.
3. 이후 기능 개발은 "정상 개발 사이클" 절차를 따른다.
4. 이 문서는 파이프라인이 바뀔 때마다(예: 패키지 매니저 도입, CI 도구 확정 등) 갱신한다.
