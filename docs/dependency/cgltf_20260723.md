# Step 1 — Evaluation

## Alternatives

| | cgltf | tinygltf | Assimp(GLTF 지원) |
|---|---|---|---|
| 기능 범위 | GLTF/GLB 전용, 읽기+쓰기 | GLTF 전용, 읽기 위주 | GLTF 포함 40+ 포맷, 풀 씬 그래프 |
| 유지보수 상태 | 단종 신호 없음, raylib/bgfx 등 채택 | **v2가 유지보수 전용 모드 진입, 단종 예정** | 활발하나 대형 의존성 |
| 통합 난이도 | 단일 헤더(`CGLTF_IMPLEMENTATION` 매크로) | 단일 헤더(C++11) | 대형 의존성 |
| 라이선스 | MIT | MIT | BSD-3 계열 |

tinygltf는 v2가 2026년 중반부터 유지보수 전용 모드로 전환되며 단종 예정이라는 리스크 때문에 배제하고, cgltf를 선택했다.

## Risks

- glTF의 `mesh`는 여러 `primitive`(프리미티브별 별도 머티리얼)를 가질 수 있는데, 이번 사이클의 `Mesh`는 머티리얼 참조를 하나만 갖도록 단순화되어 있어, 한 mesh의 모든 primitive를 정점/인덱스 버퍼 하나로 합치고 `materialRef`는 첫 primitive의 머티리얼 이름으로 단순화했다 — 멀티 머티리얼 메쉬의 정확한 표현은 이번 사이클 스코프 밖.
- glTF 씬은 루트 노드가 여러 개일 수 있어, 이 프로젝트의 단일 루트 `Model::rootNode` 전제와 안 맞는다 — `CgltfWrapper`가 identity Transform의 합성 루트 노드로 항상 감싸는 방식으로 흡수했다.
- `has_matrix`(행렬로 직접 지정된 노드 Transform)는 이 사이클에서 shear 없음을 가정한 간이 분해(translation/rotation/scale 추출)로 처리한다 — 정확한 일반 행렬 분해가 아니다.

# Step 2 — Wrapper Design Draft

CLAUDE.md 원칙("외부 라이브러리는 반드시 내부 wrapper 클래스로 감싼다")을 그대로 적용.

- `cgltf.h`에 대한 직접 참조(및 `CGLTF_IMPLEMENTATION` 매크로 정의)는 `src/platform/model_import/CgltfWrapper.cpp` 단 한 곳에만 존재한다.
- `CgltfWrapper.h`는 `cgltf_` 접두사의 어떤 타입도 노출하지 않고, 프로젝트 공용 타입인 `Model`/`Mesh`/`Node`만 공개 인터페이스에 사용한다.
- `ModelLoader::LoadGLB`/`LoadGLTF`는 `CgltfWrapper`만 알고, cgltf의 존재 자체를 모른다. 둘 다 같은 `CgltfWrapper::Load`를 호출한다 — `cgltf_parse_file`이 GLB/GLTF를 파일 내용으로 자동 판별하기 때문에 별도 분기가 필요 없다.
- `cgltf_data`의 노드-메쉬 참조 구조를 그대로 순회해 씬 그래프 내부 인스턴싱을 보존한다(flatten하지 않음).

**빌드 타겟 격리**

- cgltf는 단일 헤더 라이브러리라 컴파일할 소스 파일이 없다 — `FetchContent`로 소스만 받아 include 경로만 `app_lib`에 `PRIVATE`로 추가한다.
- `tests` 타겟은 `ModelLoaderTest.cpp`에서 `ModelLoader.h`만 include하며, `cgltf.h`를 직접 include하지 않는다.
