# Step 1 — Evaluation

## Alternatives

| | Dear ImGui | Nuklear | RmlUi |
|---|---|---|---|
| 패러다임 | Immediate mode (매 프레임 코드로 UI 재구성) | Immediate mode, single-header | Retained mode (HTML/CSS 유사 마크업) |
| 기능 범위 | 위젯/도킹/플롯 등 게임 개발 도구 UI에 필요한 거의 모든 것 제공 | 기본 위젯 위주, 기능이 ImGui보다 적음 | 웹 스타일 레이아웃/스타일링, 게임 인게임 UI(상점/인벤토리 등)에 적합 |
| DirectX 백엔드 지원 | 공식 백엔드로 DX9/10/11/12/OpenGL/Vulkan 등 다수 제공, 이 프로젝트가 쓰는 3개 버전(DX9/11/12) 전부 커버 | 백엔드가 커뮤니티 예제 수준, 공식 DX9/11/12 지원 없음 | 자체 렌더링 인터페이스를 구현해야 함(공식 DX 백엔드 없음, 통합 비용 높음) |
| 커뮤니티/인지도 | C++ 게임/툴 개발 진영 사실상 표준 디버그 UI, 레퍼런스/예제 압도적으로 많음 | 상대적으로 마이너, 임베디드/미니멀 지향 | 인게임 UI 특화 라이브러리로 알려져 있으나 ImGui 대비 사용자층 작음 |

이번 사이클의 목표는 "기본 UI 프레임워크 확보"이며, 브레인스토밍에서 이미 이 프로젝트가 런타임에 DX9/11/12를 전환한다는 제약이 확인됨 — 세 버전 모두에 대한 **공식** 백엔드가 있는 라이브러리가 필요하고, 이 조건을 만족하는 건 사실상 Dear ImGui뿐이다.
디버그/툴 UI 용도(포트폴리오 목적의 실시간 파라미터 조정, 향후 렌더링 디버깅 오버레이 등)에도 retained-mode인 RmlUi보다 immediate-mode인 ImGui가 적합 — `Dear ImGui` 선택.

## Maintenance Status

- 저장소: `ocornut/imgui` (GitHub). 2014년부터 현재까지 지속적으로 유지보수되는 활발한 저장소.
- 최신 안정 릴리스 태그(`v1.91.x` 계열)를 `FetchContent`로 고정해서 받아온다 — `docking` 브랜치가 아닌 `master`(안정) 브랜치 기준 릴리스만 사용.
- 이슈/PR이 활발히 처리되며, 주요 그래픽 API(DX9~12, Vulkan, Metal, OpenGL 등) 백엔드가 라이브러리 본체와 함께 공식 관리됨.

## Risks

- **공식 CMake 타겟 부재**: `nlohmann::json`/`googletest`와 달리 Dear ImGui는 저장소에 소비자용 CMake 빌드 스크립트를 제공하지 않는다 — `FetchContent`로 소스를 받은 뒤 필요한 `.cpp` 목록(`imgui.cpp`/`imgui_draw.cpp`/`imgui_tables.cpp`/`imgui_widgets.cpp`/백엔드 파일)을 우리 쪽 `CMakeLists.txt`에서 직접 나열해야 한다. 이는 라이브러리 자체의 리스크라기보다 "직접 통합 비용"이 있다는 뜻 — 전략 문서에서 정확한 파일 목록으로 관리한다.
- **런타임 DX 백엔드 전환과의 상호작용**: 이 프로젝트는 `--renderer`/`config.json`으로 DX9/11/12를 런타임에 선택한다. ImGui의 각 백엔드(`imgui_impl_dx9/11/12`)는 서로 독립적인 초기화/해제 API라 렌더러 전환 시 이전 백엔드를 확실히 `Shutdown`하지 않으면 리소스 누수/크래시 위험이 있다 — 각 `DirectXnRenderer`가 자기 `ImGuiManagerDXn`을 소유하고 `Shutdown()`에서 반드시 먼저 정리하도록 구현해 해소(실제로 DX9/11/12 세 백엔드 모두 연결 완료, 아래 Step 3 참고).
- **폰트 텍스처/디스크립터 힙 관리(DX12 한정)**: `DirectX12Renderer`가 이미 갖고 있는 RTV 힙과 별개로 `ImGuiManagerDX12`가 SRV(CBV_SRV_UAV) 디스크립터 힙을 자체 소유하도록 구현 완료. 최신 ImGui(v1.92.8)는 `ImGui_ImplDX12_Init`이 `ImGui_ImplDX12_InitInfo` 구조체(+ `SrvDescriptorAllocFn`/`FreeFn` 콜백)를 요구하는 API로 바뀌어 있었다(브레인스토밍 당시 가정한 구버전 시그니처와 다름) — 이번 사이클은 폰트 아틀라스 텍스처 하나만 쓰므로 힙의 유일한 슬롯을 그대로 내주는 최소 콜백으로 구현.
- **빌드 시간 증가**: `imgui.cpp` 등 소스가 header-only는 아니지만 파일 수/크기가 작아(수천 줄 수준) `nlohmann::json` 단일 헤더보다 오히려 컴파일 단위가 잘게 나뉘어 있어 증분 빌드에 유리한 편 — 실질적 리스크 낮음.

# Step 2 — Wrapper Design Draft

CLAUDE.md 원칙("외부 라이브러리는 반드시 내부 wrapper 클래스로 감싼다")을 그대로 적용한다. (최종 설계는 브레인스토밍 중 DX9/11/12 전부 연결로 확정되어, 아래는 DX11 단일안이 아닌 최종 구현 구조를 반영한다.)

- `imgui.h`/`imgui_impl_win32.h`/`imgui_impl_dx9.h`/`imgui_impl_dx11.h`/`imgui_impl_dx12.h`에 대한 직접 참조는 각각 `src/graphics/ui/directx9/ImGuiManagerDX9.cpp`, `src/graphics/ui/directx11/ImGuiManagerDX11.cpp`, `src/graphics/ui/directx12/ImGuiManagerDX12.cpp` 단 한 곳에만 존재한다.
- 공용 인터페이스 `src/graphics/ui/IUiManager.h`는 ImGui 타입을 전혀 노출하지 않는다 — `NewFrame()`/`Render()`/`Shutdown()`/`HandleWin32Message(HWND,UINT,WPARAM,LPARAM)`만 순가상함수로 둔다. `Initialize`는 백엔드마다 필요한 DX 타입이 완전히 달라 인터페이스에 넣지 않고, 각 구현체가 자신에게 맞는 생성자를 갖는다.
- `DirectX9Renderer`/`DirectX11Renderer`/`DirectX12Renderer`가 각각 자기 짝 `ImGuiManagerDX9`/`DX11`/`DX12`를 멤버로 소유하며, `main.cpp`/`Win32Window`/`RendererFactory`는 이들의 존재 자체를 모른다. ImGui 백엔드는 `config.renderer` 선택에 자동 종속되고 별도 config 필드는 없다.
- `Win32Window`는 범용 `SetMessageHook` 콜백만 제공 — ImGui를 포함해 어떤 특정 UI 라이브러리도 알지 못한다.
- DX12만 draw call 기록에 커맨드 리스트가 필요해 `IUiManager::Render()`(무인자)로 표현이 안 된다 — `ImGuiManagerDX12`에 인터페이스 밖 전용 메서드 `RenderWithCommandList(ID3D12GraphicsCommandList*)`를 추가하고, `DirectX12Renderer`는 `IUiManager*`가 아니라 구체 타입으로 직접 호출한다.

**빌드 타겟 격리 (`nlohmann_json`/`googletest` 사례와 동일 원칙)**

- ImGui 관련 소스는 전부 `app_lib`에 포함되고, include 경로는 `PRIVATE`로 격리 — `main`/`tests` 타겟의 include 경로 상으로 ImGui 헤더가 노출되지 않는다(grep으로 확인 완료).
- `tests`의 `ImGuiManagerDX9/11/12Test.cpp`는 `ImGuiManagerDXn.h`(공개 인터페이스)와 표준 DX SDK 헤더(`<d3d9.h>` 등, 기존 `DirectX9/11/12RendererTest`와 동일)만 include하고, `imgui.h`를 직접 include하지 않는다.

# Step 3 — Verification Status

- `[x] Verified` — CMake `FetchContent`로 ImGui v1.92.8 소스를 받아 `app_lib`에 통합 (`main`/`tests`는 include 경로 상으로 ImGui에 무의존 — grep으로 확인)
- `[x] Verified` — `ImGuiManagerDX9`/`DX11`/`DX12`가 각각 `DirectX9/11/12Renderer`의 디바이스(+DX11은 컨텍스트, DX12는 커맨드 큐)로 정상 초기화됨 (`ImGuiManagerDX9/11/12Test` 6개 케이스 통과)
- `[x] Verified` — `Win32Window::SetMessageHook`이 메시지를 받고, `true` 반환 시 그 자리에서 처리를 끝내며, `false` 반환 시 기존 리사이즈 콜백이 정상 동작함(`Win32WindowTest` 2개 신규 케이스)
- `[x] Verified` — `main.exe --renderer=directx9`/`directx11`/`directx12` 각각 실행 시 크래시 없이 창이 뜸(수동 확인, 1.5초간 프로세스 생존 확인 — 시각적 ImGui 콘텐츠는 없음, 빌드까지만 검증하기로 확정된 범위)
- `[x] Verified` — `ImGuiManagerDXn::Shutdown`이 각 렌더러의 `Shutdown()`에서 디바이스 해제보다 먼저 호출됨(코드 검토 + 전체 72개 테스트 통과로 크래시/누수 징후 없음 확인)
- `[ ] Unverified` — 렌더러 리사이즈 시 ImGui 오버레이가 크래시 없이 함께 반응하는지는 기존 `SurvivesResizeAndRenderFrame` 계열 테스트로 간접 확인되었으나(리사이즈 후 `RenderFrame` 정상 동작), ImGui `DisplaySize` 갱신 자체를 직접 검증하는 케이스는 없음 — 실제 UI 위젯을 그리는 다음 사이클에서 시각적으로 재확인 필요
