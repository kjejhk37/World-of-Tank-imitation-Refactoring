# How

브레인스토밍에서 확정된 내용을 다음과 같이 코드/파일로 적용한다.

## 1. 디렉토리/파일 구조

```
src/
  main.cpp
  config/
    LaunchConfig.h            (struct LaunchConfig { RendererBackend backend; };)
    LaunchConfigParser.h/.cpp  (LaunchConfig ParseLaunchConfig(int argc, char** argv);)
    LaunchConfigStore.h/.cpp   (namespace 기반 전역 저장소: Init(LaunchConfig) / Get())
  renderer/
    RendererBackend.h       (enum class RendererBackend { DirectX, OpenGL };)
    IRenderer.h             (인터페이스: Initialize() / Shutdown())
    RendererFactory.h/.cpp  (std::unique_ptr<IRenderer> Create(const LaunchConfig&);)
    DirectXRenderer.h/.cpp  (IRenderer 구현, 스텁)
    OpenGLRenderer.h/.cpp   (IRenderer 구현, 스텁)
tests/
  LaunchConfigParserTest.cpp   (GoogleTest — ParseLaunchConfig 케이스)
```

이름을 `AppConfig` → `LaunchConfig`로 변경 — "부팅 시점에 1회 결정되고 이후 불변"이라는 성격을 이름에 명시하기 위함 (사용자 확인, Q&A Log 참고).

## 2. 인자 파싱 규칙 (`ParseLaunchConfig`)

- 지원 플래그: `--renderer=directx`, `--renderer=opengl` (대소문자 구분).
- 플래그 누락 시: 기본값 `RendererBackend::DirectX` 반환 (이 프로젝트의 실질적 목표가 DirectX 마이그레이션이므로 기본값으로 채택 — 이견 있으면 Q&A로 알려줄 것).
- 알 수 없는 값(`--renderer=foo` 등) 입력 시: `std::invalid_argument` 예외를 던짐.
- `main.cpp`는 이 예외를 catch해서 표준 에러에 메시지를 출력하고 0이 아닌 종료 코드를 반환한다.

## 3. `LaunchConfigStore` 초기화 규칙

- `main()` 진입 직후, 다른 스레드가 뜨기 전에 `LaunchConfigStore::Init(ParseLaunchConfig(argc, argv))`를 단 한 번 호출한다.
- 이후 `LaunchConfigStore::Get()`은 읽기 전용으로만 사용하며, 재초기화하지 않는다 (브레인스토밍에서 합의한 "쓰기 후 불변" 규칙 — 이름 자체가 이 계약을 표현함).

## 4. `main.cpp` 흐름

```cpp
int main(int argc, char** argv) {
    try {
        LaunchConfigStore::Init(ParseLaunchConfig(argc, argv));
    } catch (const std::invalid_argument& e) {
        // 에러 메시지 출력 후 종료
        return 1;
    }
    auto renderer = RendererFactory::Create(LaunchConfigStore::Get());
    renderer->Initialize();
    return 0;
}
```

## 5. CMake 구성 변경

- 프로덕션 소스를 정적 라이브러리 타겟 `app_lib`으로 묶는다 (`config/`, `renderer/` 하위 `.cpp` 전부).
- `main` 타겟은 `src/main.cpp`만 컴파일하고 `app_lib`을 링크한다.
- `FetchContent`로 GoogleTest 1.17.0을 받아와 `tests` 타겟에서만 링크한다 (`dependency_eval.md`에서 합의한 "빌드 타겟 분리" 격리 방식 — `main` 타겟은 GoogleTest에 전혀 의존하지 않음).
- `enable_testing()` + `gtest_discover_tests(tests)`로 CTest 연동.

## 6. 단위 테스트 케이스 (`tests/LaunchConfigParserTest.cpp`)

- `--renderer=directx` → `RendererBackend::DirectX`로 파싱됨을 확인.
- `--renderer=opengl` → `RendererBackend::OpenGL`로 파싱됨을 확인.
- 플래그 없음 → 기본값 `RendererBackend::DirectX` 확인.
- `--renderer=foo` → `std::invalid_argument` 예외 확인 (`EXPECT_THROW`).

## 7. 주석 규칙

Step 4 구현 시 CLAUDE.md의 주석 작성 규칙(작성자/설명/입력/출력/비고/작성일)을 모든 신규 함수·클래스에 적용한다. 특히 `LaunchConfigStore`의 "1회 초기화, 이후 불변" 제약은 비고(트레이드오프/리스크) 항목에 반드시 명시한다.

# Q&A Log

- **Q.** `Config`라는 단어에 대해 어떻게 생각해? 오해가 없을까?
  **A.** "Config"는 일반적으로 "가변, 지속성 있는 설정"이라는 뉘앙스가 강해서, 우리가 정한 "부팅 시 1회 결정 후 불변" 규칙과 이름만으로는 잘 안 드러남 (실제로 Unreal의 `GConfig`도 이름은 Config지만 런타임 가변임 — 혼동 여지 있음). 이 성격을 이름에 담기 위해 `LaunchConfig`를 제안.

- **Q.** (지시) `LaunchConfig`로 변경해서 전략 다시 작성.
  **A.** 반영. `AppConfig`/`AppConfigParser`/`AppConfigStore` → `LaunchConfig`/`LaunchConfigParser`/`LaunchConfigStore`로 전면 변경.

- **Q.** (결정) 플래그 누락 시 기본값 `DirectX` 동의, 알 수 없는 값 입력 시 처리 방식은?
  **A.** 기본값 `DirectX` 동의. 알 수 없는 값 입력 시 "main에서 바로 오류 코드를 내보내면서 종료" — 기존 설계(`ParseLaunchConfig`가 `std::invalid_argument` throw → `main`이 catch해서 에러 메시지 출력 후 0이 아닌 종료 코드 반환)와 일치, 그대로 확정.
