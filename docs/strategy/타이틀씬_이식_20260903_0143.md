# Strategy: Scene 전환 매커니즘 정비 + Title/Loading 최소 스텁

## 목적

브레인스토밍에서 확정된 대로, 이번 사이클의 핵심은 "TitleScene 이식"이 아니라
**여러 씬을 전환하는 매커니즘 자체를 정비**하는 것이다.
`TitleScene`/`LoadingScene`은 그 매커니즘을 검증할 최소 스텁으로만 둔다.

Cross-repo 의존성 검토: 아래 모든 항목이 `projects`(이 저장소) 내부에서 완결된다.
`ImageUI`/`ButtonUI`/`LabelUI`(graphics), `Log::Info`/`ConsoleLogSink`(platform)는 이미 구현된 기존 기능을
그대로 재사용할 뿐, `platform`/`graphics`에 새 기능을 요청할 필요가 없다.
따라서 전 항목이 `[self]`이며, `team_task_delegation.md`를 거칠 항목이 없다.

## Checklist

### Phase 1 — SceneManager 싱글턴 전환 + 스냅샷 선택 책임 추가

- [ ] `[self]` `SceneManager`를 싱글턴으로 전환 (`SceneManager::Get()` 정적 접근자)
- [ ] `[self]` 테스트 격리를 위해 `SceneManager::ResetForTest()`(또는 동등한 메서드) 추가 — 단위테스트마다 등록된 씬/활성 목록을 초기화
- [ ] `[self]` `SceneManager`에 "현재 스냅샷 대상 씬" 지정 책임 추가 — 예: `SetCurrent(key)` / `GetCurrentScene() const` (등록된 여러 씬 중 어느 것의 엔티티를 스냅샷에 반영할지 선택)
- [ ] `[self]` `SceneSnapshotBuilder::Build`를 `GetActiveScenes()` 전체 순회 대신 `GetCurrentScene()` 하나만 반영하도록 수정

### Phase 2 — 기존 GameManager 제거

- [ ] `[self]` `src/projects/game/GameManager.h`/`.cpp` 삭제
- [ ] `[self]` `InstanceUpdateWorker::Run()`이 `SceneManager::Get()`을 직접 호출하도록 수정 (로컬 `GameManager gameManager;` 제거)

### Phase 3 — UnitTestScene + SceneManager 단위테스트

- [ ] `[self]` `UnitTestScene`(더미 `Scene` 구현체, 테스트 전용) 작성 — 엔티티 1개 + `TransformComponent`를 생성해 스냅샷 검증에 사용
- [ ] `[self]` `SceneManagerTest`: 기본 생명주기(Create/Add/Remove/Update) 단위테스트
- [ ] `[self]` `SceneManagerTest`: `SetCurrent`로 지정한 씬의 엔티티만 `SceneSnapshotBuilder`가 반영하는지 검증(여러 씬이 동시에 active여도 `GetCurrentScene()` 아닌 씬은 스냅샷에 안 섞이는 케이스 포함)

### Phase 4 — TitleScene / LoadingScene 최소 스텁

- [ ] `[self]` `TitleScene`(빈 로직 + 자신을 식별하는 라벨 텍스트 하나) 작성 — `IntroScene`과 동일한 패턴(렌더링 없음, 위젯은 `main.cpp` 소유)
- [ ] `[self]` `LoadingScene`(빈 로직 + 라벨 텍스트 하나) 작성
- [ ] `[self]` `main.cpp`: 활성/현재 씬에 따라 그릴 위젯 세트(라벨 하나 + 필요 시 전환 버튼)를 교체하는 로직 추가 — `IntroUi` 패턴을 일반화

### Phase 5 — 전환 트리거 + 콘솔 로그 검증

- [ ] `[self]` 각 스텁 화면에 전환용 버튼 하나 추가 (Intro → Title → Loading 순환 또는 유사)
- [ ] `[self]` 버튼 클릭 시 `SceneManager::Get().Remove(이전)/Add(다음)/SetCurrent(다음)` 호출 배선
- [ ] `[self]` 씬 `Start()`/`End()`와 버튼 클릭 시점에 `Log::Info(...)` 호출 추가 — 콘솔에 전환 이벤트 순서가 출력되는지 확인 (별도 콘솔 할당 불필요 — `main` 타겟이 이미 콘솔 서브시스템)

### Phase 6 — 빌드/테스트 검증

- [ ] `[self]` 전체 빌드 + 기존 테스트 전부 통과 확인
- [ ] `[self]` `main.exe` 실행 후 버튼 클릭으로 Intro→Title→Loading 전환 및 콘솔 로그 출력을 수동 확인

## 요약

- 만들 것: `SceneManager` 싱글턴 + 현재 스냅샷 대상 씬 선택, `GameManager` 삭제, `UnitTestScene` 기반 단위테스트, `TitleScene`/`LoadingScene` 스텁과 버튼 전환, 콘솔 로그 검증.
- 모든 항목이 `projects` 저장소 안에서 끝나는 `[self]` 항목이며 `graphics`/`platform`에 요청할 것이 없다.
- 승인 기준: 체크리스트 17개 항목을 한 항목씩 승인받은 뒤 구현하고, 빌드 + 전체 테스트 통과 + `main.exe` 수동 실행으로 씬 전환과 콘솔 로그를 확인한다.

## 사용자 결정 사항

1. 목적 재정의 — "TitleScene 이식"이 아니라 "여러 씬을 전환하는 매커니즘을 정비하고, TitleScene/LoadingScene은 그 매커니즘을 검증할 최소 스텁으로 둔다".
   → 원본 TitleScene의 실제 콘텐츠 구현은 이번 사이클 범위에서 빠진다.
2. `SceneManager`를 원본과 같은 싱글턴으로 전환하고, 활성 씬 중 어느 씬의 스냅샷을 가져올지 선택하는 책임까지 맡긴다.
   → 2026-08-11 게임로직 이식 사이클의 DI 결정을 되돌리며, 테스트마다 리셋이 필요한 격리 트레이드오프를 감수한다. 이 때문에 `ResetForTest()` 항목이 체크리스트에 들어간다.
3. 기존 `GameManager` 클래스는 삭제하고 `InstanceUpdateWorker`가 `SceneManager::Get()`을 직접 호출한다.
   → Phase 2(기존 GameManager 제거)가 생긴다.
4. `SceneSnapshotBuilder`는 `SceneManager`가 선택한 씬만 반영한다.
   → `InstanceSnapshot`(graphics)과 `DoubleBufferPublisher<T>`(platform) 계약 변경이 필요 없어 전 항목이 `[self]`가 된다.
5. `WOTScene`/`WOTGameManager`는 만들지 않으며, 앞으로 WOT 고유 게임 콘텐츠 클래스에는 `WOT` 접두사를 붙인다.
   → 이번 사이클의 스텁 씬은 `TitleScene`/`LoadingScene`처럼 엔진 흐름 검증용 이름을 쓴다.
6. 개별 오브젝트 병렬 연산 설계는 `WOTGameManager`를 실제로 개발하는 미래 사이클로 이연한다.
   → 커밋 리포트에 범위 밖으로 명시한다.
7. 더미 씬 `UnitTestScene`으로 `SceneManager` 생명주기와 스냅샷 선택 로직을 단위테스트한다.
   → Phase 3(UnitTestScene + SceneManager 단위테스트)이 생긴다.
8. `TitleScene`/`LoadingScene`은 최소 스텁 + 구분용 라벨 텍스트 하나씩으로 둔다.
   → Phase 4(TitleScene / LoadingScene 최소 스텁)의 범위가 라벨 수준으로 제한된다.
9. 스텁 씬 간 전환은 버튼 클릭으로 트리거하고 `Log::Info` + `ConsoleLogSink`로 콘솔에 전환 순서를 출력해 검증한다.
   → Phase 5(전환 트리거 + 콘솔 로그 검증)가 생기며 별도 콘솔 할당은 필요 없다.
10. 로고 페이드인, 튜토리얼 페이지, 종료 확인 페이지, 배경음악은 제외한다.
    → 커밋 리포트에 범위 밖 항목으로 명시한다.

## 사용자 확인 사항

아래 체크리스트 항목은 모두 아직 승인되지 않았다.
각 항목은 Before / After 코드와 수정 이유를 채운 뒤 한 턴에 하나씩 승인을 요청하며, 권장 답은 전 항목 "승인"이다.
승인되면 해당 항목에 `(승인됨)`을 붙이고 이 목록에서 뺀다. 피드백이 오면 그 항목을 고쳐 다시 제시한다.

1. SceneManager 싱글턴 전환(`SceneManager::Get()`)을 승인하는가?
2. 테스트 격리용 `SceneManager::ResetForTest()` 추가를 승인하는가? — 제품 코드에 테스트용 메서드가 노출되는 트레이드오프가 있다.
3. `SceneManager`에 현재 스냅샷 대상 씬 지정 책임(`SetCurrent` / `GetCurrentScene`) 추가를 승인하는가?
4. `SceneSnapshotBuilder::Build`가 `GetCurrentScene()` 하나만 반영하도록 하는 수정을 승인하는가?
5. `GameManager.h`/`.cpp` 삭제를 승인하는가?
6. `InstanceUpdateWorker::Run()`이 `SceneManager::Get()`을 직접 호출하도록 하는 수정을 승인하는가?
7. 테스트 전용 더미 씬 `UnitTestScene` 작성을 승인하는가?
8. `SceneManagerTest` 기본 생명주기(Create/Add/Remove/Update) 단위테스트를 승인하는가?
9. `SceneManagerTest`에서 여러 씬이 동시에 활성이어도 현재 씬만 스냅샷에 반영되는지 검증하는 테스트를 승인하는가?
10. `TitleScene` 최소 스텁(빈 로직 + 라벨 하나) 작성을 승인하는가?
11. `LoadingScene` 최소 스텁(빈 로직 + 라벨 하나) 작성을 승인하는가?
12. `main.cpp`에서 현재 씬에 따라 위젯 세트를 교체하는 로직(`IntroUi` 패턴 일반화) 추가를 승인하는가? — 지난 사이클에서 보류한 "`BuildIntroUi()` 분기 단위테스트(fake `IRenderer` 필요)"를 이 항목에 함께 넣을지도 이때 결정한다. 넣으면 범위가 커지고, 빼면 보류 상태가 유지된다.
13. 각 스텁 화면에 전환용 버튼 하나를 추가하는 것을 승인하는가?
14. 버튼 클릭 시 `SceneManager::Get().Remove(이전)/Add(다음)/SetCurrent(다음)` 호출 배선을 승인하는가?
15. 씬 `Start()`/`End()`와 버튼 클릭 시점의 `Log::Info` 호출 추가를 승인하는가?
16. 전체 빌드 + 기존 테스트 통과 확인 절차를 승인하는가?
17. `main.exe` 실행 후 버튼으로 Intro→Title→Loading 전환과 콘솔 로그를 사용자가 수동 확인하는 절차를 승인하는가? — 화면 출력은 Claude가 볼 수 없으므로 사용자 확인이 필요하다.
