# Brainstorming: 게임 기본 기능 채우기

## Details

Task 문서에 추가된 목표(`UI 및 Rendering 이식`, `WOT 내부에 존재하는 시작 UI 이식 (Button, Event, 설명 UI등)`)의 실제 범위를 정하기 위해 `WOT-master`(D3DX_2209)를 직접 확인했다.

### 확인 1 — `Objects/UI`에는 Button/Event 클래스가 없다

- `Objects/UI`에는 `UIImage`, `ProgressBar` 두 클래스만 존재한다.
- `UIImage`는 텍스처 하나를 quad 메시로 그리는 순수 렌더링 오브젝트다 — 클릭/입력 처리, 콜백, 이벤트 로직이 전혀 없다.
- `ProgressBar`는 `UIImage`를 상속해 `Shaders/UI/ProgressBar.hlsl`로 값(0~1)을 시각화하는 것뿐이다 — 역시 입력/이벤트 없음.
- 저장소 전체(`class.*Button`, `class.*Event` 패턴)를 검색한 결과 `Button`/`Event` 이름의 클래스는 어디에도 없다.
- `GameManager.cpp`의 `ImGui::` 사용처는 FPS 표시 + `Inspector`라는 디버그 패널 하나뿐 — 플레이어용 UI가 아니라 개발자 디버그 도구다.

### 확인 2 — "시작 UI"에 해당하는 씬 자체가 빈 스텁이다

- `Scene/WOT/WOT.h`/`WOT.cpp`는 이름상 "World of Tank를 대표하는 실제 Scene"이라는 주석만 있고, `Update`/`PreRender`/`Render`/`PostRender`/`GUIRender` 5개 메서드가 전부 빈 함수다.
- 즉 원본 코드에도 "게임 시작 화면", "설명 UI", "버튼으로 시작" 같은 기능이 만들어진 적이 없다 — 이식할 원본 구현 자체가 존재하지 않는다.

### 확인 3 — `TestScene`에는 실제 렌더링 콘텐츠가 있다

- `TestScene`은 `Tank01_Body`/`Tank01_Gun`/`Tank01_Turret` 3개 `Model`, `BoxCollider` 2개(`collider_Body`/`collider_Turret`), `Outline`(포스트 이펙트, `RenderTarget`+`DepthStencil` 별도 사용), `Trail`, `TestOutlineObject`(naruto 2개)로 구성된다.
- 이 중 `Outline`/`Trail`은 `Objects/PostEffect`에 있는 별도 렌더링 이펙트로, "UI"가 아니라 "게임 오브젝트 시각 효과"에 해당한다.
- 즉 Task 문서의 "UI 및 Rendering 이식"은 실제로는 성격이 다른 두 가지를 가리킬 수 있다 — (a) `Objects/UI`의 화면 오버레이(이미지/프로그레스바류), (b) `TestScene`의 3D 오브젝트 렌더링 효과(Outline/Trail). 이 둘은 이식 난이도와 의존 대상(graphics 계층 vs projects 계층)이 다르다.

### 확인 4 — 사용자가 진행 방향을 구체화함 (2D UI 프레임워크 우선)

- Open Question 1(신규 설계 여부)에 대한 답이 나왔다 — 원본에 없던 것을 이번 사이클에서 신규 설계하는 쪽으로 확정.
- 우선순위 라인: **`Button UI` → `Progress UI` → `String Field UI`** 순서로 2D UI 프레임워크(입력/상태 처리 포함하는 기반 클래스들)를 먼저 작성한다.
- 그 다음 단계로, 이 UI들에 `Image`를 붙인다 — `Image` 자체(텍스처 렌더링)는 `WOT-master`의 `Objects/UI/UIImage`를 그대로 활용할 수 있을 것으로 예상(확인 1 참고: quad 메시 + 텍스처 렌더링만 하는 순수 렌더링 오브젝트).
- 즉 진행 순서는 "입력/상태를 가진 UI 위젯 골격 완성 → 그 위에 기존 `UIImage` 렌더링 이식을 붙여 실제로 보이게 만든다"로 재정렬됐다. 이전엔 "Image 이식"과 "Button/Event 설계"를 구분하지 않았지만, 이번에 **Image(렌더링)가 UI 위젯(입력/상태)의 하위 구성 요소**라는 관계로 명확해졌다.

### 확인 5 — `team_task_delegation` 활용 의사

- 사용자가 이번 사이클에서 `team_task_delegation.md` 워크플로우를 실제로 사용해보고 싶어한다.
- 이 워크플로우는 `agent_harness/CLAUDE.md`에 따라 **Step 3(Strategy) 체크리스트 항목에 `[graphics]`/`[platform]`/`[mixed]` 태그가 붙을 때만** 트리거된다 — 지금은 아직 Step 2(Brainstorming) 단계라 아직 이르다.
- Button/Progress/StringField UI가 화면에 그려지려면(quad 렌더링, 셰이더, RenderTarget 등) `graphics` 계층의 렌더링 계약이 필요할 가능성이 높다 — `docs/architecture/platform_graphics_projects.md` 기준으로 "특정 렌더링 파이프라인의 계약"은 `graphics` 소속이므로, Strategy 체크리스트를 나눌 때 이 부분이 `[graphics]` 태그를 받을 후보.
- 따라서 이번 브레인스토밍에서 "UI 위젯의 입력/상태 로직(=projects 또는 platform 몫)"과 "화면에 그리는 렌더링 계약(=graphics 몫)"을 구분해두면, Strategy 단계에서 자연스럽게 `[graphics]` 항목을 뽑아 `team_task_delegation`으로 넘길 수 있다.

### 확인 6 — Label UI 확정 + 텍스트 관련 원본 자산 서베이

- 사용자가 `Label UI`를 4번째 기본 위젯으로 확정했다. 대상 위젯: **Button / Progress / StringField / Label**.
- `Objects/UI`(Button/Event 없음), `Textures/UI/`(`cancel.png`, `cursor.png`, `hp_bar*.png`), 저장소 전체(Slider/Checkbox/Dropdown/Tooltip/Panel/Window/Menu 클래스명)를 검색했지만 4종 외의 새로운 위젯 타입은 없었다.
- `cursor.png`(크로스헤어용 `UIImage` 재사용), `cancel.png`(`Material::UnselectMap`의 `ImGui::ImageButton` 아이콘 — 에디터 툴용, 플레이어 UI 아님), `hp_bar*.png`(이미 `ProgressBar`가 커버) — 전부 새 위젯 타입 근거가 안 됨.
- 유일하게 새로 걸린 것은 `Framework/Utility/Font`(Direct2D/DirectWrite 기반 텍스트 렌더링, Singleton) — 지금은 `GameManager`의 FPS 표시 등 디버그 텍스트에만 쓰이고, `Objects/UI` 계열(GameObject 기반)과 무관한 별도 유틸이며 **DX11 전용**이라 그대로 이식 불가.

### 확인 7 — 이미 이식된 `graphics/ui`(ImGui 프레임워크)가 있다 → 구현 경로의 핵심 갈림길

- `src/graphics/ui/IUiManager.h` + `ImGuiManagerDX{9,11,12}`가 2026-07-19 사이클에 이미 이식되어 있다. 단, 지금 인터페이스는 `NewFrame()`/`Render()`/`Shutdown()`/`HandleWin32Message()` 뿐이고, Button/Text 같은 위젯 호출 메서드는 하나도 없다.
- `src/projects` 어디에도(`main.cpp` 포함) 이 `IUiManager`가 아직 실제로 생성·호출되지 않는다 — 존재는 하지만 미사용 상태. 이번 사이클이 사실상 첫 실사용이 된다.
- ImGui 자체에는 `ImGui::Button`/`ImGui::ProgressBar`/`ImGui::InputText`/`ImGui::Text`처럼 지금 만들려는 4종 위젯에 1:1로 대응하는 즉시모드(immediate-mode) 위젯이 이미 있다.
- `WOT-master`에서 ImGui는 `Inspector`(개발자 디버그 패널)에만 쓰였다 — 플레이어가 보는 화면에 쓰인 적은 한 번도 없다.
- 이 때문에 구현 경로가 두 갈래로 갈린다.

**Option A — ImGui 기반 (graphics/ui 확장)**

- `graphics`가 `IUiManager`(또는 별도 인터페이스)에 `Button(text)`/`ProgressBar(fraction)`/`InputText(...)`/`Text(...)` 같은 계약 메서드를 추가하고, DX9/11/12 구현체는 내부적으로 해당 ImGui 호출로 위임한다.
- Core Development Principle("외부 라이브러리는 반드시 내부 wrapper로 감싸고, 다른 모듈은 직접 참조 금지")을 지키려면 이 방식이 필수다 — `projects`가 `<imgui.h>`를 직접 include해서 `ImGui::Button(...)`을 부르면 이 원칙 위반.
- `platform`엔 이 옵션에서 당장 새로 추가할 게 마땅치 않다 — ImGui가 상태/입력/렌더링을 이미 다 처리하기 때문(YAGNI).
- `projects`는 새 화면(예: `WOT.cpp`가 비어있던 자리를 채우는 씬)에서 wrapper 메서드만 호출해 Label+Button+ProgressBar+StringField를 조합하고, 클릭 시 `SceneManager` 전환 같은 게임 로직을 붙인다.
- 장점: 개발량이 훨씬 적다 — 이미 이식된 3-백엔드 인프라를 그대로 재사용.
- 단점: ImGui 특유의 "개발자 디버그 툴" 룩앤필이 그대로 드러나 커스텀 스킨 자유도가 낮다(불가능하진 않지만 별도 스타일링 작업 필요). 포트폴리오 관점에서 "그냥 ImGui를 갖다 썼다"로 보일 위험이 있다.

**Option B — `WOT-master`식 커스텀 위젯 (Objects/UI 확장)**

- `graphics`가 quad 렌더링 계약을 확장하고, 텍스트 래스터라이징을 DX9/11/12 세 백엔드 모두에 맞게 새로 설계해야 한다 — 원본 `Font`는 DX11 Direct2D 전용이라 그대로 못 쓴다.
- `platform`은 렌더링에 종속되지 않는 메커니즘(위젯 상태 FSM: idle/hover/pressed/disabled, 2D hit-test: 사각형 포함 판정)을 담당할 수 있다 — `entity_component` 패턴처럼 재사용 가능한 형태로.
- `projects`는 실제 위젯 배치, 텍스트 콘텐츠, 클릭 핸들러를 담당.
- 장점: 원본과 동일한 렌더링 파이프라인 설계 경험(셰이더/텍스트 래스터라이징 등) — 포트폴리오 학습 가치가 크다. 룩앤필 자유도도 높다.
- 단점: 개발량이 훨씬 크다. 특히 텍스트 렌더링을 3개 백엔드용으로 새로 설계하는 작업이 상당한 비중을 차지할 것으로 예상된다.

### 확인 8 — `projects`가 상속받아 쓸 위젯 베이스 클래스의 생성/관리 주체

사용자가 지적한 지점: `projects`에서 쓰는 구체 위젯(예: "시작" 버튼)은 분명 `ButtonUI` 같은 베이스 클래스를 **상속**받을 텐데, 이 베이스 클래스 자체와 그 인스턴스들의 생성/관리를 어떻게 할 것인가.

**베이스 클래스(`ButtonUI`/`ProgressUI`/`StringFieldUI`/`LabelUI`)는 어디 소속인가**

- `docs/architecture/platform_graphics_projects.md`의 `InstanceSnapshot` 사례(필드가 순수 데이터처럼 보여도, 모양을 결정하는 주체가 렌더링 파이프라인이면 graphics 소속)를 그대로 적용하면: 이 베이스 클래스들은 결국 `IUiManager`(ImGui) 호출을 감싸는 게 본질이라 **graphics 소속**이 된다. `platform/entity_component::ComponentBase`(렌더링에 완전히 무지한 제네릭 베이스)와는 성격이 다르다 — `ButtonUI`는 처음부터 "ImGui라는 특정 UI 백엔드로 그린다"는 지식을 내장하므로 platform 자격(완전한 렌더링 무지)을 충족 못 한다.
- `projects`는 이 graphics 베이스를 상속해 WOT 전용 구체 위젯(예: `StartButton : ButtonUI`, `PlayerNameField : StringFieldUI`)을 만든다 — `TransformComponent : ComponentBase`(platform 베이스 → projects 구체)와 같은 구조를, 소속만 platform→graphics로 바꿔 그대로 재사용하는 셈이다.

**인스턴스 생성/관리는 누가 하는가 — 두 가지 모델**

- **모델 1(권장) — 별도 매니저 없이 직접 소유(plain composition)**: `IUiManager`는 프레임 생명주기(`NewFrame`/`Render`/`Shutdown`)만 책임지는 얇은 wrapper로 남기고, `StartButton`/`PlayerNameField` 같은 구체 위젯 인스턴스는 이들을 쓰는 `Scene`(또는 다음에 만들 화면 단위)이 멤버로 직접 소유한다 — 지금 `TestScene`이 `Model* body`/`Outline* outline`/`Trail* trail`을 그냥 멤버로 들고 있는 것과 동일한 패턴. 매 프레임 `IUiManager::NewFrame()` ~ `Render()` 사이에서 각 위젯의 `Render()`를 직접 호출한다.
  - 근거: 지금 프로젝트에서 "키로 등록해 컬렉션을 관리"하는 Manager(`EntityManager`/`SceneManager`)는 전부 "런타임에 개수가 가변적이고, 외부에서 key로 조회해야 하는" 대상에만 쓰였다. Button/Label처럼 화면 하나에 몇 개 없고 소유 Scene이 명확한 대상까지 Manager로 감싸는 건 이 프로젝트가 이미 한 번 YAGNI로 보류한 패턴(확인 — 2026-08-11 사이클 DEFERRED 이슈 중 "Entity 제거 미설계"도 같은 맥락: 지금 없는 요구를 미리 대비하지 않는다)과 같은 기준으로 과설계 위험.
- **모델 2 — 전용 Manager(예: `UiElementManager`)가 key로 생성/보유**: `SceneManager::Create(key, scene)`과 동일한 패턴으로 위젯을 등록·조회. 나중에 여러 `StringField` 사이 탭 순서, 전역 포커스 관리, 위젯 활성/비활성 일괄 제어 같은 요구가 생기면 필요해질 수 있는 구조.
  - 지금 시점엔 이런 요구가 구체적으로 없다 — YAGNI 관점에서 모델 1보다 근거가 약함.

**참고 — 기존 DEFERRED 이슈와의 교훈**: `Scene`의 `m_entities`(열거용)와 `EntityManager`(소유)가 이중 자료구조로 나뉘어 있어 나중에 어긋날 위험이 있다고 이미 지적된 바 있다(확인 8과 무관하지만 참고할 선례). 위젯 관리 구조를 설계할 때도, "그리기용 목록"과 "소유권"을 별도 자료구조로 중복 관리하지 않도록(단일 소유권 원칙) 유의해야 한다.

### 확인 9 — 확인 7/8 최종 정리: `IUiBase`/`IUiElementRegistry`/`WOTUiManager` 3분할, 그리고 Image 재검토

확인 7의 "Option A" 초안(`IUiManager`에 `Button`/`Text` 등을 직접 추가)과 확인 8의 "모델 1 vs 모델 2"는 사용자와의 추가 논의로 다음과 같이 구체화·수정됐다.

- **`IUiManager`(기존, graphics)** — 변경 없음. ImGui 프레임 생명주기(`NewFrame`/`Render`/`Shutdown`/`HandleWin32Message`)만 책임. `ImGuiManagerDX9/11/12`가 계속 구현.
- **`IUiBase`(신규, graphics)** — 위젯 하나의 최소 계약(`Render()` 등).
- **`ButtonUI`/`ProgressUI`/`StringFieldUI`/`LabelUI`(신규, graphics, `IUiBase` 구현)** — 각자 `Render()`에서 대응하는 ImGui 함수를 직접 호출. `imgui.h`를 아는 파일이 기존 3개(`ImGuiManagerDX*`)에서 이 4개까지 늘어나지만 전부 `graphics` 안이라 "projects는 imgui.h를 모른다"는 원칙은 유지됨.
- **`IUiElementRegistry`(가칭, 신규, graphics)** — `Add(IUiBase*)`/`Remove(...)`/`RenderAll()`만 아는 순수 레지스트리 인터페이스. 위젯 종류를 모름.
- **`WOTUiManager : IUiElementRegistry`(projects)** — 구체 위젯(`StartButton` 등)의 생성·소멸·등록만 담당. DirectX도 ImGui도 모르는 순수 C++ 객체 라이프사이클 관리자.
- **`IRenderer`** — 기존 `m_uiManager`(ImGui 백엔드) 외에 `IUiElementRegistry&`도 보유. `RenderFrame` 내부에서 `m_uiManager->NewFrame() → registry.RenderAll() → m_uiManager->Render()` 순서로 호출.

이로써 확인 8의 미결정 사항(위젯 베이스 소속: graphics — 유지, 생성/관리 모델: 모델 1/2의 절충인 "DirectX-free 전용 레지스트리"로 확정)과 확인 7의 미결정 사항(인터페이스 분리 여부: `IUiManager` 그대로 두고 별도 인터페이스 신설로 확정)이 모두 정리됐다.

**부수적으로 발견된 재검토 필요 사항 — `Image`**

- 확인 4에서 "Image 자체는 `WOT-master`의 `UIImage`를 그대로 활용할 수 있을 것"이라 가정했는데, 이는 Option B(커스텀 quad/mesh 렌더링) 전제였다.
- Option A(ImGui 기반)로 확정되면서 `UIImage`(quad 메시 + 커스텀 셰이더 클래스) 자체는 재사용 대상이 아니게 됐다 — ImGui는 `ImGui::Image(textureId, size)`/`ImGui::ImageButton(textureId, size)`로 이미 텍스처 표시를 지원하기 때문이다.
- `WOT-master`에서 실제로 재사용 가능한 건 `UIImage` 클래스가 아니라 **텍스처 로딩/에셋 자체**(`Textures/UI/*.png` 등)일 가능성이 높다 — 이 부분은 아직 사용자와 확정하지 않았다.

### 확인 10 — 완료 기준 확정 + `TestScene` 폐기, `IntroScene`/`GameScene` 구조로 전환

- **완료 기준 확정**: `IntroScene`을 만들고 그 안에서 4종 위젯(Button/Progress/StringField/Label)을 띄울 수 있으면 이번 사이클 완료. 비주얼 디자인/스타일링은 범위 밖. 단위 테스트는 이 프로젝트의 기존 관례(Core Development Principle — "기능을 개발할 때마다 빌드·단위 테스트를 예외 없이 실행")대로 진행.
- **`TestScene`이라는 이름/구조 자체를 더 이상 쓰지 않는다** — `WOT-master`를 참고 대상에서 제외한 이상, `Scene/WOT/TestScene`을 흉내낸 이름을 가져올 이유가 없다는 판단. 대신 `IntroScene`(이번 사이클 대상), 이후 `GameScene`(다음 사이클 이후) 같은 목적 기반 이름으로 나눈다.
- 이에 따라 확인 1의 미해결 질문("Rendering 이식이 TestScene의 Outline/Trail을 포함하는가")은 **자동으로 범위 밖으로 정리된다** — TestScene 자체를 이번 사이클 이후로도 만들 계획이 없으므로, Outline/Trail이 붙어 있던 원본 맥락이 사라졌다. 필요해지면 그건 `GameScene`(실제 게임플레이) 쪽 별도 사이클의 몫이다.
- **연쇄적으로 걸리는 기존 DEFERRED 이슈**: 2026-08-11 사이클에서 "`GameManager`가 씬을 정확히 1개(`"Prototype"`)만 생성자에 하드코딩한다"가 보류(DEFERRED)됐었다(`docs/architecture/게임로직_구조_현황.md` 참고). 이번 사이클에서 `IntroScene`을 추가하면 씬이 최소 2개(`PrototypeScene` 유지 여부에 따라) 이상 필요해질 수 있어, 이 DEFERRED 이슈가 이번 사이클 범위에 들어올지 확인이 필요하다 — `GameManager`가 여전히 씬 1개만 등록 가능하면 `IntroScene`을 등록할 자리가 없다.

### 확인 11 — `Image`는 ImGui로 구현하되, 나중에 직접 구현으로 교체 가능한 경로를 남겨둔다

- 사용자 결정: 우선 `ImGui::Image`/`ImGui::ImageButton`으로 구현하고, 이게 어려운 케이스가 생기면 직접(커스텀 quad/셰이더) 구현으로 전환할 수 있는 경로를 열어둔다.
- 확인 9에서 이미 `ButtonUI`/`ProgressUI`/`StringFieldUI`/`LabelUI`를 `IUiBase` 뒤에 숨기는 설계를 확정했으므로, `Image`도 같은 방식(`ImageUI : IUiBase`, 내부적으로 지금은 `ImGui::Image` 호출)으로 만들면 이 요구가 추가 설계 없이 자연스럽게 충족된다 — `projects`/다른 위젯은 `ImageUI`의 내부 구현이 ImGui인지 커스텀 렌더링인지 몰라도 되기 때문에, 나중에 `ImageUI::Render()` 내부만 바꿔치기하면 된다.

## Trade-offs

- **"이식"이라는 표현을 그대로 쓸 경우** — 원본에 Button/Event/시작 화면 구현이 없으므로, 사실상 이식이 아니라 **신규 설계**가 된다. `UIImage`/`ProgressBar`라는 렌더링 기반은 재사용할 수 있지만, 입력 처리·이벤트 디스패치·버튼 상태(hover/pressed) 같은 로직은 이번에 처음 만들어야 한다.
  - 장점: 자유도가 높고, 기존 3계층 경계 규칙에 맞춰 처음부터 깔끔하게 설계할 수 있다.
  - 단점: "원본을 참고해서 그대로 옮긴다"는 이전 사이클들의 작업 방식과 다르게, 설계 결정(이벤트 시스템 구조, 버튼 상태 머신 등)을 이번 사이클에서 새로 내려야 한다 — 범위가 커질 위험.
- **범위를 `Objects/UI`(UIImage/ProgressBar) 이식으로 한정할 경우**
  - 장점: 원본이 존재하므로 이식 범위가 명확하고 작다. `graphics` 계층의 렌더러 위에 화면 오버레이를 그리는 기반만 먼저 갖춘다.
  - 단점: Button/Event/시작 화면은 이번 사이클에서 다루지 못하고 다음 사이클로 미뤄야 한다.
- **`TestScene`의 Outline/Trail(렌더링 이펙트)까지 포함할 경우**
  - 장점: "Rendering 이식"이라는 목표 문구를 문자 그대로 충족.
  - 단점: UI 작업과 성격이 다른 별개 작업(포스트 프로세싱 파이프라인, RenderTarget/DepthStencil 관리)이라 한 사이클에 같이 묶으면 체크리스트가 비대해지고 SRP상으로도 나눠 다루는 게 자연스럽다.

## Q&A Log

- Q: 자세한 작업을 말하기 전에, `agent_harness`에서 graphics 요청 관련 내용이 존재해?
  A: 없다. `team_task_delegation.md`라는 **워크플로우 정의**는 있지만, 실제로 오간 요청 기록(`docs/inbox`/`docs/outbox`, `request/*` 브랜치)은 WOT·`src/graphics` 어디에도 없다 — 지금까지 `[graphics]` 태그 요청이 한 번도 발생한 적 없는 상태.
- Q: 우리가 확인한 내용 중 (1) `imgui.h`는 특정 파일에서만 알고 외부는 모른다, (2) 전체적인 객체 생성/관리는 Manager를 쓴다 — 이 두 가지가 맞는지, 맞다면 Option A가 맞는 방향 아닌지?
  A: 둘 다 맞다. (1) `src` 전체에서 `imgui.h`/`imgui_impl_*.h`를 include하는 파일은 `graphics/ui/directx{9,11,12}/ImGuiManagerDX{9,11,12}.cpp` 3개뿐 — `ImGuiManagerDX11.h`의 기존 주석("`<imgui.h>`...를 아는 유일한 파일")과 정확히 일치. (2) `EntityManager`/`MeshManager`/`SaveLoadManager`(platform), `ConfigManager`/`GameManager`/`SceneManager`(projects), `IUiManager`+`ImGuiManagerDX*`(graphics) 전부 `*Manager` 네이밍으로, 이 프로젝트 전반의 확립된 관례. → Option A(ImGui 기반, `IUiManager` 확장)가 두 관례 모두와 자연스럽게 맞는다: `ImGuiManagerDX*`가 이미 `<imgui.h>`를 아는 유일한 파일이므로 위젯 메서드를 여기 추가해도 캡슐화가 깨지지 않고, `IUiManager`라는 이름 자체가 이미 Manager 관례를 따른다.
  참고(뉘앙스): 단, 기존 Manager들(`EntityManager`/`SceneManager`/`MeshManager` 등)은 "장기 생존 객체의 컬렉션을 보유·조회"하는 역할인 반면, `IUiManager`는 ImGui가 즉시모드(immediate-mode)라 Button/Label 같은 위젯의 "인스턴스를 보유"하지 않고 "프레임마다 그리는 호출을 감싸 제공"하는 역할이 된다 — 이름은 같은 관례를 따르지만 관리 대상의 성격은 다르다. Option A 선택을 막는 문제는 아니고, 설계 시 유념할 차이.
- Q: agent_harness를 먼저 최신으로 바꿔줘.
  A: (사용자가 곧이어 스스로 정정) 이미 `team_task_delegation.md`가 존재하니 업데이트가 필요 없다 — 실제로 현재 `agent_harness` 체크아웃(`5c6eef7`)이 이 워크플로우를 도입한 바로 그 커밋이라 최신 상태 맞음. 사용자의 실제 의도는 버전 갱신이 아니라 **team_task_delegation 워크플로우를 이번 사이클에서 실제로 사용해보는 것**.
- Q: `IUiManager`는 기본적으로 `IUiBase`만 알고 그것을 관리하는 기본적인 형태만 가지면 되지 않아? `IRenderer`는 `IUiManager`를 소유할 권한만 가지고 실질적으로는 모르고. `projects`에서 `DirectX11Renderer`를 선택하고, 그 안에 들어갈 `IUiManager`를 상속받는 `WOTUiManager`를 만들어 넣으면, 전체 생명주기의 공통 사항만 graphics가 조정하고 자세한 DirectX 버전과 UI 생성/소멸 함수는 projects에서 개발 가능하지 않을까?
  A: 방향은 맞지만 이름이 겹친다 — 기존 `IUiManager`는 이미 "ImGui 프레임 생명주기" 책임을 갖고 있어서, 여기에 위젯 레지스트리 책임까지 얹으면 `WOTUiManager`가 `NewFrame`/`HandleWin32Message`까지 구현해야 해 결국 DirectX 쪽으로 끌려간다. 그래서 기존 `IUiManager`는 그대로 두고, 위젯 레지스트리 전용으로 `IUiElementRegistry`(가칭)를 새로 만들어 `WOTUiManager`가 그걸 구현하는 쪽으로 정리했다(확인 9).
- Q: (이어서) "자세한 DirectX 버전과 UI 생성/소멸 함수"라고 헷갈리게 말한 건, `projects`가 config에 따라 DirectX 버전을 선택한다는 뜻으로 한 말이었고, "UI 생성/소멸"은 위젯 C++ 객체(`new`/`delete`) 얘기였음 — DirectX API를 직접 다룬다는 뜻은 아니었음. 맞음?
  A: 맞다. DirectX 버전 선택은 이미 `RendererFactory`/`LaunchConfigStore`가 하고 있어 새로 설계할 게 없고, "위젯 생성/소멸"이 순수 C++ 객체 라이프사이클이라면 `WOTUiManager`가 DirectX/ImGui를 전혀 몰라도 된다 — 확인 9의 설계와 정확히 일치.
- Q: `IntroScene` 추가로 `GameManager`의 씬 1개 하드코딩 DEFERRED 이슈가 걸리는데, (a) 이번 사이클에서 다중 씬 지원까지 해결 vs (b) `IntroScene`을 임시 유일 등록 씬으로 삼고(`PrototypeScene` 등록 제거/교체) 다중 씬 지원은 계속 미룸 — 어느 쪽?
  A: (b). `GameManager`의 다중 씬 등록 지원(DEFERRED 이슈)은 이번 사이클 범위에 포함하지 않는다 — 계속 보류. `GameManager`는 `IntroScene`만 등록하도록 바꾼다(기존 `"Prototype"` 등록을 대체).
