# Strategy: 게임 기본 기능 채우기 (IntroScene 4종 위젯)

## 적용 방식

브레인스토밍에서 확정된 설계(Option A/ImGui 기반, `IUiBase`/`IUiElementRegistry`/`WOTUiManager` 3분할, `IntroScene` 신설)를 코드에 적용한다.

- `graphics`(submodule, 별도 저장소) 쪽 변경은 `IUiBase`/`ButtonUI`/`ProgressUI`/`StringFieldUI`/`LabelUI`/`ImageUI`/`IUiElementRegistry`/`IRenderer` 확장/DirectX9·11·12Renderer 배선 — 전부 `graphics` 저장소가 소유해야 할 공개 추상화라 `team_task_delegation.md`로 요청한다.
- `projects`(이 저장소) 쪽 변경은 `WOTUiManager`, `IntroScene`, 구체 위젯, `GameManager`/`main.cpp` 배선 — `[self]`로 이 저장소 안에서 직접 구현한다.
- `[graphics]` 항목은 `graphics`가 응답(공개 인터페이스 확정)하기 전까지 `[self]` 항목 구현을 시작할 수 없다 — 의존 순서상 `[graphics]`가 먼저 완료돼야 한다.

## 완료·검증 기준

- `IntroScene`에서 Button / Progress / StringField / Label / Image 5종 위젯이 화면에 표시됨을 확인 (비주얼 디자인/스타일링 불필요).
- 신규 클래스(`WOTUiManager`, `IntroScene`, 구체 위젯들)에 대한 단위 테스트 작성 및 통과.
- `platform_lib`/`graphics_lib`/`app_lib`/`tests`/`main` 전체 빌드 통과.
- 기존 테스트(`SceneManagerTest`/`GameManagerTest`/`InstanceUpdateWorkerTest`) 회귀 없음. `PrototypeScene`/`PrototypeSceneTest`는 삭제 대상이라 이번 사이클에서 없어지는 게 정상.

## 설계 변경 — 엔진/렌더 스레드 경계 문제 (2026-08-19, graphics 응답 반영 후 발견)

`graphics` 응답을 코드 레벨로 검토하는 과정에서, 원래 계획(`WOTUiManager`를 `IntroScene`이 소유, `IntroScene`은 `GameManager`를 통해 engine 스레드에서 동작)이 스레드 경계를 위반한다는 게 드러났다.

- `SetUiElementRegistry`로 등록된 registry는 `DirectX11Renderer::RenderFrame()`(렌더/메인 스레드) 내부 `NewFrame()` 직후 `RenderAll()`로 호출된다.
- `IntroScene`은 `GameManager`(→ `InstanceUpdateWorker::Run()`의 지역 변수)를 통해 **engine 스레드**에서 산다.
- 위젯/registry가 engine 스레드에 있는데 렌더 스레드가 동시에 `RenderAll()`로 접근하면 데이터 레이스 — 3D 데이터(`InstanceSnapshot`)처럼 `DoubleBufferPublisher`로 안전하게 넘기는 장치가 UI 위젯엔 없다(ImGui 자체도 스레드 세이프하지 않음).

**결정**: `WOTUiManager`/`IntroScene::Start()`의 위젯 등록 계획을 취소한다. 대신 위젯 5종과 `UiElementRegistry`를 **`main.cpp`(렌더 스레드)가 직접 소유**한다 — `IntroScene`/`GameManager`/`SceneManager`(engine 스레드) 파이프라인과는 완전히 분리. `IntroScene`은 지금 만든 빈 뼈대 그대로 유지(향후 실제 엔진 스레드 로직이 필요해지면 그때 다시 쓰임).

## OpenGL 관련 참고

`IRenderer`에 `SetUiElementRegistry(...)`를 추가하면 `OpenGLRenderer`도 `IRenderer`를 구현하는 이상 이 메서드 시그니처는 가져야 한다(순수 가상 함수 상속). 이번 사이클에선 `OpenGLRenderer`의 구현을 **no-op**(등록만 받고 실제로 그리지 않음)으로 남겨 컴파일만 통과시키고, 실제 배선은 다음에 OpenGL이 필요해질 때 처리한다 — `[graphics]` 요청 문서에 이 조건을 명시한다.

위 체크리스트 확정 후, `[graphics]` 항목 전체를 하나의 요청으로 묶어 `team_task_delegation.md` Step 1~4를 진행한다.

2. `docs/inbox/{YYYYMMDD_HHMM}_wot_request.md` 작성 — Requester/Purpose/Needed interface(위 `[graphics]` 체크리스트 초안)/Related strategy doc(이 문서)/Priority.
