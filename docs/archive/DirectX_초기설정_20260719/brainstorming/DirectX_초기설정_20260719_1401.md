# Brainstorming: DirectX 초기 설정 및 빈 화면 출력

## Details

### 1. 버전 선택 방식 — `RendererBackend` enum 확장 (확정, DirectX 9 추가 반영)

현재 `RendererBackend { DirectX, OpenGL }` + `RendererBackendParser`("directx"/"opengl" 문자열 파싱) + `ConfigManager`/`LaunchConfigParser`가 이미 "기본값 → JSON → argv" override 체인을 완성해둔 상태.

- **확정: `RendererBackend { DirectX9, DirectX11, DirectX12, OpenGL }`**, 문자열 토큰 `"directx9"`/`"directx11"`/`"directx12"`/`"opengl"`. 기존 선택 인프라(파서/Config/argv override/테스트 구조) 전부를 그대로 재사용 — 값 하나만 더 늘어남.
- 기존 `"directx"` 문자열 토큰과 `RendererBackend::DirectX` 값은 완전히 제거하고 대체 — 하위 호환 shim 없음(개인 프로젝트, 실사용자 없음).
- `RendererBackendParserTest`/`LaunchConfigParserTest`/`ConfigManagerTest`의 관련 케이스를 이번 사이클에서 갱신.
- 참고: CLAUDE.md 프로젝트 목표는 "DirectX 11 → 상위 버전 마이그레이션"이라 DX9은 방향상 더 오래된 버전이지만, 사용자가 밝힌 이유(구형 하드웨어 호환성 대응 + 포트폴리오 상 폭넓은 DirectX 세대 경험 증명)에 따라 셋 다 구현하기로 확정.

### 2. 윈도우 생성 — 신규 `Win32Window` wrapper (확정, `src/platform/`)

코드베이스에 Win32 윈도우 생성 코드가 전혀 없음. "빈 화면을 띄운다"는 요구를 만족하려면 `CreateWindowEx`/`RegisterClassEx`/메시지 펌프가 필요함.

- DirectX뿐 아니라 (향후) OpenGL도 렌더링 대상 윈도우(HWND/HDC)가 필요하므로, 윈도우 생성을 렌더러 내부에 두지 않음 — `Win32Window`를 렌더러와 완전히 분리된 독립 컴포넌트로 만들고, `main()`이 하나 생성해서 선택된 렌더러에게 넘겨주는 구조.
- **확정: 디렉토리 이름 `src/platform/`.**
- `IWindow` 인터페이스는 만들지 않음 — Windows 전용 프로젝트이고 두 번째 윈도우 구현체 계획이 없어 과설계.

### 3. `IRenderer` 인터페이스 확장 (확정, 최소 구현)

```cpp
class IRenderer
{
public:
    virtual ~IRenderer() = default;
    virtual bool Initialize(HWND windowHandle, int width, int height) = 0;
    virtual void RenderFrame() = 0;   // Clear + Present
    virtual void OnResize(int width, int height) = 0;  // 창 크기 변경 시 스왑체인 버퍼 재생성
    virtual void Shutdown() = 0;
};
```

- `HWND`는 서드파티 라이브러리가 아니라 Windows 플랫폼 자체 타입이라 wrapper 규칙 대상이 아님 — `IRenderer.h`가 `<windows.h>`를 아는 건 문제 없음. `ID3D11Device`/`ID3D12Device` 같은 DirectX 전용 타입만 `IRenderer`에 노출하지 않으면 됨.
- `main()`의 루프는 최소화: `while (window.PumpMessages()) { renderer->RenderFrame(); }` — 별도 `GameLoop`/`Application` 클래스는 이번 사이클에서 만들지 않음.
- 사용자 지시대로 "최소 구현"만 진행 — 위 4개 메서드 이상으로 이번 사이클에 인터페이스를 키우지 않음.

### 4. DirectX 11 / DirectX 12 wrapper 격리 수준 (확정)

**확정 기준(사용자 지정): `<d3d11.h>`를 아는 파일과 `<d3d12.h>`를 아는 파일을 완전히 분리한다.** 이 조건만 만족하면 나머지는 단순안으로 진행.

- `DirectX9Renderer.h/.cpp`만 `<d3d9.h>`를 include. `DirectX11Renderer.h/.cpp`만 `<d3d11.h>`/`<dxgi.h>`/`<wrl/client.h>`를 include. `DirectX12Renderer.h/.cpp`만 `<d3d12.h>`를 include. 세 파일이 서로의 헤더를 포함하는 일은 없음.
- 각 렌더러는 해당 버전의 디바이스/컨텍스트 관련 멤버(DX9는 `IDirect3DDevice9*` 계열, DX11/DX12는 `Microsoft::WRL::ComPtr<...>`)를 헤더에 직접 보유(pImpl 없음) — `RendererFactory.cpp`(구체 타입 생성을 위해 세 헤더를 모두 include)의 번역 단위에는 D3D 헤더가 전이적으로 들어가지만, 그 파일이 D3D API를 직접 호출하는 코드를 작성하지는 않음. `IRenderer` 경계로 "다른 모듈이 외부 라이브러리를 직접 참조하지 않는다"는 원칙의 실질적 목적은 달성됨.
- DX9은 DXGI를 쓰지 않는 세대(스왑체인 개념이 `D3DPRESENT_PARAMETERS`를 통한 암시적 스왑체인)라 DX11/DX12와 내부 구조가 상당히 다름 — 다만 외부에 노출되는 `IRenderer` 인터페이스는 동일하므로 호출부(`RendererFactory`/`main()`)에는 영향 없음.

### 5. 확장성 / DirectX 사용성 — wrapper 내부 설계 원칙 (사용자 우려사항 반영)

이번 사이클 목표는 "빈 화면"까지지만, wrapper 자체가 다음 사이클(실제 오브젝트 렌더링: 셰이더/버텍스 버퍼/파이프라인 스테이트 등)에서 다시 만들어야 하는 막다른 구조면 안 됨. 아래 두 원칙으로 대응.

- **디바이스 상태는 영속 멤버로 보유.** `DirectX11Renderer`/`DirectX12Renderer`는 device/context/swapchain/RTV(DX12는 커맨드 큐/할당자/리스트/펜스까지)를 매 프레임 지역 변수로 새로 만들지 않고 클래스 멤버(ComPtr)로 들고 있음 — 다음 사이클에서 `Draw(...)`/`CreateBuffer(...)` 같은 메서드가 추가돼도 이 상태를 그대로 재사용 가능.
- **`IRenderer`는 추가로 확장, 재작성 아님.** `RendererFactory`/`Win32Window`/`main()`은 `IRenderer` 인터페이스에만 의존하므로, 나중에 순가상함수를 몇 개 더 추가해도(예: `SubmitDrawCall`) 기존 호출부는 변경할 필요 없음 — 이미 Open/Closed 원칙이 구조적으로 보장됨.
- **wrapper 내부는 DirectX를 있는 그대로 다룬다.** `ComPtr` + 직접 D3D API 호출 방식을 유지하고, wrapper 안에 또 다른 추상화 계층(예: 자체 커맨드 큐 시뮬레이션 등)을 만들지 않음 — 나중에 실제 렌더링 기능을 추가할 때 코드가 일반적인 최신 DirectX 코드처럼 읽혀야, 확장할 때 wrapper 자체와 싸우지 않음.
- 지금 이 시점에 draw call/리소스 바인딩 API를 미리 설계하지는 않음(YAGNI) — 위 두 원칙은 "나중에 추가하기 쉬운 모양"을 만드는 것이지, 미래 기능을 미리 구현하는 게 아님.

### 6. DirectX 12의 스코프 — "빈 화면"까지만

DX12는 DX11 대비 필요한 객체가 훨씬 많음(디바이스, 커맨드 큐, 커맨드 할당자/리스트, 디스크립터 힙, 펜스+동기화 등). 이번 사이클 목표는 "빈 화면 + Clear 색상만 Present"까지로 한정 — 파이프라인 스테이트/셰이더/버텍스 버퍼 등은 다음 사이클(실제 오브젝트 렌더링) 범위.

### 7. 테스트 전략 — GPU 없이 디바이스 생성 검증 (확정, DX9 포함)

DXGI의 **WARP(소프트웨어 래스터라이저) 어댑터**를 쓰면 GPU 없이도 디바이스 생성을 실제로 검증할 수 있음 — DX11은 `D3D_DRIVER_TYPE_WARP`, DX12는 `IDXGIFactory::EnumWarpAdapter`. DX9은 DXGI가 없는 세대라 WARP라는 이름은 없지만, 동등한 목적의 `D3DDEVTYPE_NULLREF`(널 레퍼런스 디바이스 — 실제 렌더링 없이 디바이스 생성 성공 여부만 확인 가능, GPU 불필요)로 대응.

- `DirectX9Renderer`/`DirectX11Renderer`/`DirectX12Renderer`의 "디바이스 생성 성공" 여부는 각각 NULLREF/WARP로 실제 자동 테스트 작성(CI에서도 동작). "윈도우가 실제로 보이고 화면이 비어있다"는 스크린샷 비교 없이는 자동 검증이 어려우므로 `/verify`로 수동 실행 확인.

### 8. 창 크기/제목 — Config화 (확정)

- **창 크기**: 기존 `AppConfig.width`/`height`(기본 1280x720)를 처음으로 실제 윈도우 생성에 배선.
- **창 제목**: 상수 하나로만 박아두지 않고 **Config로 노출** — `AppConfig`에 `windowTitle` 필드 추가, `ConfigFields::kTitle` 상수와 기본값 상수(`"World of Tank Imitation"`)를 함께 정의. 기존 `DataRecordAccess::GetStringOr`를 그대로 재사용해 추가 배관 없이 구현 가능.

### 9. 전체화면 / 창 모드 전환 + 창 크기 조절(리사이즈) (신규 요청 반영)

- **시작 모드**: 기존 `AppConfig.fullscreen`(bool)을 그대로 사용 — Config로 설정 가능, 기본값 `false`(창 모드)로 이미 맞춰져 있음. 이번 사이클은 "시작 시 모드 결정"까지만 다룸 — 실행 중 단축키 등으로 토글하는 기능은 범위 밖(필요하면 별도 논의).
- **전체화면 구현 방식** — 두 가지 선택지:
  - **(제안) 테두리 없는 전체화면(borderless fullscreen)**: 창을 모니터 해상도로 리사이즈하고 테두리(`WS_POPUP`)만 제거. DXGI exclusive fullscreen 전환/디바이스 손실 처리가 필요 없어 이번 스코프에 안전하고 단순함.
  - (대안) DXGI exclusive fullscreen(`IDXGISwapChain::SetFullscreenState`): 성능상 이점이 있지만 alt-tab/디바이스 손실 처리 등 복잡도가 늘어남 — "빈 화면" 스코프에는 과함.
  - → borderless 방식으로 진행 제안. 다른 방식을 원하면 알려줘.
- **창 크기 조절(리사이즈)**: `Win32Window`를 `WS_OVERLAPPEDWINDOW`(테두리 드래그로 크기 조절 가능) 스타일로 생성. `WM_SIZE` 수신 시 등록된 콜백(`std::function<void(int,int)>`)을 호출하고, `main()`에서 `window.SetResizeCallback([&](int w,int h){ renderer->OnResize(w,h); })`로 연결 — `Win32Window`는 `IRenderer`를 몰라도 됨(SRP 유지).
  - 최소화(minimize) 시 `WM_SIZE`가 크기 0으로 들어오는 경우가 있어, `OnResize` 구현에서 0 크기는 무시하는 가드가 필요 — 전략 문서에서 체크리스트 항목으로 명시.

### 10. 근시안적 설계 우려 검토 (사용자 제기, 확인 필요)

사용자가 "약간 근시안적으로 개발하는 느낌이 있다"는 우려를 제기함 — Details 5번(확장성/DirectX 사용성 원칙)만으로 충분한지 재점검. 후보를 세 가지로 정리해 사용자에게 재질문한 상태.

- **(후보 1) DX12의 멀티스레딩 여지 미반영.** CLAUDE.md 리팩토링 범위에 "현재 싱글스레드 설계에 멀티스레딩 적용"이 명시돼 있는데, 지금 계획은 DX12를 "DX11보다 객체가 많은 버전" 정도로만 다루고 있음. DX12를 채택하는 핵심 이유 중 하나가 커맨드 리스트를 여러 스레드에서 병렬 기록할 수 있다는 점인데, 지금 구조대로면 커맨드 할당자/리스트를 1개만 만들어 DX11과 사실상 동일한 싱글스레드 패턴이 됨. 제안: 지금 당장 멀티스레드 렌더링을 구현하지는 않되, 커맨드 할당자/리스트 개수가 "1개로 고정"되지 않는 구조(예: 개수를 상수로 분리하거나 커맨드 리스트를 목록으로 다루는 형태)로 시작해 나중에 실제로 붙일 때 재설계가 필요 없게 함.
- **(후보 2) 리소스 관리(버텍스 버퍼/텍스처/셰이더) 여지 미반영.** 지금은 아예 다루지 않는데, "빈 화면" 다음 단계에서 바로 필요해질 영역 — 인터페이스 이름/폴더 구조 정도는 지금 결정에 영향받지 않도록 여지를 남겨야 함.
- **(후보 3) `AppConfig`의 렌더러 옵션 확장 여지 미반영.** 지금은 렌더러 관련 설정(해상도/전체화면/버전)이 `AppConfig`에 평면적으로 들어있는데, 향후 그래픽 옵션(안티앨리어싱, VSync 등)이 늘어나면 렌더러 전용 하위 구조체로 분리할 시점이 올 수 있음 — 지금 당장 할 필요는 없지만 인지해둘 필요.
- 사용자에게 위 세 후보 중 어느 지점이 우려였는지, 혹은 완전히 다른 지점(예: 아키텍처 전체 그림, 테스트 전략)인지 재질문함.
- **확인 결과: 특정 후보를 콕 집은 게 아니라, "현재 목표 기준으로만 만드는 데 중점을 두는 것 같다"는 일반적인 확장성 당부였음.** 세 후보를 개별로 확정 짓기보다, 아래를 이번 사이클의 확장성 가이드라인으로 채택.
  - (후보 1 반영) DX12 커맨드 할당자/리스트 개수를 하드코딩 1개로 박지 않고 상수/컨테이너로 분리 — 실제 멀티스레드 기록은 구현하지 않되 구조는 열어둠.
  - (후보 2 반영) 리소스 관리 관련 네이밍/폴더 구조는 이번 사이클에서 결정하지 않고, 다음 사이클에서 자연스럽게 얹을 수 있는 형태(디바이스 상태를 멤버로 보유하는 현재 원칙)만 유지.
  - (후보 3 반영) `AppConfig`를 지금 당장 분리하지 않되, 필드가 계속 늘어나면 렌더러 전용 하위 구조체로 쪼갤 수 있다는 점을 인지하고 진행.

## Trade-offs

| 항목 | 선택 | 장점 | 단점/리스크 |
|---|---|---|---|
| 버전 선택 축 | `RendererBackend` enum 확장 | 기존 인프라 100% 재사용, 코드량 최소 | "API 종류"와 "버전"이 개념적으로 한 축에 섞임 |
| 윈도우 생성 위치 | 렌더러와 분리된 `Win32Window` | 향후 OpenGL도 재사용 가능, 렌더러는 그리기 로직에만 집중(SRP) | 새 디렉토리(`platform/`) 하나 추가 |
| DirectX 헤더 격리 | d3d9.h/d3d11.h/d3d12.h 파일 완전 분리 + 단순안(직접 include) | 보일러플레이트 최소, 사용자 지정 조건 충족 | pImpl 대비 격리 강도는 낮음(다만 실질 목적은 달성) |
| DX9 추가 포함 | DX9/DX11/DX12 셋 다 구현 | 구형 하드웨어 호환성, 포트폴리오상 폭넓은 세대 경험 증명 | CLAUDE.md의 "DX11→상위 버전" 마이그레이션 방향과는 다소 결이 다름(사용자 명시적 확인 사항) |
| wrapper 내부 설계 | ComPtr 멤버 영속 보유 + 추가 추상화 없음 | 다음 사이클 확장이 "추가"로 가능, DirectX 코드가 자연스럽게 읽힘 | 지금 당장은 draw call API가 없어 "빈 화면"까지만 가능(의도된 범위) |
| 전체화면 방식 | borderless fullscreen | exclusive fullscreen 대비 구현/예외 처리 단순 | 진짜 exclusive fullscreen 대비 미세한 성능 차이 가능(이 스코프에선 무의미) |
| 창 리사이즈 | `WS_OVERLAPPEDWINDOW` + resize 콜백 | 테두리 드래그로 크기 조절 가능, Window↔Renderer 결합 없음(콜백으로 분리) | 최소화 시 0 크기 처리 등 예외 케이스 주의 필요 |

## Q&A Log

- Q: "DirectX 버전 선택"이 정확히 무슨 의미인지?
  A: DirectX 11과 DirectX 12를 둘 다 실제로 구현해두고, 외부 Config(`config.json`)에서 읽은 값에 따라 런타임에 실행할 버전을 결정하는 것. 이유는 (1) 사용자 GPU/드라이버 호환성 대응, (2) 포트폴리오 관점에서 DX12 역량도 보여줄 필요.
- Q: DirectX도 외부 라이브러리처럼 wrapper로 감싸야 하는지?
  A: 그렇다 — 외부(호출부)는 버전 선택값과 안정된 인터페이스만 알고, DX11/DX12 세부 API 호출은 각 wrapper 클래스 내부로 격리한다.
- Q: 7개 열린 질문에 대한 답변?
  A: 1(문자열 완전 대체) 승인. 2(격리 수준)는 "d3d11.h만 아는 파일, d3d12.h만 아는 파일로 분리"만 만족하면 단순안 승인. 3(`src/platform/`) 승인. 4(`IRenderer` 확장)는 최소 구현으로 진행. 5(WARP 테스트) 승인. 6(창 크기/타이틀)은 승인하되 타이틀은 상수화 또는 Config화 필요. 7(전체화면)은 창/전체화면 둘 다 설정 가능, 기본은 창 모드로. 추가로 창 테두리 드래그로 크기 조절하는 기능도 요청.
- Q: 확장성/DirectX 사용성도 고려해서 wrapper를 만들어야 하는데 알고 있는지?
  A: 맞다 — Details 5번에 원칙을 명시함(디바이스 상태를 영속 멤버로 보유해 다음 사이클에서 재사용 가능하게, `IRenderer`는 재작성이 아니라 추가로만 확장, wrapper 내부는 DirectX를 있는 그대로 다뤄 나중에 실제 렌더링 기능을 붙이기 쉽게 유지).
- Q: (사용자 발언) "약간 근시안적으로 개발하는 느낌이 살짝 있다."
  A: Details 10번에 세 가지 후보(DX12 멀티스레딩 여지, 리소스 관리 여지, `AppConfig` 렌더러 옵션 확장 여지)를 정리해 제시하고, 어느 지점이 우려였는지 사용자에게 재질문함.
- Q: (재질문에 대한 답) 세 후보 중 어느 지점이 우려였는지?
  A: 특정 후보를 콕 집은 게 아니라, "현재 목표 기준으로만 만드는 데 중점을 두는 것 같다"는 일반적인 확장성 당부였음 — "확장성 고려만 해달라"는 취지. 세 후보 모두 이번 사이클의 확장성 가이드라인으로 채택(Details 10번 참고).
- Q: 브레인스토밍 승인하고 전략으로 넘어가되, DirectX 9까지 확장해서 구현해달라는 요청.
  A: 반영 — `RendererBackend`에 `DirectX9` 추가, `DirectX9Renderer`(`<d3d9.h>`만 아는 파일)를 세 번째 wrapper로 신설. DX9은 DXGI 없는 세대라 내부 구조가 DX11/DX12와 다르지만 `IRenderer` 경계는 동일하게 유지. 테스트는 WARP 대신 `D3DDEVTYPE_NULLREF`로 대응. CLAUDE.md의 "DX11→상위 버전" 마이그레이션 방향과는 다소 결이 다르다는 점만 참고로 명시(Trade-offs 표 참고), 사용자가 명시적으로 요청했으므로 그대로 진행.

## Summary & Open Questions (사용자 결정 필요)

**현재까지 확정된 내용**

- `RendererBackend { DirectX9, DirectX11, DirectX12, OpenGL }`로 확장, `"directx"` 토큰은 완전히 제거하고 `"directx9"`/`"directx11"`/`"directx12"`로 대체.
- `Win32Window`(신규, `src/platform/`)를 렌더러와 분리해 생성 — `IWindow` 인터페이스는 만들지 않음.
- `IRenderer`에 `Initialize(HWND,width,height)`/`RenderFrame()`/`OnResize(width,height)`/`Shutdown()` 4개 메서드만 최소로 확장.
- DirectX 헤더 격리: `<d3d9.h>`/`<d3d11.h>`/`<d3d12.h>`를 아는 파일을 완전히 분리(`DirectX9Renderer`/`DirectX11Renderer`/`DirectX12Renderer`) + 나머지는 단순안(직접 include, 디바이스 멤버 직접 보유).
- wrapper 내부 설계 원칙: 디바이스 상태는 영속 멤버로, `IRenderer`는 추가로만 확장, DirectX 코드는 있는 그대로(추가 추상화 없이) 작성 — 다음 사이클(실제 렌더링) 확장을 대비.
- 확장성 가이드라인(Details 10번): DX12 커맨드 할당자/리스트 개수를 상수/컨테이너로 분리(멀티스레드 기록은 구현하지 않되 구조는 열어둠), 리소스 관리는 이번에 설계하지 않되 디바이스 상태를 멤버로 보유하는 원칙만 유지, `AppConfig`는 지금 분리하지 않되 향후 렌더러 전용 하위 구조체 분리 가능성 인지.
- DX9/DX12 스코프는 "빈 화면(Clear+Present)"까지로 한정.
- 디바이스 생성 자동 테스트: DX11/DX12는 WARP 어댑터, DX9은 `D3DDEVTYPE_NULLREF` + 수동 시각 확인(`/verify`) 병행.
- 창 크기(`AppConfig.width/height`, 기본 1280x720)와 시작 모드(`AppConfig.fullscreen`, 기본 창 모드)는 기존 필드를 그대로 배선.
- 창 제목은 `AppConfig.windowTitle` 필드로 Config화, 기본값은 이름 있는 상수(`"World of Tank Imitation"`).
- 전체화면은 borderless 방식으로 구현, 창 리사이즈는 `WS_OVERLAPPEDWINDOW` + resize 콜백으로 `Win32Window`↔`IRenderer::OnResize` 연결.
