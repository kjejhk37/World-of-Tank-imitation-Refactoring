# Strategy: Config 및 Save/Load 시스템 초안

## 적용 방식 요약

브레인스토밍에서 확정된 아키텍처를 아래 순서로 코드에 반영한다 — 하위 계층(저장소 추상화) → 상위 계층(Config, Save/Load) → 진입점 연결 → 검증 순.

- `IDataStore` 인터페이스를 먼저 만들고, `JsonDataStore`로 실제 구현한다.
- `ConfigManager`와 `SaveLoadManager`는 `IDataStore`에만 의존하도록 만들어, 이후 `SqliteDataStore`로 교체해도 두 클래스는 수정이 필요 없게 한다 (의존성 역전).
- `nlohmann::json`을 직접 참조하는 코드는 `JsonDataStore` 내부로 한정한다 (CLAUDE.md 외부 라이브러리 wrapper 원칙).
- 비동기 저장은 `SaveLoadManager`에 시그니처(예: `SaveAsync`)만 선언해 확장 지점을 열어두고, 이번 사이클에서는 동기 구현으로 둔다 — 실제 스레드화는 별도 Task.
- `SqliteDataStore`는 클래스 골격(헤더 + 생성자 + `IDataStore` 메서드 시그니처)만 작성하고, 메서드 본문은 미구현 상태(예: 컴파일은 되지만 호출 시 명시적으로 "미구현" 처리)로 남긴다. 실제 SQLite 라이브러리는 이번 사이클에 링크하지 않는다.

## 최종 승인 및 검증 기준

- CMake로 `main`, `tests` 타겟이 모두 정상 컴파일·링크된다.
- `tests` 타겟의 모든 케이스(Config override 우선순위, `JsonDataStore` 왕복, Save/Load 왕복)가 통과한다.
- Config 파일이 없는 상태에서 `main.exe`를 실행해도 하드코딩 기본값으로 크래시 없이 기동한다.
- `nlohmann::json`에 대한 직접 참조가 `JsonDataStore` 외부 어디에도 없다 (grep으로 확인).
- `ConfigManager` / `SaveLoadManager` / `JsonDataStore` / `SqliteDataStore`가 각각 단일 책임만 가지는지 코드 리뷰로 확인한다 (SRP).
- 신규 작성된 모든 함수/클래스에 CLAUDE.md 주석 규칙(Author / 설명 / Input / Output / Notes / Date)이 반영되어 있다.
