# Code Review: Config 및 Save/Load 시스템 초안

## Stage 1 — Quality Inspection

### 즉시 해결 가능 (이번 Task 범위 내) — 전부 해결 완료

- `[RESOLVED]` `[MEDIUM]` **[사용자 지적 사항]** 이름 없는 문자열 리터럴이 여러 파일에서 직접 비교/조회에 쓰이고 있다.
  - `RendererBackendParser.cpp`: `"directx"`, `"opengl"`
  - `ConfigManager.cpp`: `"width"`, `"height"`, `"fullscreen"`, `"volume"`, `"renderer"`, `"true"`, `"false"`
  - `main.cpp`: `"config.json"`
  - 같은 Task 안에서 `SaveLoadManager.cpp`(`kSaveVersionField`)와 `PlayerProgress.cpp`(`kCurrencyField`, `kUnlockedTankIdsField`)는 이미 named constant로 뽑아뒀다.
  - 이 세 파일만 그 패턴을 따르지 않아 스타일이 일관되지 않는다.
  - **[해결 방안]** (사용자와의 논의를 거쳐 확정된 최종안 — 상수 개수 기준 문턱 적용)
    - 상수가 3개 이상이고 늘어날 여지가 있는 `ConfigManager`의 필드명 5개는 같은 디렉토리의 별도 헤더 `src/config/ConfigFields.h`로 분리한다.
    - 상수가 1~2개뿐인 `RendererBackendParser.cpp`(`kDirectXName`, `kOpenGLName`)와 `main.cpp`(`kDefaultConfigFilePath`)는 로컬에 유지하되, "500줄 또는 상수 5개 초과 시 분리"라는 기준을 파일 상단 주석으로 남겨 향후 판단 근거를 명시한다.
    - 리뷰 도중 `ConfigManager::ParseIntOr`와 `PlayerProgress::FromRecord`(아래 두 번째 항목)의 파싱 로직이 거의 동일하게 중복된다는 점이 추가로 발견됨 — 상속이 아니라 `src/serialization/DataRecordAccess.h/.cpp`(네임스페이스 자유 함수)로 공용화해 `ConfigManager`/`PlayerProgress` 양쪽이 조합(사용)하도록 리팩터링한다.
  - **[처리 결과]**
    - `src/serialization/DataRecordAccess.h/.cpp` 신설 (`GetIntOr`/`GetBoolOr`/`GetFloatOr`/`GetStringOr`), `DataRecordAccessTest` 8건 추가.
    - `src/config/ConfigFields.h` 신설, `ConfigManager.cpp`가 이를 통해 필드명 참조 (로컬 파싱 헬퍼 3개 제거, `DataRecordAccess` 호출로 대체).
    - `PlayerProgress::FromRecord`도 `DataRecordAccess::GetIntOr` 사용으로 교체.
    - `RendererBackendParser.cpp`/`main.cpp`에 named constant 추가 + 분리 기준 주석 추가.

- `[RESOLVED]` `[MEDIUM]` `PlayerProgress::FromRecord`(`src/persistence/PlayerProgress.cpp`)가 `currency` 필드를 `std::stoi(it->second)`로 예외 처리 없이 파싱한다.
  - 손상되거나 사람이 잘못 편집한 세이브 파일이 들어오면 `std::invalid_argument`가 그대로 전파된다.
  - 이 예외는 `SaveLoadManager::Load` 호출부까지 그대로 전파되어 크래시로 이어진다.
  - 같은 사이클의 `ConfigManager::ParseIntOr`(`std::from_chars` 실패 시 기본값 폴백), `JsonDataStore::Load`(파싱 실패 시 `false` 반환)와 달리 이 클래스만 실패에 안전하지 않다.
  - **[해결 방안]**
    - `ConfigManager.cpp`의 `ParseIntOr`와 동일하게 `std::from_chars`로 교체한다.
    - 파싱 실패 시 기존 `currency` 값(또는 0)으로 폴백시킨다.
    - `std::from_chars`는 예외를 던지지 않으므로 별도 `try/catch` 없이도 안전해지고, 프로젝트 전체 파싱 방식과 일관된다.
  - **[처리 결과]** 위 `DataRecordAccess::GetIntOr` 공용화에 흡수되어 함께 해결됨 — `PlayerProgressTest`로 검증 완료.

- `[RESOLVED]` `[LOW]` 테스트 커버리지 공백이 있다.
  - `ConfigManager`에 숫자가 아닌 값(`"width": "abc"`)이 들어왔을 때 기본값으로 폴백하는 경로를 검증하는 테스트가 없다.
  - `PlayerProgress::FromRecord`에 손상된 `currency` 값이 들어왔을 때의 동작(위 MEDIUM 항목과 직결)을 검증하는 테스트가 없다.
  - **[해결 방안]**
    - `ConfigManagerTest`에 `FallsBackToDefaultOnNonNumericWidth` 케이스를 추가해 `"width": "abc"` 입력 시 기본값(1280)을 유지하는지 검증한다.
    - `SaveLoadManagerTest` 또는 신규 `PlayerProgressTest`에 `FromRecord`에 `"currency": "not_a_number"`를 넣었을 때 크래시 없이 기존/기본값을 유지하는 케이스를 추가한다.
  - **[처리 결과]** `ConfigManagerTest::FallsBackToDefaultOnNonNumericWidth`, 신규 `tests/PlayerProgressTest.cpp` 2건, 신규 `tests/DataRecordAccessTest.cpp` 8건 추가.

### 그 외 검사 결과 — 위반 없음

- **SOLID**
  - SRP/OCP/ISP/DIP 위반 없음.
  - `ConfigManager`/`SaveLoadManager`가 `IDataStore`에만 의존하도록 잘 분리됨.
  - `DataRecordAccess` 공용화 시 상속이 아닌 네임스페이스 자유 함수(조합)로 처리 — `ConfigManager`와 `PlayerProgress`처럼 IS-A 관계가 아닌 클래스를 상속으로 묶는 안티패턴을 피함.
- **라이브러리 격리**
  - `nlohmann::json` 직접 참조는 `JsonDataStore.cpp` 한 곳뿐임을 grep으로 재확인.
- **주석 규칙**
  - 공개 헤더의 클래스/함수에는 Author/Description/Input/Output/Notes/Date가 빠짐없이 있음.
  - `.cpp` 내부 anonymous namespace 헬퍼 함수는 기존 코드(`LaunchConfigParser.cpp`의 원래 `ParseRendererBackend` 등)와 동일하게 주석 생략 — 기존 컨벤션과 일관됨.
- **단위 테스트**
  - 모든 항목 해결 후 커버리지 공백 없음.
  - 전체 33개 테스트 통과 (`ctest`).
