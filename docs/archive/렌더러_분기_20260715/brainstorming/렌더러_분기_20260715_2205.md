# Details

## 1. 용어 정리 — `*args`/`**kwargs` → C++ 대응

`*args`/`**kwargs`는 Python 문법이며 C++에는 동일한 개념이 없음.
C++에서 "실행 시점 인자를 받는" 지점은 `int main(int argc, char** argv)`의 `argc`/`argv`임.

- `argv`에 `--renderer=dx12`, `--renderer=opengl` 같은 값을 넣어 실행하면, `main`이 이를 파싱해서 어떤 백엔드를 초기화할지 결정하는 구조.
- 즉 사용자가 원하는 "인자로 진입점을 바꾼다"는 목적은 `argc`/`argv` 파싱 + 분기로 그대로 달성 가능함.

## 2. 아키텍처 — Strategy/Factory 패턴

DirectX와 OpenGL은 디바이스 생성, 스왑체인/컨텍스트 구성 등 초기화 절차 자체가 다르므로, 하나의 함수 안에서 `if/else`로 나누기보다 인터페이스로 분리하는 것을 제안.

- `IRenderer` 인터페이스 정의 (예: `Initialize()`, `Shutdown()`).
- `DirectXRenderer`, `OpenGLRenderer`가 `IRenderer`를 구현.
- `RendererFactory`가 파싱된 인자(enum `RendererBackend { DirectX, OpenGL }`)를 받아 알맞은 구현체를 생성.
- `main.cpp`는 `argv` 파싱 → `RendererFactory` 호출 → `IRenderer::Initialize()` 호출만 담당 (SRP: 진입점은 "무엇을 실행할지 선택"만 책임지고, 각 백엔드의 실제 초기화 로직은 각자의 클래스가 책임).

이 구조는 CLAUDE.md의 "외부 라이브러리는 반드시 내부 wrapper 클래스로 감싼다" 원칙과도 자연히 맞아떨어짐 — `DirectXRenderer`/`OpenGLRenderer`가 각각 DirectX/OpenGL API를 감싸는 wrapper 역할을 겸함.

## 3. 프로젝트 범위와의 정합성 — 확정: 옵션 B

`DirectXRenderer`, `OpenGLRenderer` 둘 다 로직 없이 껍데기(`Initialize()`가 미구현 상태를 나타내는 반환값만 주는 수준)만 두고, 이번 태스크는 순수하게 "인자 파싱 → 백엔드 선택 → 분기" 구조 확보에만 집중.
현재 `main.cpp`가 순수 스텁(`return 0;`) 상태인 것과 일관됨.
DirectX 실 초기화 로직은 다음 태스크에서 다룸.

## 4. 인자 파싱 방식 — 확정: 직접 구현 (`argc`/`argv`)

외부 라이브러리 없이 `int main(int argc, char** argv)`의 `argc`/`argv`를 직접 파싱.
플래그가 1개(`--renderer=...`) 수준이므로 이 방식으로 충분하며, `dependency_eval.md` 절차도 필요 없음.

## 5. 파일/디렉토리 구조 (제안)

```
src/
  main.cpp
  renderer/
    IRenderer.h
    RendererBackend.h        (enum + argv 파싱 결과 타입)
    RendererFactory.h/.cpp
    DirectXRenderer.h/.cpp
    OpenGLRenderer.h/.cpp
```

## 6. 단위 테스트 — 확정: 이번 태스크에 포함, 범위는 파싱 구조로 한정

사용자 결정: "main에서 데이터를 받고 이를 파싱하는 구조까지만" 테스트.
옵션 B(둘 다 스텁) 확정에 따라 이번 사이클에서 실질적으로 테스트할 로직도 "인자 문자열 → `RendererBackend` enum 파싱/분기 로직"뿐이므로, 결정 사항이 서로 일관됨 — 렌더러 초기화(`IRenderer::Initialize()`) 자체는 스텁이라 테스트 대상이 아님.

- 현재 프로젝트에는 테스트 프레임워크가 아직 구성되어 있지 않음 (`CMakeLists.txt`에 테스트 타겟 없음).
- 테스트 프레임워크는 외부 라이브러리이므로, CLAUDE.md 핵심 원칙("외부 라이브러리 도입 전 평가")에 따라 `dependency_eval.md` 절차를 먼저 거쳐야 함 — **사용자 결정 필요**: 어떤 프레임워크를 후보로 평가할지.
  - 후보 예시: GoogleTest(가장 널리 쓰임, CMake `FetchContent` 통합 용이), Catch2(헤더 온리에 가까움, 빌드 연동 단순), doctest(가장 가벼움, 컴파일 속도 이점).

- **Q.** 이번 태스크에서 DirectX 실 구현까지 포함할까, DirectX/OpenGL 둘 다 빈 스텁으로 두고 "선택 구조"만 확보할까?
  **A.** 둘 다 빈 스텁 (옵션 B).

- **Q.** 인자(argv) 파싱을 직접 구현할까, 외부 라이브러리를 검토할까?
  **A.** "cpp에서도 python처럼 외부 실행 값을 받을 수 있는 걸로 아는데 그 방법으로 진행해줘. `*args`/`**kwargs`는 그냥 python이 익숙해서 그런 걸 말한 것." → `argc`/`argv` 직접 파싱으로 확정 (외부 라이브러리 불필요).

- **Q.** 단위 테스트 프레임워크 도입을 이번 태스크에 포함할까, 별도 태스크로 분리할까?
  **A.** "이번 테스트에서는 main에서 데이터를 받고 이를 파싱하는 구조까지만 진행할 것." → 해석: 테스트는 이번 태스크에 포함하되, 범위는 "인자 파싱/백엔드 선택 구조"로 한정 (렌더러 초기화 자체는 스텁이라 테스트 대상 아님). 이 해석이 맞는지 확인 필요 — 만약 "이번 태스크에서는 테스트 프레임워크 없이 파싱 구조만 만들고 테스트는 다음으로 미룬다"는 의미였다면 정정 요청.

- **Q.** 테스트 프레임워크 후보들(GoogleTest / Catch2 / doctest)에 대해서는 각기 장점, 단점이 있어?

- **Q.** 라이선스 BSD-3, BSL-1.0, MIT는 뭐야?
  **A.** 셋 다 permissive 오픈소스 라이선스 (카피레프트 없음, 상업적 이용 포함 자유로운 사용/수정/재배포 허용).
  - MIT: 가장 단순, 원저작권 고지만 유지하면 됨.
  - BSD-3-Clause: MIT와 거의 동일 + "기여자 이름을 마케팅에 임의로 쓰지 말 것" 조항 추가.
  - BSL-1.0(Boost): 셋 중 가장 관대함, 소스/바이너리 배포 시 고지 요구가 가장 약함.
  → 이 프로젝트(개인 학습/포트폴리오, 상업적 재배포 없음)에는 세 라이선스 모두 실질적 리스크 없음, GoogleTest(BSD-3) 도입에 라이선스 걸림돌 없음.

- **Q.** (지시) 테스트 프레임워크는 GoogleTest로 진행.
  **A.** 확정. `docs/dependency/googletest_20260715.md`에 `dependency_eval.md` Step 1(평가)/Step 2(래퍼 설계 초안)/Step 3(검증 체크리스트) 작성함. Step 2는 클래스 래퍼 대신 "빌드 타겟 분리"(GoogleTest는 `tests` 타겟에만 링크, `main` 타겟은 무의존)로 원칙을 적용하는 대안을 제시 — 사용자 확인 대기 중.

- **Q.** (지시) 단위 테스트에 대해서는 파싱 부분도 추가하자, 정상적으로 파싱이 되는지도 중요하니까.
  **A.** 반영. 단위 테스트 범위를 "선택 구조가 존재하는지"뿐 아니라 "argv가 실제로 올바르게 파싱되는지"까지 명시적으로 포함하도록 확정. 구체적으로 다음 케이스들을 테스트 대상으로 함 (전략 단계에서 체크리스트화 예정).
  - `--renderer=dx12` → `RendererBackend::DirectX`로 정확히 파싱.
  - `--renderer=opengl` → `RendererBackend::OpenGL`로 정확히 파싱.
  - 플래그 누락 시 기본값(또는 정의된 에러 처리) 동작.
  - 알 수 없는 값(`--renderer=foo`) 입력 시 정의된 에러 처리 동작.
