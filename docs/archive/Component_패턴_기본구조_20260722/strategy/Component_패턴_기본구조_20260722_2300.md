# Strategy: Component 패턴 기본 구조 구현

## 개요

브레인스토밍에서 확정한 설계를 `src/entity_component/`에 구현한다.

- `IEntity`가 `EntityId`와 Component 컨테이너를 직접 소유하는 컴포지션 패턴 (Unity Classic/Unreal Classic과 동일 계열).
- Component 저장 키는 `ComponentId` (같은 타입 다중 보유 지원), `type_index` 보조 인덱스로 타입별 조회.
- `EntityId`/`ComponentId`는 진짜 UUID가 아닌 프로세스 내 유일 정수 ID, 원자적 카운터로 발급.
- `EntityManager`만 두고 `ComponentRegistry`는 만들지 않음 (Component는 Entity가 전담 관리).
- System은 이번 범위 제외. Entity 간 계층(부모-자식) 구조도 이번 범위 제외.
- 컨테이너 자체(Entity/EntityManager)는 단일 스레드 접근을 전제로 하고 주석에 명시, ID 발급만 원자적으로 스레드 안전.

## 설계 세부사항

### ID 타입 — 강한 타입(opaque enum class)으로 EntityId/ComponentId를 구분

`EntityId`와 `ComponentId`를 둘 다 `std::uint64_t` 그대로 쓰면 실수로 서로 바꿔 넣어도 컴파일러가 잡아주지 못한다.
`enum class`로 감싸 타입 레벨에서 구분한다 (런타임 오버헤드 없음, C++14부터 `std::hash`가 모든 enum 타입에
자동 특수화되어 있어 `unordered_map`의 키로 별도 해시 함수 없이 바로 사용 가능).

```cpp
enum class EntityId : std::uint64_t {};
enum class ComponentId : std::uint64_t {};
```

ID 발급은 태그 타입으로 파라미터화한 원자적 카운터 템플릿 하나로 통일한다 (`EntityId`/`ComponentId`가 서로
다른 타입이므로 템플릿 인스턴스화가 갈라져 카운터도 독립적으로 유지된다).

```cpp
template <typename IdType>
class UniqueIdGenerator
{
public:
    static IdType Next();  // static std::atomic<uint64_t> counter, fetch_add(1, relaxed)
};
```

### IComponent / ComponentBase

`IComponent`는 `GetId() const -> ComponentId` 하나만 요구하는 순수 인터페이스로 최소화한다 (ISP).
매 Component 구현체가 ID 저장·발급 로직을 반복하지 않도록, `ComponentBase : public IComponent`가
생성자에서 `UniqueIdGenerator<ComponentId>::Next()`로 ID를 발급받아 저장하고 `GetId()`를 구현한다.
실제 Component(예: 향후 사이클의 `ColliderComponent`)는 `IComponent`가 아니라 `ComponentBase`를 상속하면
ID 처리를 신경 쓸 필요가 없다. 이번 사이클에서는 실제 게임 Component(Collider 등)는 만들지 않고
테스트 안에 더미 Component 하나만 두어 검증한다 (Task 범위: Entity/Component 저장·조회 구조 자체).

### IEntity — 인터페이스는 non-template, 편의 API는 free template 함수

C++은 가상 함수에 템플릿을 쓸 수 없으므로, `IEntity` 인터페이스 자체는 `std::type_index` 기반의
non-template 가상 함수만 선언한다.

```cpp
class IEntity
{
public:
    virtual ~IEntity() = default;
    virtual EntityId GetId() const = 0;
    virtual IComponent& AddComponent(std::unique_ptr<IComponent> component) = 0;
    virtual bool RemoveComponent(ComponentId id) = 0;
    virtual IComponent* FindComponent(std::type_index type) const = 0;
    virtual std::vector<IComponent*> FindComponents(std::type_index type) const = 0;
};
```

타입 안전한 편의 API(`AddComponent<T>()`, `GetComponent<T>()`, `GetComponents<T>()`)는 `IEntity&`를 받는
free template 함수로 `IEntity.h`에 함께 선언한다 — `std::get<T>`가 `std::variant`의 멤버가 아니라 free
function인 것과 같은 이유다. 이렇게 하면 인터페이스는 얇게 유지하면서도 호출부는 타입 안전하게 쓸 수 있다.

`AddComponent`가 내부적으로 `std::type_index(typeid(*component))`(런타임 동적 타입)로 타입 보조 인덱스를
갱신하므로, 조회 시 `typeid(T)`(호출부에서 명시한 정적 타입)와 일치하려면 항상 **컴포넌트의 가장 파생된
구체 클래스**로 Add/Get 해야 한다 (예: `AddComponent<ColliderComponent>(entity, ...)` → `GetComponent<ColliderComponent>(entity)`,
중간 기반 클래스로는 조회하지 않는다). 이 제약은 헤더 주석(Notes)에 명시한다.

### Entity — 저장 구조

```cpp
class Entity : public IEntity
{
    EntityId m_id;
    std::unordered_map<ComponentId, std::unique_ptr<IComponent>> m_components;       // 소유권
    std::unordered_map<std::type_index, std::vector<ComponentId>> m_componentsByType; // 타입별 보조 인덱스
};
```

- `AddComponent`: 소유권 map에 삽입 + 타입 인덱스에 `ComponentId` 추가, 삽입된 Component 참조 반환.
- `RemoveComponent(id)`: 소유권 map에서 타입 조회 후 양쪽에서 제거. 없는 id면 `false` 반환.
- `FindComponent(type)`: 타입 인덱스에서 첫 번째 `ComponentId`로 소유권 map 조회, 없으면 `nullptr`.
- `FindComponents(type)`: 타입 인덱스의 모든 `ComponentId`를 소유권 map에서 조회해 `vector<IComponent*>`로 반환.
- 소멸자: 명시하지 않아도 `unordered_map<ComponentId, unique_ptr<IComponent>>` 소멸 시 각 Component가
  자동 소멸 — Entity를 통해서만 생성·소멸된다는 원칙이 RAII로 자연히 성립한다 (Q2 논의).

### EntityManager

```cpp
class EntityManager
{
    std::unordered_map<EntityId, std::unique_ptr<IEntity>> m_entities;
public:
    IEntity& CreateEntity();               // Entity 생성 + m_entities에 소유권 등록
    void DestroyEntity(EntityId id);        // 존재하면 제거(소멸) — Entity 소멸 시 Component도 연쇄 소멸
    IEntity* FindEntity(EntityId id) const; // 없으면 nullptr
};
```

### 스레드 안전성 범위

`UniqueIdGenerator`의 `std::atomic<uint64_t>` 카운터만 스레드 안전. `Entity`/`EntityManager`의 컨테이너
변경(추가/삭제)은 이번 사이클에서 **단일 스레드 호출을 전제**로 하고, 각 클래스 헤더 주석의 Notes에
"동시 접근 미지원 — 단일 호출 스레드 가정"을 명시한다 (Details 7 합의 사항).
