# Code Review: Component 패턴 기본 구조 구현

## Stage 1 — Quality Inspection

전 항목이 이번 사이클에서 개발한 코드(`src/entity_component/`, `tests/EntityTest.cpp`,
`tests/EntityManagerTest.cpp`) 범위 안에서 즉시 해소 가능한 항목이었다.
사용자의 사전 승인(코드 리뷰에서 바로 해소 가능한 건 바로 해소)에 따라 아래 전부를 직접 수정하고
재빌드·재테스트까지 완료한 뒤 `[RESOLVED]`로 표기한다.

- [RESOLVED] `GetComponent<T>()`/`GetComponents<T>()`가 `static_cast`로 `IComponent*`를 `T*`로 변환하고 있었다.
  - `type_index` 기반 내부 색인이 항상 정확하다는 전제 위에서는 안전하지만, 그 불변조건이 향후 다른
    `IEntity` 구현체 등으로 인해 깨지는 경우 조용한 UB로 이어질 수 있다.
  - **[해결 방안]**
    - `src/entity_component/IEntity.h`의 두 free template 함수에서 `static_cast`를 `dynamic_cast`로 교체.
    - `IComponent`가 이미 가상 소멸자를 가진 다형 타입이라 `dynamic_cast` 사용에 문제 없음을 확인.
    - Notes 주석에 방어적으로 dynamic_cast를 쓴 이유를 명시.
- [RESOLVED] `Entity::AddComponent`가 인자로 받은 `unique_ptr<IComponent>`가 null인 경우를 검사하지 않고
  바로 역참조(`component->GetId()`)하고 있었다.
  - `AddComponent<T>()` 템플릿 경유 호출은 항상 `make_unique`로 유효한 인스턴스를 만들어 문제 없지만,
    `Entity::AddComponent` 자체는 public 가상 메서드라 향후 다른 호출부(예: 역직렬화 로더)가 직접 null을
    넘기면 정의되지 않은 동작이 발생한다.
  - **[해결 방안]**
    - `src/entity_component/Entity.cpp`에 `assert(component != nullptr && ...)` 추가 (Debug 빌드에서만 검증,
      Release 빌드 비용 없음).
- [RESOLVED] `Entity.h`, `EntityManager.h`가 `std::unique_ptr`를 직접 사용하면서도 `<memory>`를 명시적으로
  include하지 않고 `IEntity.h`/`Entity.h`를 통한 전이적(transitive) include에 의존하고 있었다.
  - **[해결 방안]**
    - 두 헤더에 `#include <memory>`를 직접 추가 (Include What You Use 원칙).
- [RESOLVED] `Entity.cpp`가 `std::type_index`를 직접 사용(새 지역 변수 선언)하면서도 `<typeindex>`를
  명시적으로 include하지 않고 `Entity.h`를 통한 전이적 include에 의존하고 있었다.
  - **[해결 방안]**
    - `Entity.cpp`에 `#include <typeindex>`를 직접 추가.
- [RESOLVED] `Entity::RemoveComponent`가 한 타입의 마지막 Component를 제거할 때 `m_componentsByType`에서
  해당 타입 항목 자체를 지우는 분기(`if (ids.empty()) { m_componentsByType.erase(typeIt); }`)를
  검증하는 테스트가 없었다.
  - **[해결 방안]**
    - `tests/EntityTest.cpp`에 `RemovingAllComponentsOfATypeLeavesTypeQueryableAndEmpty` 테스트 추가 —
      마지막 인스턴스 제거 후 조회가 빈 결과를 반환하고, 이후 같은 타입을 다시 추가해도 정상 동작하는지 확인.

### 검증 결과

- SOLID: `IComponent`/`IEntity`는 최소 인터페이스(ISP), `Entity`는 자신의 Component 저장·조회만 책임지고
  (SRP), `EntityManager`는 Entity 수명 관리만 책임진다(SRP). 새 Component 타입은 `ComponentBase`를
  상속하는 것만으로 확장되고 기존 코드를 수정하지 않는다(OCP). `EntityManager`/자유 함수는 `IEntity`
  추상화에만 의존한다(DIP, `CreateEntity`가 구체 타입 `Entity`를 생성하는 것은 컴포지션 루트로서 불가피함).
- Library Isolation: 이번 사이클은 외부 라이브러리를 전혀 사용하지 않아 해당 사항 없음.
- Unit Tests: `EntityTest.cpp`(10개) / `EntityManagerTest.cpp`(5개), 전체 242/242 통과 (기존 227 + 신규 15).
- Comment Rules: 모든 클래스(`UniqueIdGenerator`, `EntityId`, `ComponentId`, `IComponent`, `ComponentBase`,
  `IEntity`, `Entity`, `EntityManager`) 및 `IEntity.h`의 free template 함수 각각에 Author/Description/
  Input/Output/Notes/Date를 포함한 주석이 있다 (기존 코드베이스 관례상 클래스당 하나의 주석 블록이
  모든 멤버 함수를 포괄하며, `IRenderer.h`/`Win32Window.h`와 동일한 패턴).

**Needs separate handling(해소 불가능/범위 밖 이슈): 없음.**
발견된 5건 모두 이번 사이클이 개발한 코드 범위 안에서 즉시 해소했다.
