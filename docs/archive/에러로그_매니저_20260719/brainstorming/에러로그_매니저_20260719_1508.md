# Brainstorming: 에러/로그 매니저

## Details

### 현재 코드 상태 (근거)

`src/app/main.cpp`에 이미 4곳의 에러 처리 지점이 있고, 전부 `std::fprintf(stderr, ...)` 후 `return 1`로 강제 종료한다.

- `LaunchConfigStore::Init` 실패 (`std::invalid_argument`)
- `Win32Window` 생성 실패 (`std::runtime_error`)
- `RendererFactory::Create`가 `nullptr` 반환
- `renderer->Initialize` 실패

`CMakeLists.txt`의 `add_executable(main ...)`에 `WIN32` 키워드가 없으므로 현재 `main.exe`는 콘솔 서브시스템으로 빌드된다 — 즉 지금은 항상 콘솔 창이 함께 뜬다. 다만 이후 사이클에서 배포용으로 `WIN32` 서브시스템(콘솔 없는 창 모드)으로 바꿀 가능성이 있으므로, "cmd 창이 있으면 print" 요구사항은 지금 당장은 항상 참이지만 구조적으로는 `GetConsoleWindow() != NULL` 체크를 넣어두는 것이 맞다.

### 제안하는 구조

- `LogLevel` enum class: `Info`, `Warning`, `Error` (요구사항 그대로 3단계).
- `Logger` 클래스 하나가 포맷팅 + 출력 대상(콘솔/파일) 분배를 담당하되, SRP를 지키기 위해 내부를 다음처럼 쪼갠다.
  - `LogFormatter` (또는 자유 함수): `LogLevel`, 타임스탬프, 메시지를 받아 `"타입 : YYYY-MM-DD HH:MM:SS : 내용"` 한 줄 문자열로 조립. 시간은 `<chrono>` + `localtime_s`(Windows) 사용.
  - `ConsoleLogSink`: `GetConsoleWindow() != NULL`일 때만 `std::cout`/`std::cerr`에 출력 (Error/Warning은 stderr, Info는 stdout 분리 고려).
  - `FileLogSink`: 생성자에 경로를 받고, 경로가 비어있으면 아무것도 하지 않는 no-op 상태로 동작 — 이러면 `Logger` 쪽에서 "경로가 없으면 파일 출력 생략" 분기를 따로 안 둬도 됨(널 오브젝트 패턴).
- 기존 `JsonDataStore`/`SqliteDataStore`가 `IDataStore`를 구현하는 것과 같은 방식으로, `FileLogSink`도 나중에 다른 파일 포맷(예: 회전 로그)으로 교체 가능하도록 작은 인터페이스(`ILogSink`) 뒤에 두는 걸 권장 — 테스트에서도 실제 디스크에 안 쓰고 메모리에 받는 Fake sink를 주입해 검증 가능.

### main.cpp 통합 여부

이번 사이클에서 `Logger` 유틸리티만 만들고 끝낼지, 아니면 기존 4곳의 `std::fprintf(stderr, ...)`를 실제로 `Logger`로 교체하는 배선까지 포함할지 범위를 정해야 한다.
Purpose에 "지금 try/catch 시 강제 종료로 진행하지만 이에 대한 로그가 없다"고 명시되어 있으므로, 배선까지 포함하는 것을 권장 — 안 하면 이번 사이클 결과물이 아무 데서도 안 쓰이는 죽은 코드가 된다.

### Error Code 체계 범위 (확정)

사용자 결정: 현재 확인되는 4가지 에러를 이번 사이클에서 `ErrorCode`로 규정하고, 프로젝트가 커지면서 계속 확장하는 걸 전제로 설계한다.
카테고리별로 번호 대역을 나눠서, 나중에 같은 카테고리에 에러가 추가돼도 기존 번호가 밀리지 않게 한다.

```cpp
enum class ErrorCode
{
    // 1000번대: 설정/실행 인자(Launch/Config)
    LaunchConfigParseFailed = 1001,

    // 2000번대: 플랫폼/윈도우
    WindowCreationFailed = 2001,

    // 3000번대: 렌더러
    UnknownRendererBackend = 3001,
    RendererInitializationFailed = 3002,
};
```

- `main.cpp`의 기존 4개 에러 지점이 각각 위 4개 코드에 그대로 대응된다.
- 다음 사이클 이후 새 에러가 생기면 해당 카테고리 대역 안에서 다음 번호를 이어 붙이면 됨 — 카테고리 자체가 늘어나면(예: 렌더링 파이프라인, 세이브/로드) 4000번대부터 새로 배정.
- 로그 메시지 포맷에 `ErrorCode`를 어떻게 노출할지(예: `Error : 2026-07-19 15:10:00 : [2001] Win32Window 생성 실패: ...`)는 전략 문서에서 정확한 포맷 문자열로 확정한다.

### 전역 접근 방식

기존 `LaunchConfigStore`가 namespace 기반 전역 저장소로 "부팅 시 1회 초기화 후 불변" 계약을 쓰고 있다(이전 사이클 Notes에서 재검토 필요성이 이미 언급됨).
로거는 코드베이스 전역에서 호출되는 게 자연스러운 유틸(스레드 어디서든 `Log::Error(...)` 형태로 호출)이라, 같은 패턴(`LogManager::Init(path)` 1회 초기화 + 전역 접근 함수)을 재사용하는 걸 제안한다.
다만 전역 상태는 단위 테스트 시 상태 초기화/격리가 번거로워지는 트레이드오프가 있어, `Logger` 핵심 로직(포맷팅 + sink 분배)은 인스턴스 가능한 클래스로 만들고, 전역 접근 함수는 그 인스턴스를 감싸는 얇은 래퍼로 분리하는 걸 권장 — 단위 테스트는 인스턴스를 직접 만들어 전역 상태 없이 검증 가능.

### 스레드 안전성

CLAUDE.md 범위에 "현재 단일 스레드 설계에 멀티스레드 적용" 항목이 있고, DX12 렌더러도 향후 멀티스레드 커맨드 기록으로 확장 여지를 남겨뒀다.
로거는 여러 스레드에서 동시에 호출될 가능성이 구조적으로 가장 높은 컴포넌트이므로, 이번 사이클부터 `std::mutex`로 콘솔/파일 출력을 보호하는 걸 권장(과함이 아니라 로거는 원래 멀티스레드 대비가 기본기임).

## Trade-offs

- **널 오브젝트 패턴 (`FileLogSink` 경로 없으면 no-op) vs `Logger`가 직접 분기**
  - 널 오브젝트: `Logger` 코드가 단순해지고 SRP 유지가 쉬움. 대신 sink가 하나 더 필요(약간의 클래스 수 증가).
  - 직접 분기: 클래스 수는 줄지만 `Logger`가 "포맷/분배" 외에 "파일 유무 판단" 책임까지 떠안음(SRP 약화).
  - → 널 오브젝트 패턴 권장.
- **파일 쓰기: 실행 내내 열어두고 매 호출 후 flush vs 매 호출마다 open-append-close** (사용자 확정: 실시간 저장 — 원인 모를 종료에도 추적 가능해야 함)
  - 열어두고 매 호출 후 `flush()`: 파일 핸들을 `Init` 시점에 한 번만 append 모드로 열고, 각 로그 기록 직후 `flush()`로 OS에 밀어넣는다. 재호출마다 열고 닫는 것보다 오버헤드가 적으면서도, `flush()` 시점 이후의 내용은 프로세스가 크래시해도 디스크에 남는다(정전/OS 크래시까지 보장하진 않음 — 이번 사이클 범위 밖).
  - 매번 open-append-close: 핸들을 안 들고 있어도 되지만 호출마다 파일 시스템 오버헤드가 더 크다.
  - → 열어두고 매 호출 후 flush 권장. "실시간 저장"이라는 목적에 부합하면서 매번 열고 닫는 비용을 피함.
- **전역 접근 함수 vs 매번 인스턴스 주입(DI)**
  - 전역: 호출부가 간단(`Log::Error("...")`), 기존 `LaunchConfigStore` 패턴과 일관성.
  - DI: 테스트 격리가 쉽고 SOLID(DIP) 관점에서 더 깔끔하지만, 앱 전역에서 쓰는 유틸을 매번 주입받게 하면 실용성이 떨어짐.
  - → 핵심 로직은 인스턴스화 가능한 클래스로 만들되, 얇은 전역 래퍼를 얹는 절충안 권장(위 "전역 접근 방식" 참고).
