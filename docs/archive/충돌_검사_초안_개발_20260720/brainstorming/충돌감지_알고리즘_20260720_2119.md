# Brainstorming: 충돌 감지 알고리즘 라이브러리

## Details

### 1. 현재 `src/geometry` / `src/math` 자산 확인

이번 모듈이 input으로 삼을 수 있는 타입은 다음이 전부다.

- `math/Vec3`, `math/Quaternion`, `math/Matrix4x4`, `math/Transform` — 순수 수학 타입, 다른 모듈 참조 없음.
- `geometry/Sphere`, `AABB`, `OBB`, `Capsule`, `Cylinder` — 순수 데이터 구조체(판정 로직 없음).
- `geometry/Mesh` — 정점/인덱스 목록만 갖는 삼각형 리스트 데이터.
- `geometry/Intersections.h/.cpp` — 도형 쌍별 특수 교차 함수 모음(SAT 등 이미 일부 구현됨). 이번 사이클이 만들 5종 알고리즘과 목적이 겹치지만, 기존 코드는 "쌍별 전용 함수"이고 이번 요청은 "범용 알고리즘"이라 대체 관계가 아니라 별개 계층으로 본다.

즉 GJK/EPA/BVH/R-Tree/Voxel/FCL 전부 이 타입들만 알면 되고, 서로를 몰라야 한다.

### 2. 요청된 5종 알고리즘의 성격 분류

충돌 감지는 보통 두 단계로 나뉜다 — 이 분류가 "독립성"을 어떻게 지킬지의 기준이 된다.

| 알고리즘 | 단계 | 역할 |
|---|---|---|
| GJK / EPA | Narrow-phase | 두 볼록 도형 사이의 정확한 충돌 여부 + 겹침 벡터(EPA) 계산 |
| BVH | Broad-phase | 다수 객체(혹은 메시 삼각형) 중 실제로 검사할 후보 쌍을 트리 구조로 추려냄 |
| R-Tree | Broad-phase | BVH와 같은 목적, 사각형/박스 묶음을 R-Tree 구조로 색인 |
| Voxel 공간 | Broad-phase | 같은 목적, 균일 격자(grid)로 공간을 나눠 후보를 추려냄 |
| FCL | Broad+Narrow 통합 | 실제 FCL(Flexible Collision Library)은 위 broad-phase 자료구조(BVH 등)와 narrow-phase(GJK/EPA 등)를 한 파이프라인으로 묶은 라이브러리 |

BVH/R-Tree/Voxel 3개는 "같은 문제(다수 객체 중 후보 쌍 추리기)를 푸는 서로 다른 방법"이라 서로 몰라야 한다는 요구사항과 자연스럽게 맞는다. 각자 독립 모듈로 두고, 필요하면 이후 사이클에서 공통 인터페이스로 교체 가능하게 만들 수 있다(이번 사이클 범위는 아님).

GJK/EPA는 narrow-phase라 broad-phase 3종과 목적 자체가 다르므로 독립은 자연스럽다.

### 3. FCL 항목의 모호성 — 열어야 할 질문

FCL은 실존하는 오픈소스 C++ 라이브러리(`flexible-collision-library/fcl`, BSD-3, 로보틱스/충돌 검사용으로 널리 쓰임)다. "FCL 구현"이 다음 중 무엇을 뜻하는지에 따라 설계가 크게 갈린다.

- (A) **실제 FCL 라이브러리를 외부 의존성으로 도입** — `imgui`/`nlohmann_json`/`googletest` 때와 같은 패턴으로 `docs/dependency/fcl_YYYYMMDD.md` 평가 문서를 쓰고, 특정 wrapper 스크립트(예: `src/collision/fcl/FclCollisionModule.cpp` 한 곳)에서만 FCL 헤더를 알게 한다. 이 경우 FCL 내부가 이미 자체 BVH/GJK를 갖고 있어 우리가 직접 만드는 BVH/GJK 모듈과 "같은 문제를 두 번 푸는" 형태가 되지만, 학습/포트폴리오 목적(직접 구현 vs 검증된 라이브러리 비교)상 오히려 의미가 있을 수 있다.
- (B) **FCL이라는 이름의 "통합 파이프라인" 모듈을 직접 구현** — 외부 라이브러리 없이, 이번 사이클에서 만든 BVH(혹은 R-Tree/Voxel) + GJK/EPA를 한 파이프라인으로 엮는 우리 자체 모듈. 이 경우 "독립성" 요구사항과 정면으로 충돌한다 — FCL 모듈이 다른 모듈에 의존하게 되므로, 요구사항 1(상호 독립)의 예외로 명시적으로 인정해야 한다.

어느 쪽이든 있을 수 있는 설계이지만 결과물이 완전히 다르므로, 전략 문서 작성 전에 확정이 필요하다 → Open Question.

### 4. 충돌 감지 알고리즘 자료 조사 (Claude 조사)

실시간 충돌 감지 분야에서 실제로 쓰이는 알고리즘을 단계별로 정리하면 아래와 같다(참고: Ericson, *Real-Time Collision Detection*; Bullet/PhysX/FCL 공개 구현).

**Broad-phase (다수 객체 중 후보 쌍 추리기) — 사용자 요청 3종(BVH/R-Tree/Voxel) 포함**

| 알고리즘 | 핵심 아이디어 | 실무 채택 사례 |
|---|---|---|
| BVH (요청됨) | 도형을 감싸는 볼록체(AABB 등)를 계층 트리로 구성 | Bullet(`btDbvt`), PhysX, FCL 내부 |
| R-Tree (요청됨) | 박스들을 최소 확장 기준으로 묶어 다차원 색인 트리 구성 | 공간 DB(PostGIS 등), 로보틱스 |
| Voxel 공간 (요청됨) | 월드를 균일 격자로 나눠 셀별 오브젝트 목록 관리 | 파티클/유체 시뮬레이션, 오픈월드 게임의 청크 시스템 |
| Sweep and Prune (SAP) | 각 축으로 오브젝트의 AABB 구간을 정렬, 겹치는 구간만 후보로 추림 | Bullet(`btAxisSweep3`), PhysX(레거시 SAP 단계) |
| Spatial Hashing | 좌표를 해시로 셀에 매핑(Voxel과 유사하나 격자를 배열 대신 해시맵으로 관리 — 경계 없는 월드에 유리) | 대규모 파티클 시스템, 일부 오픈월드 엔진 |
| Octree | 밀도에 따라 재귀적으로 8분할하는 적응형 트리(Voxel의 비균일 버전) | 다수의 3D 엔진 씬 그래프, 프러스텀 컬링과 겸용 |
| k-d Tree | 축을 번갈아 기준으로 이등분하는 이진 트리 | 정적 씬의 광선/최근접점 질의(레이트레이싱 등)에 강점, 동적 갱신엔 약함 |

**Narrow-phase (두 도형의 정확한 충돌/겹침 계산)**

| 알고리즘 | 핵심 아이디어 |
|---|---|
| SAT (분리축 정리) | 두 볼록 도형이 겹치지 않으면 반드시 분리하는 축이 존재 — 후보 축들을 모두 검사(이미 `Intersections.cpp`에서 OBB-OBB 등에 부분 사용 중) |
| GJK (요청됨) | Minkowski 차 공간에서 원점 포함 여부를 심플렉스로 반복 좁혀 판정 — support function만 있으면 임의 볼록 도형에 적용 |
| EPA (요청됨) | GJK가 충돌을 확인한 뒤, 겹침 방향/깊이(penetration vector)를 다면체 확장으로 계산 |
| MPR (Minkowski Portal Refinement, XenoCollide) | GJK/EPA의 대안 — 구현이 더 단순하면서 충돌 여부+근사 깊이를 한 번에 계산, 다만 EPA만큼 정밀한 깊이 보장은 약함 |

**연속 충돌 감지(CCD, 고속 이동체용)**

| 알고리즘 | 핵심 아이디어 |
|---|---|
| Conservative Advancement | 두 도형의 최대 접근 속도를 보수적으로 추정해 안전 구간만큼씩 시간을 전진, 충돌 시점(Time of Impact)에 수렴 |
| Swept Sphere/Shape | 이동 구간 전체를 감싸는 볼록체(예: capsule)를 만들어 이산 알고리즘으로 재사용 — 구현은 쉽지만 근사치(false positive 증가) |

**통합 파이프라인 / 라이브러리**

| 이름 | 성격 |
|---|---|
| FCL (요청됨) | 위 broad-phase(BVH 등) + narrow-phase(GJK/EPA 등)를 한 API로 묶은 실존 오픈소스 라이브러리(BSD-3, 로보틱스 표준) |
| Bullet `btCollisionWorld` / PhysX `NpScene` | 같은 성격의 상용/오픈소스 물리 엔진 충돌 파이프라인(참고용, 도입 대상 아님) |

### 5. Claude 추천 우선순위

- **Sweep and Prune (1순위 추천)** — BVH/R-Tree/Voxel과 목적은 같은 broad-phase지만 자료구조가 가장 단순해 세 알고리즘과 나란히 비교하기 좋은 대상이고, 실무 채택 사례(Bullet)도 뚜렷하다.
- **Conservative Advancement 기반 CCD (2순위 추천)** — 이 프로젝트가 탱크 게임이라 포탄처럼 빠른 투사체의 터널링 문제가 실질적으로 발생할 도메인. 다만 "충돌 감지" 범위를 넘어 시뮬레이션 루프(타임스텝)와 맞닿는 부분이 있어 범위 조율이 필요.
- **Octree / Spatial Hashing / k-d Tree (참고용, 낮은 우선순위)** — Voxel·R-Tree와 목적이 겹쳐 이번 사이클에 추가할 실익이 적다. 다음 사이클 후보로만 기록.
- **MPR (참고용)** — GJK/EPA와 목적이 겹치는 대안 알고리즘이라 이번 사이클에서 병행 구현할 필요는 낮다.

## Trade-offs

| 알고리즘 | 장점 | 단점 / 리스크 |
|---|---|---|
| GJK/EPA | 임의의 볼록 도형 쌍에 범용 적용, 겹침 벡터까지 계산 가능(EPA) | 구현 복잡도 높음(single case 버그가 흔함), 오목 도형(Mesh 전체)은 볼록 분해 없이는 직접 처리 불가 |
| BVH | 정적/동적 씬 모두에 적용 가능, 실무에서 가장 흔한 broad-phase | 트리 재구성/균형 비용, 구현 시 분할 전략(SAH 등) 선택 필요 |
| R-Tree | 2D/3D 박스 색인에 특화, BVH 대비 삽입/삭제가 잦은 동적 씬에 유리한 변형 존재(R*-Tree 등) | 이번 사이클엔 정적 삽입만 다룰지 동적 갱신까지 다룰지 범위 결정 필요 — BVH와 차별점이 흐려질 위험 |
| Voxel 공간 | 구현 간단, 격자 크기 고정 시 조회가 O(1)에 가까움 | 오브젝트 밀도가 불균일하면 비효율(빈 격자 낭비 또는 한 격자에 과밀), 격자 크기 튜닝 필요 |
| FCL | (A안) 검증된 라이브러리로 정확성/성능 신뢰 가능 / (B안) 우리 모듈 재사용으로 통합 파이프라인 학습 | (A안) 외부 의존성 추가 관리 비용 / (B안) 요구사항 1(독립성)의 명시적 예외 필요 |
| SAP (추천) | 구현 쉬움, 정렬 유지 비용만 지불하면 매 프레임 갱신이 저렴 | 축 정렬 편향이 심한 씬(한 축에 오브젝트가 몰림)에서는 비효율 |
| CCD (추천) | 고속 투사체(포탄) 터널링 방지 — 탱크 게임에 직접적 효용 | 이산 알고리즘 대비 계산 비용 증가, 이번 사이클의 "충돌 감지" 범위를 넘어 "충돌 응답/시뮬레이션 루프"와 맞닿아 범위 조율 필요 |
| Octree (참고용) | Voxel 대비 적응형이라 밀도 불균일에 강함 | Voxel과 목적 중복 — 우선순위 낮음 |

### 6. 통일된 Geometry 입력 타입 — 설계 대안 (사용자 제안 검토)

사용자 결정 2·3에 따라 GJK/EPA뿐 아니라 BVH/R-Tree(및 향후 Voxel/SAP/CCD/커스텀 FCL 전부)가 "6종 도형(`Sphere`/`AABB`/`OBB`/`Capsule`/`Cylinder`/`Mesh`) 중 아무거나"를 동일한 방식으로 받아야 한다. 사용자는 이를 `IGeometry` 클래스로 묶는 안을 제안했다 — 다만 기존 코드 전반의 설계 원칙과 충돌하는 지점이 있어 대안과 함께 검토한다.

기존 `geometry/*.h` 전부가 명시적으로 "이 클래스는 데이터만 갖고, 판정/로직은 `Intersections.h`의 자유 함수로 뺀다"는 원칙을 코멘트로 못박아 두었다(가상함수/상속 없는 순수 데이터 구조체). `IGeometry`를 고전적인 추상 클래스(가상 함수 `Support()`/`GetBounds()` 등)로 만들면 이 6개 구조체가 전부 상속을 갖게 되어 이 원칙과 정면으로 배치된다.

| 설계안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| (A) `IGeometry` 추상 클래스 (사용자 제안) | `Sphere`/`AABB`/... 전부 `IGeometry` 상속, `Support(dir)`/`GetBounds()` 가상 함수 오버라이드 | 사용자에게 익숙한 OOP 패턴, 새 도형 추가 시 인터페이스가 강제됨(컴파일 타임 누락 방지) | 기존 "데이터 전용 구조체 + 자유 함수" 설계 원칙을 뒤집음, 가상 함수 호출 오버헤드, 도형 struct가 `math`/`geometry` 밖의 인터페이스 헤더에 의존하게 됨 |
| (B) `std::variant` 기반 통일 타입 (Claude 대안 추천) | `using GeometryVariant = std::variant<Sphere, AABB, OBB, Capsule, Cylinder, Mesh>;` + 자유 함수 `Vec3 Support(const GeometryVariant&, const Vec3& dir)` / `AABB GetBounds(const GeometryVariant&)`를 `std::visit`으로 구현 | 기존 도형 struct를 전혀 수정하지 않음(상속 無), 기존 "자유 함수로 로직 분리" 원칙과 완전히 일치(Intersections.h와 같은 패턴), 가상 호출 없음(컴파일 타임 분기), `Overload` 패턴(아래 참고)을 쓰면 새 타입 누락 시 가상 함수와 동급으로 컴파일 에러 발생 | `sizeof(GeometryVariant)`가 6개 타입 중 가장 큰 것(`Mesh`) 기준으로 고정됨 — `Sphere` 하나만 저장해도 `Mesh`만큼의 메모리를 차지(아래 4번 참고) |

Claude 추천은 (B)다 — 기존 코드베이스가 이미 이 패턴(데이터 구조체 + 자유 함수 디스패치)을 5개 파일에 걸쳐 일관되게 써왔고, 이번 모듈만 예외적으로 상속 기반으로 가면 두 패턴이 코드베이스에 공존하게 되어 일관성이 깨진다. 다만 이름은 사용자 제안대로 개념적으로 "IGeometry"(공용 지오메트리 입력 타입)라고 불러도 무방하다 — 실제 구현이 인터페이스냐 variant냐의 문제로 좁혀서 결정하면 된다.

**정직한 재검토(Q5 참고)**: (B)의 우위가 "단순 구현 편의성"만은 아니다 — 값 의미론(힙 할당/포인터 간접참조 없이 컨테이너에 값으로 저장, 캐시 지역성)과 가상 호출 오버헤드 제거라는 실질적 차이가 있다. 다만 실제 물리 엔진(Bullet의 `btCollisionShape`, PhysX의 `PxGeometry` 계열)도 다수가 가상 클래스 계층을 씀 — 콜리전 디텍션의 실제 병목은 보통 기하 연산 자체지 vtable 조회 한 번이 아니라서, 이 프로젝트 규모에서 (A)를 택해도 성능상 실질적 손해는 크지 않을 가능성이 높다. (A)를 택할 경우, 기존 `geometry/*.h`가 명시해 둔 "데이터 전용 구조체 + 자유 함수" 원칙은 이 사이클부터 명시적으로 갱신(무효화)하는 것으로 전략 문서에 기록한다.

**정정 (Q7 참고)**: 위 표에서 "새 도형 추가 시 컴파일 경고로만 알 수 있음"이라고 적었던 것은 정확하지 않다 — 제네릭 람다 + `if constexpr` 조합에만 해당하는 얘기고, 여러 `operator()`를 모은 `Overload` 헬퍼(`template<class... Ts> struct Overload : Ts... { using Ts::operator()...; };`)로 `std::visit`을 쓰면 새 타입 추가 시 대응하는 오버로드가 없어 컴파일 자체가 실패한다 — exhaustiveness 강제력은 (A)와 사실상 동급이다.

**Mesh와 `sizeof` 관계 (Q7 참고)**: `Mesh`는 `std::vector<Vec3> vertices` + `std::vector<uint32_t> indices` 두 개를 멤버로 갖는다. `std::vector`는 "핸들(handle)" 구조체라 실제 원소 데이터는 힙에 별도로 할당되고, `vector` 자신은 그 힙 버퍼를 가리키는 포인터 3개(begin/end/capacity, 64비트 환경 기준 총 24바이트) 정도의 고정 크기다. 즉 `sizeof(Mesh)`는 정점이 0개든 100만 개든 항상 같다(약 48바이트 — vector 2개 몫) — variant의 크기를 결정하는 건 "Mesh가 비어있는가"가 아니라 "vector라는 핸들 구조체 자체의 고정 크기"다. 실제 정점 데이터(가변 크기)는 variant의 인라인 저장 공간 밖, 별도 힙 블록에 존재하며 각 Mesh 인스턴스마다 독립적으로 커진다.
