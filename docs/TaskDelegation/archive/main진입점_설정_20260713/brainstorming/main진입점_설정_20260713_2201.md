# Details

## 1. 진입점: `int main()` (확정)

사용자가 이미 결정한 사항.

- 이유: DirectX 전용이 아니라 추후 OpenGL도 고려하는 API 중립적 구조를 원함.
- `wWinMain`은 Win32/DirectX에 종속적인 진입점이라, OpenGL(GLFW 등)과 병행하기에 부자연스러움.
- `int main()` + 콘솔 서브시스템으로 시작하면, 창 생성은 이후 태스크에서 Win32 API(`CreateWindowW` 등)나 GLFW 같은 라이브러리로 직접 처리 가능 — API 중립성 확보.

## 2. 이번 태스크의 구현 범위: 순수 스텁

목표(`목표` 섹션)가 다음 두 가지이므로, 범위를 여기서 넘지 않는다.

- `[ ]` 진입점 `main.cpp` 확보
- `[ ]` `main.cpp`를 빌드한 `main.exe` 확보

즉 `main()`은 아무 로직 없이 `return 0;`만 하는 상태로 두고, "CMake 빌드 → `main.exe` 생성 → 실행 시 정상 종료(exit code 0)"까지만 확인한다.

창 생성이나 그래픽 API 초기화는 포함하지 않는다 — 범위가 커지면 이번 태스크의 목적("기초 빌드 구조 확보")이 흐려지고, 다음 태스크(창/그래픽 API)와 책임이 섞인다.

## 3. 디렉토리 구조: 최소한으로

지금 구조를 다 잡지 않고, 다음만 만든다.

```
World-of-Tank-imitation-Refactoring/
  CMakeLists.txt
  src/
    main.cpp
```

- CLAUDE.md의 리팩토링 범위에 "디렉토리/프로젝트 구조 정리"가 이미 별도 항목으로 있음 — 그 태스크에서 `include/`, `assets/` 등 최종 구조를 논의하는 게 맞다.
- 지금 최종 구조까지 미리 잡으면, 이후 구조 리팩토링 태스크와 범위가 겹치고 되돌릴 작업이 생긴다.

## 4. C++ 표준: C++17 (확정)

사용자가 이미 결정한 사항 — 호환성 우선.

- MSVC/Clang/GCC 전부 성숙하게 지원해서 툴체인 문제로 막힐 일이 거의 없음.
- 리팩토링 범위의 "멀티스레드 적용"에 필요한 건 C++17로 충분함 (`std::thread`, `<execution>` 병렬 알고리즘 등).
- 게임/그래픽스 업계에서 여전히 C++17을 기본값으로 쓰는 곳이 많아, 포트폴리오 관점에서도 실무 적합성이 있음.
- (참고로 검토했던 대안: C++20 — concepts/ranges 등 최신 문법을 보여줄 수 있지만, 모듈의 CMake 지원이 아직 까다롭고 이번 리팩토링 목표엔 필수가 아니라서 기각.)

## 5. CMake generator: Ninja (확정)

Visual Studio(MSVC) generator와 Ninja 중 선택 필요했음.

| 항목 | Visual Studio(MSVC) generator | Ninja |
|---|---|---|
| 구성 방식 | Multi-config — 한 번의 configure로 Debug/Release 등 여러 설정을 동시에 준비, 빌드 시 `--config`로 선택 | Single-config — configure당 Debug/Release 중 하나만. 둘 다 쓰려면 빌드 디렉토리를 분리해야 함 |
| 산출물 | `.sln`/`.vcxproj`, MSBuild가 빌드 수행 | `build.ninja`, `ninja.exe`가 빌드 수행 (별도 설치 필요, 컴파일러 자체는 그대로 MSVC `cl.exe`) |
| 속도 | 상대적으로 무겁고 느림 | 증분 빌드가 빠름 |
| 이 프로젝트와의 적합성 | Visual Studio IDE로 직접 열어 디버깅할 때 유리 | VS Code + CMake Tools 확장이 기본 선호, 헤드리스 빌드/검증(Claude가 매번 빌드 확인) 루프에 더 적합 |

CLAUDE.md에 명시된 개발 환경 방향(VS Code, 에이전트가 매번 헤드리스로 빌드/검증)에 맞춰 Ninja로 확정.

# Trade-offs

| 항목 | 선택 | 장점 | 단점 / 리스크 |
|---|---|---|---|
| 진입점 | `int main()` | OpenGL 등 API 중립적, 콘솔 로그 출력이 쉬움(디버깅 용이) | 최종 배포 시 콘솔 창이 같이 뜸 → 창 생성 태스크에서 `WIN32` 서브시스템 전환 필요 (해결 가능한 리스크, 지금 당장 처리하지 않음) |
| 범위 | 순수 스텁만 | 태스크가 작고 명확함, 빌드 파이프라인만 먼저 검증 | 실제로 "동작하는" 것을 보려면 다음 태스크(창 생성)까지 기다려야 함 |
| 디렉토리 구조 | 최소(`src/`만) | 지금 결정할 게 적음, 되돌릴 위험 없음 | 최종 구조가 나중에 바뀌면 `CMakeLists.txt` 경로 일부 재수정 필요 (경미) |
| 단위 테스트 | 이번 태스크는 생략 | `return 0`만 하는 함수는 테스트할 로직이 없음 | CLAUDE.md의 "모든 기능에 단위 테스트 작성" 원칙과 형식상 충돌 — 로직이 없다는 이유로 명시적으로 예외 처리 |
| C++ 표준 | C++17 | 툴체인 호환성, 실무 적합성, 이번 범위(멀티스레드 포함)에 충분 | C++20의 concepts/ranges 등 최신 문법은 못 보여줌 (필수는 아님) |
| CMake generator | Ninja | 증분 빌드 빠름, VS Code/헤드리스 검증 루프에 적합 | Single-config라 Debug/Release용 빌드 디렉토리를 분리 관리해야 함 |

# Q&A Log

- **Q.** CMake generator: Visual Studio(MSVC) generator와 Ninja의 차이점이 뭐야?
  **A.** Visual Studio generator는 `.sln`/`.vcxproj`를 생성하고 MSBuild가 빌드하는 multi-config(한 번의 configure로 Debug/Release 등을 동시에 준비) 방식. Ninja는 `build.ninja`를 생성하고 `ninja`가 빌드하는 single-config(구성마다 빌드 디렉토리 분리 필요) 방식이며, 컴파일러는 그대로 MSVC `cl.exe`를 쓰되 증분 빌드가 더 빠름. 이 프로젝트는 VS Code + 헤드리스 빌드/검증을 지향하므로 Ninja가 더 맞는다고 제안함.

- **Q.** C++는 현재 여러 버전이 있는데, C++17이 아직 호환성 면에서 좋다고 들었음.
  **A.** 동의함 — C++17은 MSVC/Clang/GCC 전부 성숙하게 지원하고, 이번 범위(멀티스레드 적용 등)에 충분하며, 게임/그래픽스 업계에서도 여전히 기본값으로 많이 씀. C++20(concepts/ranges 등)은 최신 문법을 보여줄 수 있지만 모듈의 CMake 지원이 까다롭고 이번 목표엔 필수가 아니라서, C++17로 확정하는 것을 제안함. → 사용자 확정.

- **Q.** Ninja 사용쪽으로 결정.
  **A.** 반영함 — CLAUDE.md의 개발 환경 방향(VS Code + 헤드리스 빌드/검증)과도 맞는 선택. CMake generator: Ninja로 확정.

- **Q.** "순수 스텁, `src/main.cpp` + `CMakeLists.txt`만"로 진행해도 괜찮을까요? — 일단 이 부분으로 충분하다고 생각.
