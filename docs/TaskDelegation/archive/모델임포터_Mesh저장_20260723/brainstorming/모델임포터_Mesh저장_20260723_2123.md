# Brainstorming — 모델 Importer (Mesh 읽기/저장)

## Details

### 전체 로드맵 분할

전체 목표(다양한 모델 포맷 로딩 → DX 마이그레이션 → Shader)를 **Importer / DX 세팅 / Shader** 3개의 독립된 Task Cycle로 나눈다.
순서는 **Importer → DX 세팅 → Shader**로 결정.

- Importer를 먼저 두는 이유: 메쉬 파싱/저장 로직은 렌더링 API와 무관하게 독립적으로 개발·단위테스트할 수 있어야 SRP에 맞고, DirectX 디바이스 없이도 검증 가능하다.
- DX 세팅을 먼저 두면 셰이더/파이프라인과 강하게 얽혀서(특히 DX12의 PSO/루트 시그니처) "DX 세팅"과 "Shader"를 분리하기 애매해지고, 아직 시작하지 않은 DX11→후속 버전 마이그레이션이라는 큰 작업이 Import보다 먼저 블로킹하게 된다.
- 트레이드오프: 렌더러가 없는 상태에서는 임포트한 메쉬를 시각적으로 확인할 수 없고, 당분간 유닛 테스트(정점/인덱스 수, 데이터 무결성)로만 검증한다.

### Importer와 Entity-Component(ECS)의 독립

Importer는 `IEntity`/`IComponent`/`EntityManager`(최근 커밋 `feat: Component 패턴 기본 구조` 참고)를 알지 못해야 한다.

- Importer는 "에셋 로딩" 관심사, ECS는 "런타임 구성" 관심사로 서로 다른 축이다. 결합 시 SRP 위반이며, ECS 없이 Importer 단독 유닛테스트가 불가능해진다.
- Importer의 산출물 경계는 순수 데이터 클래스인 `Mesh`이다. ECS 쪽 참조·바인딩(예: 이후 만들 `MeshComponent`가 이 Mesh를 핸들/포인터로 들고 있는 것)은 완전히 다른 모듈의 책임으로 분리한다.
- Phase 1(Importer)의 스코프는 "파일 → Mesh 데이터 → 메모리에 저장(캐싱)"까지이고, ECS와의 연결은 이후 별도 사이클(Component 쪽에서 Mesh를 참조하는 작업)로 넘긴다.

### 공개 API 형태 — 네임스페이스 정적 함수 + 내부 wrapper 클래스

- 공개 API: `namespace ModelLoader { Model LoadOBJ(path); Model LoadFBX(path); Model LoadGLB(path); }` — 상태 없는 정적 함수. (`Model` 구조는 아래 "Mesh/Model 데이터 구조" 절에서 확정)
- 단, `agent_harness/CLAUDE.md`의 "외부 라이브러리는 반드시 내부 wrapper 클래스로 감싼다" 원칙은 그대로 지킨다. 실제 라이브러리 호출(`tinyobjloader`/`ufbx`/`cgltf`)은 `TinyObjWrapper`/`UfbxWrapper`/`CgltfWrapper`가 전담하고, 정적 함수는 이 wrapper 클래스를 함수 내부에서 지역적으로 생성·사용하는 얇은 퍼사드로 둔다.
- 이 구조의 장점: 호출자 입장에서는 상태 없는 정적 함수처럼 단순하게 보이면서도, 실제 격리 지점은 클래스 쪽에 있어 향후 라이브러리 교체 시 wrapper 클래스 내부만 바꾸면 된다.

### Mesh 저장(캐싱) 책임 — MeshManager opt-in

- Import(파싱)와 Storage(캐싱)를 분리한다. `ModelLoader`는 순수 변환만 담당하고, 저장 여부는 사용자가 `MeshManager`를 통해 선택한다(opt-in).
- `MeshManager`는 내부적으로 `ModelLoader`의 정적 함수를 호출해 경로별 캐싱(중복 로드 방지)을 제공한다. 캐싱 없이 즉시 파싱만 하고 싶으면 `ModelLoader`를 직접 호출하면 된다.
- 이 분리는 향후 ECS 통합 시에도 유리하다 — `MeshManager`가 ECS의 `MeshComponent`가 참조할 핸들을 내주는 지점이 될 수 있고, Importer 자체는 계속 ECS를 모른 채로 유지된다.

### 파싱 라이브러리 선정

두 방향을 비교했다.

**방향 A — Assimp 통합**
- BSD-3-Clause, v6.0.5(2026-04-30 릴리즈), 2026-07-15까지 커밋 활동 지속, 13K stars, 40+ 포맷 지원.
- `aiScene`이 머티리얼/애니메이션/카메라/라이트까지 포함하는 풀 씬 그래프라 "Mesh만 읽기"에는 과함.
- 배포 목표(패키징된 .exe) 대비 바이너리 크기가 커짐. zlib/rapidjson 등을 벤더링해서 끌고 들어오는 큰 의존성.
- 포맷별 독립 static 함수 구조와 자연스럽게 맞지 않음 — 내부적으로 큰 통합 객체 하나에서 필요한 것만 뽑아 쓰는 형태가 됨.

**방향 B — 포맷별 경량 라이브러리 (채택)**
- OBJ → `tinyobjloader` (MIT 계열, 2026-06-19 C11 로더 추가 등 활발히 유지보수)
- FBX → `ufbx` (MIT/Public Domain, Blender 4.5가 FBX 임포터로 채택할 만큼 실사용 검증됨)
- GLTF/GLB → `cgltf` (MIT, raylib/bgfx 등 채택) — `tinygltf`는 v2가 2026년 중반 유지보수 전용 모드 진입 후 단종 예정이라 배제.
- 장점: 각 라이브러리가 단일 헤더/단일 소스 수준으로 가벼움. 포맷별 독립 static 함수 + wrapper 클래스 구조와 1:1로 자연스럽게 맞음. 배포 exe 크기도 작음.
- 단점: wrapper 클래스가 3개로 늘어나고, 포맷별 엣지케이스를 각각 검증해야 함. 신규 포맷 추가 시 매번 새 라이브러리+wrapper를 찾아야 함(Assimp는 이미 지원).

**결정: 방향 B 채택.** 이유는 다음과 같다.

- 이미 합의한 아키텍처(ECS 독립, 포맷별 static 함수, 클래스 wrapper)와 자연스럽게 맞음.
- 배포 크기 목표에 유리함.
- 마이그레이션 리스크 관점에서도 B가 더 안전함 — 파사드 설계 덕분에 포맷 하나씩 라이브러리를 교체하는 비용은 A→B든 B→A든 대칭적이지만, "전면 이탈"이 필요한 최악의 경우 A(Assimp 단일 의존)는 4개 포맷이 한 지점에 묶여 있어 한꺼번에 재작업해야 하고 마이그레이션 도중 바이너리가 일시적으로 더 커지는 역효과가 있다. B는 나중에 Assimp가 필요해져도 기존 wrapper를 건드리지 않고 추가만 하면 되므로 점진적·저위험이다.

**마이그레이션 방향에 대한 실사례 재확인**: 실제 개발 사례를 조사한 결과, Assimp를 나중에 이탈하는 이유로 보고되는 것은 (1) 번들 크기(특히 모바일 배포), (2) 스켈레탈/애니메이션 데이터를 다루기 번거로움, (3) 커스텀 바이너리 포맷·의존성 축소 욕구였다. 반대로 "경량 로더로 시작했다가 Assimp로 옮겼다"는 사례는 확인되지 않았다. 즉 실제 이탈 압력은 항상 Assimp → 경량 라이브러리 방향으로만 관측되며, 이는 앞서의 아키텍처적 추론(B가 더 안전한 시작점)을 실사례 측면에서도 뒷받침한다.

### 스레드 안전성 조사

향후 멀티스레딩 적용(프로젝트 목표)을 고려해 세 라이브러리의 스레드 안전성을 조사했다.

- `ufbx`: MSVC/Clang/GCC/TCC + C11/C++11 컴파일 시 atomic 기반으로 thread-safe (프로젝트 툴체인인 MSVC 해당). 구형 컴파일러/pre-C99에서만 일부 기능이 thread-safe하지 않음.
- `cgltf`: 전역/정적 mutable state 없음. `cgltf_data` 인스턴스를 스레드별로 분리하면 완전히 reentrant.
- `tinyobjloader`: 전역 상태 없음. `ObjReader` 인스턴스 멤버로만 상태 유지. 기본(내장 멀티스레딩 옵션을 켜지 않은) 모드에서 서로 다른 파일을 동시에 파싱하는 것은 안전.

**결론**: wrapper 클래스가 라이브러리 객체를 매 호출마다 지역 변수로 생성하기만 하면(전역/정적 캐시를 wrapper 내부에 두지 않으면) 멀티스레드 환경에서 파일별 동시 로딩이 안전하다. 단, `MeshManager`의 캐시 자체는 라이브러리가 보장해주지 않으므로 별도 동기화(mutex 등)가 필요하다는 요구사항이 새로 확인됨 — Requirements에 반영.

### Mesh 데이터 공유 및 저장 최적화 (인스턴싱 vs 기하 합동 탐지)

"동일 형상을 Transform만 다르게 해서 여러 번 쓰는 경우, 메모리를 줄일 수 있는가"라는 질문은 성격이 다른 세 가지 문제로 나뉜다.

**(a) 같은 파일을 두 번 로드하는 경우** — 이미 설계된 경로 기반 캐싱(`MeshManager`)으로 해결된다. 추가 작업 불필요.

**(b) 같은 메쉬 데이터를 여러 위치/회전/스케일로 배치하는 경우 (예: 탱크 바퀴 6개)** — 실무에서는 이걸 "탐지"하지 않는다. USD 등 업계 표준 파이프라인은 애초에 **Transform을 정점 데이터에 굽지(bake) 않고**, 메쉬 지오메트리는 한 번만 저장한 뒤 각 인스턴스가 Transform만 별도로 들고 참조하는 구조를 쓴다. 즉 `MeshManager`가 `Mesh`를 **값 복사가 아니라 참조/핸들**(예: `std::shared_ptr<const Mesh>` 또는 handle/ID)로 반환하도록만 설계하면, 이 메모리 절감은 별도 알고리즘 없이 자동으로 얻어진다. 이건 이번 사이클의 Requirements에 명시적으로 반영해야 한다.

**(c) 서로 다른 파일에서 독립적으로 임포트된 메쉬가 우연히 임의의 Transform으로 합동(congruent)인지 탐지하는 경우** — 이것이 실제로 어려운 문제다.

- 정점 순서·테셀레이션·부동소수점 정밀도가 서로 다른 두 메쉬가 "같은 모양"인지 판별하려면 canonicalization(예: PCA 기반 정규 좌표계, 정렬된 쌍별 거리 시그니처)이 필요하다.
- 대칭 형상(구, 정육면체 등)에서는 정규 좌표계가 여러 개 나올 수 있어 canonicalization 자체가 불안정하다.
- 부동소수점 오차 허용까지 고려하면 사실상 3D 형상 정합(shape registration) 연구 주제에 가깝고, 캐시가 커질수록 매 임포트마다 기존 전체 캐시와 비교해야 해서 비용도 계속 증가한다.
- 이 프로젝트 규모(전차 부품을 개별 제작하는 수준)에서 우연한 기하학적 중복 가능성은 낮고, 의도된 재사용은 이미 (b)로 해결되므로 실익 대비 비용이 크다.

**결정**: (b)를 위해 `MeshManager`가 `Mesh`를 참조/핸들로 반환하도록 Requirements에 추가한다. (c)의 일반적인 임의-Transform 합동 탐지는 이번 사이클 스코프에서 제외하고, 필요성이 실제로 확인되면 이후 사이클에서 "정규화 후 콘텐츠 해시 비교"(엄밀한 임의-Transform 합동 탐지가 아니라, 정규화된 정점/인덱스 데이터가 동일한 경우만 잡아내는 저비용 버전) 정도로 축소해 재검토한다.

### MeshManager 캐시 정책 아키텍처 — 전략 패턴

캐시 무효화(cache invalidation) 정책 후보 4가지를 검토했다.

1. **명시적 해제(Explicit Unload)** — 호출자가 직접 `Unload(path)`를 불러야만 캐시에서 제거.
2. **참조 카운팅(Reference Counting)** — `weak_ptr` 기반. 캐시는 `unordered_map<path, weak_ptr<const Mesh>>`로 약한 참조만 들고, 마지막 `shared_ptr` 소유자가 사라지는 순간 자동 해제. 별도 스캔/타이머 불필요, RAII 원칙 그대로 적용.
3. **파일 변경 감지(Hot-reload)** — 원본 파일이 바뀌면 캐시를 무효화하고 재로드.
4. **LRU/메모리 예산 기반 축출** — 최근 사용된 N개(또는 메모리 예산 이내)를 `shared_ptr`로 강하게 유지해 재스폰 시 재파싱을 피하고, 초과분부터 축출.

**설계 충돌 지점**: 2번(`weak_ptr`, 마지막 참조 소멸 시 즉시 파괴)과 4번(축출 대상을 계속 살려둠)은 동시에 성립할 수 없다 — `weak_ptr`만 든 캐시는 아무도 안 쓰는 순간 이미 죽어 있어서 LRU가 축출할 대상 자체가 없다.

**해결책 — 전략 패턴(Strategy Pattern)**: 2/3/4번을 각각 독립된 정책 클래스로 만들고, `MeshManager`는 그중 **하나만** 선택해 사용한다(동시에 조합하지 않음). 1번(명시적 해제)은 정책과 무관하게 항상 제공되는 인터페이스 메서드로 둔다.

```
class IMeshCachePolicy {
public:
    virtual ~IMeshCachePolicy() = default;
    virtual std::shared_ptr<const Mesh> TryGet(const std::string& path) = 0;
    virtual void Store(const std::string& path, std::shared_ptr<const Mesh> mesh) = 0;
    virtual void Unload(const std::string& path) = 0;  // 1번: 정책과 무관하게 항상 제공, "2중 안전장치"
};

class RefCountingCachePolicy : public IMeshCachePolicy { /* 2번: weak_ptr 기반 */ };
class HotReloadCachePolicy   : public IMeshCachePolicy { /* 3번: 파일 변경 감지 후 재로드 */ };
class LruCachePolicy         : public IMeshCachePolicy { /* 4번: 최근 N개 shared_ptr로 유지 */ };
```

- `MeshManager`는 `unique_ptr<IMeshCachePolicy>`를 생성 시점에 주입받아 사용한다. 게임 실행 중 정책 자체를 교체할 필요성은 없다고 판단해 런타임 스왑 기능은 만들지 않는다.
- SOLID 관점: 새 정책을 추가해도(`class TimeBudgetPolicy` 등) `MeshManager`나 다른 정책 클래스를 건드리지 않음(OCP). `MeshManager`는 구체 클래스가 아니라 `IMeshCachePolicy` 인터페이스에만 의존(DIP). 정책별 독립 unit test 작성도 쉬움.
- 트레이드오프: ref-counting과 LRU를 "동시에" 쓰는 조합(최근 것만 좀 더 오래 살려두면서도 결국 자동 해제)은 이 구조에서 얻을 수 없다. 필요해지면 `RefCountingWithLruPolicy` 같은 합성 클래스를 나중에 추가하면 되므로(OCP) 지금 막힌 것은 아니다.

### HotReloadCachePolicy의 파일 변경 감지 방식

세부 감지 메커니즘도 `IFileChangeDetector` 인터페이스로 한 겹 더 추상화한다.

```
class IFileChangeDetector {
public:
    virtual ~IFileChangeDetector() = default;
    virtual bool HasChanged(const std::string& path) = 0;
};

class Win32FileWatcher      : public IFileChangeDetector { /* Win32 ReadDirectoryChangesW 기반 */ };
class PollingHashFileWatcher : public IFileChangeDetector { /* 수정 시각/해시 비교 기반 */ };
```

두 가지 실제 상용 엔진 사례를 조사했다.

- **Unreal Engine** — `DirectoryWatcher` 모듈이 플랫폼별 OS API를 래핑. Windows에서는 `ReadDirectoryChangesW`를 사용하는 이벤트 기반 구조("Auto Reimport" 기능의 기반).
- **Unity Editor** — 지속 감시가 아니라 Refresh 시점(에디터 포커스 복귀/주기적/수동)에 Assets 폴더를 스캔해 수정 시각 + 콘텐츠 해시를 `.meta` 파일의 이전 값과 비교하는 스캔 기반 구조.

두 방식 모두 실전에서 검증된 접근이라 우열이 아니라 트레이드오프 문제다 — 네이티브 감시(Unreal)는 즉시 반응하지만 전용 스레드/비동기 I/O 관리가 필요하고, 스캔+해시(Unity)는 구현이 단순하지만 즉시 감지는 아니다.

**결정**: 이 프로젝트는 이미 `Win32Window`를 wrapper 클래스로 감싼 전례가 있고(Windows/DirectX 타겟과의 아키텍처 일관성, 포트폴리오 관점에서 비동기 I/O + Win32 API 래핑 경험 가치), **`Win32FileWatcher`(`ReadDirectoryChangesW` 기반)를 이번 사이클에 구현**한다.

- 단, 게임의 메인 윈도우 메시지 루프(`WndProc`)에 결합시키지 않는다 — Importer/MeshManager가 ECS와 독립인 것과 같은 이유로 윈도우 시스템과도 독립이어야 SRP가 유지되고 렌더러 없이 단위테스트가 가능하다.
- `Win32FileWatcher`는 **전용 워커 스레드**에서 `ReadDirectoryChangesW`를 실행하고, 변경 감지 시 콜백/큐로 `HotReloadCachePolicy`에 알린다.
- `PollingHashFileWatcher`(Unity 방식)는 `IFileChangeDetector` 인터페이스만 열어둔 채 이번 사이클에서는 구현하지 않고 백로그로 미룬다. 인터페이스가 이미 추상화되어 있어(OCP) 나중에 필요해지면 기존 코드를 건드리지 않고 클래스 하나만 추가하면 된다.

### (a)/(b)/(c) 재검토 — 씬 그래프 기반 무료 인스턴싱 + Deduplicator 스코프 포함

앞선 (a)/(b)/(c) 분류를 다시 짚었다.

- **(a) 같은 파일 중복 로드**: 경로 기반 캐시로 자동 (변동 없음).
- **(b) 같은 메쉬를 여러 Transform으로 배치**: 이게 **같은 파일 내부**에서 일어나는 경우, glTF/FBX처럼 씬 그래프가 있는 포맷은 파일 자체가 "어느 노드가 어느 메쉬를 참조하는지"를 이미 알려준다. 즉 형상 비교가 전혀 필요 없고, **파싱 시 이 구조를 flatten하지만 않으면 공짜로 얻어진다.** OBJ는 씬 그래프/노드 개념이 없어 해당 없음.
  - **파급 효과**: `Mesh LoadFBX(path)`처럼 "파일 하나 = Mesh 하나"로 설계하면 이 무료 인스턴싱 기회를 파싱 시점에 영구히 잃는다. 공통 데이터 구조는 "고유 지오메트리 목록(`meshes[]`) + 이를 참조하는 노드/Transform 목록(`nodes[]`)"을 구분하는 `Model` 형태가 필요하다 — 다음 논의(Mesh 데이터 구조)에서 확정한다.
- **(c) 서로 다른 파일 간 우연한 기하 합동**: 형상 비교가 실제로 필요한 유일한 경우. 난이도(canonicalization 불안정성, 부동소수점 허용 오차)는 opt-in으로 만들어도 줄지 않는다는 점을 확인했다.

**스코프 포함 결정 (재변경)**: 사용자가 이 프로젝트의 장기 아키텍처 방향(현재는 `app`에서 `main.cpp`를 직접 쓰지만, 이후 엔진 로직을 `engine library` submodule로 분리하고 `app`은 그 submodule만 사용하게 될 예정이며, 별도 저장소의 "mesh 전처리 프로젝트"가 이 경계를 사용할 것이라는 전제)을 근거로, (c)를 이번 사이클에 **인터페이스 + 저비용 근사 구현**으로 포함하기로 결정했다. 목적은 "정확한 구현"이 아니라 "미래 모듈 경계를 지금 확정"하는 것이다.

```
class IMeshDeduplicator {
public:
    virtual ~IMeshDeduplicator() = default;
    virtual std::shared_ptr<const Mesh> FindCongruent(const Mesh& candidate) = 0;
};

class NaiveSignatureDeduplicator : public IMeshDeduplicator { /* 이번 사이클 기본 구현 */ };
```

- `IMeshCachePolicy`(수명 책임)와 분리한다 — Deduplicator는 "이게 이미 갖고 있는 것과 같은가"(정체성) 책임으로 축이 다르다(SRP).
- `MeshManager`는 `IMeshDeduplicator`를 opt-in으로 하나 더 주입받는다(기본 `nullptr` 허용). 활성화 시 캐시 저장 전에 검사해 합동이면 기존 핸들 재사용.
- `NaiveSignatureDeduplicator` 기본 구현: 무게중심 기준 정점-거리 정렬 리스트 + 표면적 + 정점 개수를 바운딩 박스 대각선 길이로 정규화한 시그니처 비교 (회전·이동·균등 스케일 불변, 비균일 스케일·미러링은 못 잡음 — 정확한 형상 정합이 아닌 휴리스틱임을 문서화).
- 인터페이스로 분리해두면 향후 별도 "mesh 전처리" 프로젝트/submodule이 더 정교한 구현으로 교체해도 `MeshManager`나 다른 코드는 건드리지 않는다(OCP, 사용자의 submodule 분리 전략과 부합).

### Mesh/Model 데이터 구조 확정

구조 레벨과 필드 레벨을 나눠 결정했다.

**구조 레벨 — `Model{ meshes: Mesh[], rootNode: Node }` 채택**

- `Mesh`(순수 지오메트리: 정점/인덱스 등, 로컬 좌표계 기준 형상 데이터만)와 `Node`(로컬 Transform + 어떤 Mesh를 참조하는지 + 부모-자식 계층)를 분리한다.
- `Model`은 파일 하나를 로드한 결과 전체 — 고유 지오메트리 목록(`meshes[]`)과 이를 참조하는 노드 계층(`rootNode`)으로 구성된다.
- 이렇게 하면 탱크 바퀴 6개처럼 씬 그래프 내부에서 반복 참조되는 메쉬가 정점 데이터 레벨에서 한 번만 존재하고, 6개 노드가 각자 다른 Transform으로 그걸 참조하는 구조가 파싱 단계에서부터 보장된다 ("(a)/(b)/(c) 재검토" 절 참고).
- OBJ는 씬 그래프가 없어 노드 1개짜리 `Model`로 감싸 반환, 세 포맷 로더의 반환 타입 시그니처를 통일한다.
- 이 결정은 `ModelLoader::LoadOBJ/LoadFBX/LoadGLB`의 반환 타입 자체를 정하는 것이라 wrapper 클래스 구현 전에 확정해야 하고, 나중에 바꾸려면 호출부 전체를 다시 써야 하는 구조적 결정이라 필드 추가보다 훨씬 무겁다.

**필드 레벨 — 이번 사이클 포함/제외 (확정)**

| 필드 | 이번 사이클 |
|---|---|
| 정점 위치 / 인덱스 / 노멀 | 포함 (기본 렌더링 필수) |
| UV | 포함 — 최대 8채널까지 확장 가능한 구조(Unity/Unreal과 동일)로 설계, 이번 사이클은 최소 1채널만 사용하고 필요할 때마다 추가 |
| 머티리얼 참조 | 포함 — 단, 인덱스/이름 참조만. 실제 텍스처 로딩/바인딩은 별도 시스템 책임 |
| 탄젠트/바이탄젠트 | 저장하지 않음 — 노멀맵 필요 시점에 런타임 계산(Unity `RecalculateTangents`와 동일, `float4` + w handedness로 바이탄젠트 재구성) |
| 본 가중치/인덱스 (스키닝) | 제외 — 차체/포탑/포신은 Node+Transform으로 충분, 캐터필러는 UV 스크롤로 구현하기로 확정되어 불필요. 향후 필요 시 정점당 최대 4개(Unity의 가변 256개 방식 대신 고정 4개)로 추가. 상세 배경: `docs/algorithm/10_Bone_가중치_스키닝.md` |

**Unity/Unreal 실사례 확인**: 두 엔진 모두 탄젠트를 `float4`(w=handedness) 하나로만 저장해 바이탄젠트를 셰이더에서 재구성한다(별도 벡터 저장 안 함). UV는 최대 8채널. 본 가중치는 Unity 구버전/Unreal이 정점당 4~8개 고정, Unity 최신 버전만 가변적으로 최대 256개까지 지원.

**MeshManager와의 관계**: `MeshManager`는 경로별로 `Model` 전체를 캐싱 단위로 삼는다(`IMeshCachePolicy`). `IMeshDeduplicator`는 `Model` 내부의 개별 `Mesh`(지오메트리) 단위로, 여러 `Model`에 걸쳐 교차 비교한다 — 즉 캐싱은 파일(Model) 단위, 중복 제거는 지오메트리(Mesh) 단위로 계층이 다르다.

### 원본 Mesh는 어디에 저장되는가 — Model 소유 vs 중앙 저장소

"`Model.meshes`가 원본 Mesh를 각자 소유하는지, 아니면 `MeshManager` 같은 중앙 저장소에 저장하는지"에 대한 질문이 나왔다. 답은 **중앙 저장소이며, 그 저장소는 `Model`이 아니라 `MeshManager`가 갖는다.**

- `Model`이 원본을 각자 소유(값 복사)하면 `IMeshDeduplicator`가 "이미 있는 것"이라고 판정해도 실현할 방법이 없다 — 두 `Model`이 각자 데이터를 값으로 들고 있으면 하나를 다른 하나로 교체할 때 소유권/수명 관리가 애매해진다. 따라서 `Model.meshes`는 `Mesh` 값이 아니라 **`shared_ptr<const Mesh>` 핸들의 목록**이어야 한다. `Node`는 이 목록의 인덱스(또는 핸들 자체)를 참조한다.
- **같은 파일 내부(같은 Model 안) 중복 제거**(탱크 바퀴 6개가 같은 메쉬를 참조)는 `MeshManager` 없이도 공짜로 얻어진다 — 한 번의 파싱 호출 안에서 라이브러리가 이미 구분해주는 고유 메쉬 목록을 flatten하지 않고 그대로 살리기만 하면 되고, 외부 상태가 전혀 필요 없다.
- **파일 간(서로 다른 Model 간) 중복 제거**(`IMeshDeduplicator`)는 "예전에 다른 파일에서 이미 본 지오메트리인가"를 판단해야 하므로, 여러 로드 호출에 걸쳐 기억을 유지하는 무언가가 필요하다. `ModelLoader`는 상태 없는 정적 함수라는 기존 원칙에 따라, 이 기억(중앙 Mesh 풀)은 `MeshManager` 내부에만 존재한다.
- **귀결**: `MeshManager`를 거치지 않고 `ModelLoader::LoadFBX`를 직접 호출하면 파일 간 중복 제거는 전혀 일어나지 않는다(같은 파일 내부 중복 제거만 적용됨). `MeshManager::GetOrLoad(path)`를 통했을 때만 새로 파싱된 `Model`의 각 `Mesh`를 중앙 풀과 `IMeshDeduplicator`로 대조해 일치 시 기존 `shared_ptr`로 교체한다.
- **이점 규모에 대한 재확인**: 같은 파일 내부 중복 제거(실제로 자주 일어나는 케이스)는 `MeshManager` 없이 이미 해결되므로, 중앙 풀이 **추가로** 잡아주는 이점은 서로 다른 파일의 우연한 기하 합동(c)뿐이며, 이는 이 프로젝트 규모에서 실익이 낮다고 이미 판단한 케이스다. 즉 중앙 풀의 실제 가치는 메모리 절감이 아니라 미래 submodule 경계 확정에 있다는 점이 이 구조 분석으로도 재확인된다.

### 절차적 프리미티브(Sphere/Cube/Cylinder)와 캐시 키 일반화

향후 절차적으로 생성하는 Sphere/Cube/Cylinder 등도 같은 중앙 저장소를 공유해야 하는지에 대한 논의.

- 절차적 프리미티브는 사실 (a) "같은 파일 두 번 로드"와 본질적으로 같은 케이스다 — "파일 경로" 대신 "생성 파라미터"(반지름, 세분화 등)가 정체성을 결정할 뿐이고, 같은 파라미터면 결정론적으로 동일한 지오메트리가 나온다. 즉 `IMeshDeduplicator`의 근사 형상 비교(어려운 (c) 케이스)가 필요 없고, 파라미터를 문자열 키(예: `"primitive:sphere:r=1.0:sub=16"`)로 만들어 기존 캐시 조회에 넣으면 된다.
- **이번 사이클에 반영**: `MeshManager`의 캐시 키를 "파일 경로"로 좁게 고정하지 않고 **의미상 고유 식별자 문자열**로 취급한다. 비용이 거의 없는 이름/타입 해석 수준의 일반화이며, 향후 프리미티브 생성기가 같은 매니저/풀을 재사용할 수 있게 해준다.
- **이번 사이클에서 제외**: `SphereGenerator`/`CubeGenerator`/`CylinderGenerator` 등 실제 절차적 생성기 구현은 "파일을 읽는" Importer의 책임과 무관하므로 스코프에서 제외하고 이후 별도 사이클(렌더링/디버그 시각화, 물리 콜라이더 등이 필요해지는 시점)로 미룬다.

## Trade-offs

| 결정 | 장점 | 단점/리스크 |
|---|---|---|
| Importer → DX → Shader 순서 | 렌더링 API 무관하게 독립 개발·테스트 가능 | 시각적 검증은 Shader 단계까지 지연됨 |
| Importer-ECS 독립 | SRP 준수, Importer 단독 테스트 가능 | ECS 연결은 별도 사이클 필요(추가 작업량) |
| 정적 함수 파사드 + 내부 wrapper 클래스 | 호출부 단순, 라이브러리 은닉 원칙 준수 | 파사드 계층이 하나 더 생겨 코드량 소폭 증가 |
| MeshManager opt-in 캐싱 | Import/Storage 책임 분리, 추후 ECS 핸들 제공 지점 확보 | 캐싱을 원치 않는 호출자는 직접 `ModelLoader` 호출 필요(문서화 필요) |
| 방향 B (경량 개별 라이브러리) | 아키텍처 부합, 배포 크기 작음, 이탈 리스크 낮음 (실사례로도 확인) | wrapper 3개 유지보수, 신규 포맷 확장 시 매번 라이브러리 조사 필요 |
| MeshManager가 Model/Mesh를 참조/핸들로 반환 | 동일 지오메트리 다중 배치(인스턴싱) 메모리 절감이 별도 알고리즘 없이 자동 확보 | Mesh/Model의 수명 관리(누가 언제 해제하는지)를 명확히 설계해야 함 |
| 임의-Transform 기하 합동 탐지(`IMeshDeduplicator`)를 이번 사이클에 포함 | 미래 submodule 경계를 지금 인터페이스로 확정, 학습/포트폴리오 가치 | 구현 복잡도(canonicalization 불안정성)는 opt-in으로 만들어도 그대로, 실제 메모리 절감 효과는 작음(대부분의 이점은 씬 그래프 인스턴싱으로 이미 확보됨) |
| MeshManager 캐시 정책을 전략 패턴으로 분리 | OCP/DIP 준수, 정책별 독립 테스트, ref-counting/LRU 충돌 회피 | ref-counting+LRU 동시 조합은 못 얻음(필요시 합성 클래스 추가로 해결 가능) |
| HotReload 감지에 Win32FileWatcher(네이티브) 채택 | 기존 Win32Window wrapper와 아키텍처 일관성, 즉시 감지, 포트폴리오 가치 | 전용 워커 스레드 관리 필요, PollingHashFileWatcher 대비 구현 복잡도 높음 |
| `Model{meshes[], rootNode}` 구조 채택, `meshes`는 shared_ptr 목록 | 씬 그래프 인스턴싱 보존, 중앙 풀과의 교체가 소유권 문제 없이 가능 | `ModelLoader` 반환 타입이 무거워짐, wrapper 구현 시 flatten하지 않도록 주의 필요 |
| MeshManager 캐시 키를 파일 경로 대신 고유 식별자 문자열로 일반화 | 향후 절차적 프리미티브(Sphere 등)가 같은 매니저 재사용 가능(OCP) | 이번 사이클엔 실제 프리미티브 생성기를 만들지 않아 이점이 당장 실현되진 않음 |

## Q&A Log

- Q: DX를 먼저 세팅 → Import → Shader로 갈지, Importer → DX 세팅 → Shader로 갈지?
  A: Importer → DX 세팅 → Shader 추천. Importer는 렌더링 API 무관하게 독립 검증 가능하고, DX 세팅을 먼저 하면 아직 시작 안 한 DX 마이그레이션이라는 큰 작업이 Import를 블로킹하게 됨.
- Q: Importer는 Entity-Component와도 독립되어야 한다고 생각하는데 어떻게 생각하는지?
  A: 동의. Importer(에셋 로딩)와 ECS(런타임 구성)는 서로 다른 관심사이며, 결합 시 SRP 위반 + Importer 단독 테스트 불가능해짐. Importer 산출물 경계는 순수 Mesh 데이터 클래스로 한정.
  후속: Mesh 저장 책임을 어디 둘지에 대해, Import는 namespace의 static 함수로 두고 저장 여부는 사용자가 MeshManager를 통해 선택하게 하자는 제안이 나옴.
  A: 책임 분리 자체는 동의하나, "정적 함수가 외부 라이브러리를 직접 호출"하는 부분은 반대 — CLAUDE.md의 wrapper 클래스 원칙과 충돌. 실제 라이브러리 호출은 내부 wrapper 클래스가 전담하고 정적 함수는 그 클래스를 지역적으로 사용하는 얇은 퍼사드로 두는 절충안 제안, 사용자 수용.
- Q: 라이브러리 방향(A: Assimp 통합 / B: 포맷별 경량 라이브러리) 중 어느 쪽?
  A: 방향 B(tinyobjloader/ufbx/cgltf) 채택 — 합의된 아키텍처와 자연스럽게 맞고 배포 크기에 유리함. tinygltf는 단종 예정이라 cgltf로 대체.
- Q: 방향 A/B 중 나중에 문제가 생겨 반대 방향으로 전환해야 할 때 어느 쪽이 유지보수가 더 쉬운지?
  A: 포맷 하나씩 교체하는 비용은 대칭적이나, "전면 이탈"이 필요한 최악의 경우 A(Assimp 단일 의존)는 4개 포맷이 한 지점에 묶여 한꺼번에 재작업해야 하고 마이그레이션 도중 바이너리가 일시적으로 커지는 역효과가 있음. B는 나중에 Assimp가 필요해져도 기존 wrapper를 건드리지 않고 추가만 하면 되므로 점진적·저위험. B로 시작하는 것이 더 안전.
- Q: (정적 함수 + wrapper 클래스 절충안에 동의하며) 스레드 안정성도 고려해서 조사해달라는 요청.
  A: 세 라이브러리 모두 전역/정적 mutable state 없이 reentrant하게 설계되어 있어 파일별 동시 로딩이 안전함을 확인. 단, MeshManager의 캐시 동기화는 별도 설계 필요.
- Q: A/B 마이그레이션 방향(재확인 요청) + 임포트된 객체가 동형(Transform으로 표현 가능)인지 판단해서 MeshManager 저장 시 메모리를 줄일 수 있는지 검토해달라는 요청.
  A: (1) 실사례 조사 결과 Assimp 이탈 사례(번들 크기·스켈레탈 데이터 문제·의존성 축소)만 확인되고 반대 방향 사례는 없어 B가 시작점으로 더 안전하다는 결론이 강화됨. (2) "동형 메쉬 저장 최적화"는 세 가지로 분리됨 — 같은 파일 중복 로드(이미 해결), 같은 메쉬를 여러 Transform으로 배치(참조/핸들 반환 설계로 자동 해결, Requirements 반영), 서로 다른 파일 간 우연한 기하 합동 탐지(연구 수준 난이도, 실익 대비 비용 커서 이번 사이클 제외).
- Q: MeshManager 캐시 무효화 정책이 뭔지 설명 요청.
  A: 캐시에 저장한 데이터를 언제 버리거나 재로드할지 정하는 규칙. 4가지 후보(명시적 해제/참조 카운팅/파일 변경 감지/LRU)를 설명하고, 처음엔 참조 카운팅+명시적 해제를 기본으로 추천.
- Q: 1번(명시적 해제)은 기본적으로 열어두고, 2번(참조 카운팅)은 자동으로 두되, 3번(핫리로드)·4번(LRU)도 구현은 먼저 해달라는 요청 — 추후 on/off 가능한 수준으로, 학습·포트폴리오 목적도 있음.
  A: 참조 카운팅(2번) 상세 재설명. 2번(weak_ptr, 즉시 해제)과 4번(LRU, 계속 살려둠)은 동시 조합이 불가능함을 지적하고 2-tier 캐시안을 제시.
  후속: 사용자가 "on/off"의 의미를 전략 패턴(정책 클래스 1개만 선택해 연결)으로 재정의 — 2-tier 안보다 이 방식이 더 깔끔하다고 판단해 채택. `IMeshCachePolicy` 인터페이스 + `RefCountingCachePolicy`/`HotReloadCachePolicy`/`LruCachePolicy`, `Unload`는 인터페이스에 포함해 정책 무관 항상 제공.
- Q: 정책은 런타임에도 교체 가능해야 하는지, HotReload 감지 방식은 Unity/Unreal 등 상용 엔진에서 어떻게 하는지 조사해달라는 요청.
  A: 런타임 정책 교체는 불필요하다고 확인, 생성 시점 1회 고정으로 결정. Unreal은 `DirectoryWatcher` 모듈이 Windows에서 `ReadDirectoryChangesW`를 쓰는 이벤트 기반, Unity Editor는 Refresh 시점에 스캔+해시 비교를 하는 방식임을 확인.
- Q: 두 감지 방식을 `IFileChangeDetector`로 추상화해 둘 다 구현하고 선택 가능하게 할 수 있는지, 불가능하면 개인적으로 Unity 방식(폴링)이 나을 것 같다는 의견.
  A: 인터페이스로 뽑으면 둘 다 구현 가능하나(OCP), 이번 사이클엔 실사용 이점 대비 테스트 비용을 고려해 하나만(사용자 선호인 Unity식 폴링) 구현하고 나머지는 인터페이스만 열어둔 채 백로그로 미루자고 제안.
  후속: 사용자가 재고 후 "기존 프로젝트(Win32Window wrapper 전례)와의 일관성"을 이유로 Unreal 방식(`ReadDirectoryChangesW`)으로 최종 결정. 단, 게임의 메인 윈도우 메시지 루프에는 결합하지 않고 전용 워커 스레드에서 독립적으로 동작하도록 설계.
- Q: (a)/(b)/(c) 중 같은 파일 및 같은 파일 내 Transform은 자동으로 Instance 저장하고, 다른 파일에 대해서만 사용자 선택으로 Instance 검사를 하는 것인지 확인 요청.
  A: (a)는 경로 캐시로 자동 확인. (b)가 "같은 파일 내부"의 경우, glTF/FBX는 씬 그래프가 파일 자체에 노드-메쉬 참조를 담고 있어 형상 비교 없이 파싱만 제대로 하면 공짜로 얻어짐(OBJ는 씬 그래프 없어 해당 없음) — 이는 (c)와 난이도가 다른 별개의 케이스임을 지적. 공통 데이터 구조를 `Mesh` 단일 반환이 아니라 `Model{meshes[], nodes[]}` 형태로 설계해야 이 정보가 보존됨을 확인.
- Q: (c)는 난이도를 알고 있고 퀄리티는 중요하지 않다며 이번 사이클에 포함해달라는 요청. 이유: 현재 프로젝트가 app에서 main.cpp를 직접 쓰지만, 향후 엔진 로직을 engine library submodule로 분리하고 app은 그 submodule만 쓰게 될 예정이며, 별도 저장소의 "mesh 전처리 프로젝트"가 이 경계를 사용할 것이라는 전제가 있음.
  A: `IMeshDeduplicator` 인터페이스 + `NaiveSignatureDeduplicator`(회전/이동/균등스케일 불변 근사 시그니처, 정확한 형상 정합 아님) 기본 구현으로 이번 사이클에 포함하기로 결정. `IMeshCachePolicy`(수명 책임)와는 분리된 별도 축(정체성 책임)으로 설계, 향후 별도 프로젝트가 더 정교한 구현으로 교체 가능하도록 인터페이스 경계를 지금 확정.
- Q: `Model.meshes`(원본 Mesh)가 `MeshManager` 같은 싱글톤 중앙 저장소에 저장되는지, 아니면 각 `Model`이 원본을 각자 소유하는지 확인 요청. 후자면 앞뒤가 안 맞고 전자면 인스턴싱 이점이 작지 않겠냐는 의견.
  A: 전자(중앙 저장소)가 맞으며, 그 저장소는 `Model`이 아니라 `MeshManager`에 있음. `Model.meshes`는 `shared_ptr<const Mesh>` 핸들 목록. 같은 파일 내부 인스턴싱은 `MeshManager` 없이 파싱 단계에서 이미 해결되고, `MeshManager`의 중앙 풀이 추가로 잡아주는 건 파일 간 우연한 합동(c)뿐이라 이점이 작다는 관찰이 맞음을 확인 — 이 기능의 가치는 메모리 절감이 아니라 미래 submodule 경계 확정에 있음.
- Q: 절차적으로 생성하는 Sphere/Cube/Cylinder 등도 같은 싱글톤 중앙 메모리에 저장하는 게 맞는지 확인 요청.
  A: 동의. 절차적 프리미티브는 "생성 파라미터"가 정체성을 결정하는 결정론적 케이스라 (a)와 같은 급이며 `IMeshDeduplicator`가 필요 없음 — 파라미터를 문자열 키로 만들어 기존 캐시에 넣으면 됨. `MeshManager`의 캐시 키를 파일 경로가 아닌 고유 식별자 문자열로 일반화하는 것만 이번 사이클에 반영하고, 실제 생성기(`SphereGenerator` 등) 구현은 Importer 책임과 무관하므로 이후 사이클로 미룸.
- Q: 탄젠트/본/UV를 Unity·Unreal이 실제로 어떻게 저장하는지 확인 요청(이전 WOT 프로젝트 기억이 흐릿함). 캐터필러는 UV 스크롤로 구현했었다는 배경 공유.
  A: 조사 결과 두 엔진 모두 탄젠트는 `float4`(w=handedness)로만 저장해 바이탄젠트를 셰이더에서 재구성, UV는 최대 8채널, 본 가중치는 Unity 구버전/Unreal이 4~8개 고정이고 Unity 최신판만 가변 256개까지 지원함을 확인. UV 스크롤은 지오메트리를 건드리지 않는 셰이더 기법이라 본 데이터가 전혀 필요 없음을 설명.
- Q: 탄젠트는 필요시 계산으로 확정, UV는 8채널 지원 구조로 하되 최소 채널부터 점진적으로 확장, 본은 4개까지 지원. Bone 가중치에 대한 아주 자세한 학습 문서를 작성해달라는 요청(충돌 검사에서도 나중에 필요, 공부 목적) — 새 `docs/study/` 폴더를 만들고 CLAUDE.md에 이 관례를 반영해달라는 요청.

- Q: CMake 통합 방식을 `googletest`/`nlohmann_json`과 동일하게 `FetchContent`로 진행해도 되는지 확인 요청.

## Summary & Open Questions (사용자 결정 필요)

**확정된 결론**

- 전체 로드맵: Importer → DX 세팅 → Shader, 3개의 독립된 Task Cycle.
- Importer는 ECS(`IEntity`/`IComponent`/`EntityManager`)와 완전히 독립.
- 공개 API: `namespace ModelLoader` 정적 함수(`LoadOBJ`/`LoadFBX`/`LoadGLB`, 반환 타입 `Model`) + 내부 wrapper 클래스(`TinyObjWrapper`/`UfbxWrapper`/`CgltfWrapper`)로 라이브러리 호출 격리.
- 라이브러리: OBJ=`tinyobjloader`, FBX=`ufbx`, GLTF/GLB=`cgltf` (방향 B) — 실사례 조사로 이탈 리스크 비대칭성 재확인됨.
- 데이터 구조: `Model{ meshes: Mesh[](shared_ptr 핸들 목록), rootNode: Node }`. glTF/FBX의 씬 그래프 내부 인스턴싱(바퀴 6개가 같은 메쉬 참조)은 파싱 단계에서 flatten 없이 보존한다. OBJ는 노드 1개짜리 `Model`로 감싸 반환 타입 통일.
- `MeshManager`는 캐시 키(파일 경로 또는 향후 절차적 프리미티브용 식별자)별로 `Model`을 opt-in 캐싱하고, `Model`/`Mesh`를 값 복사가 아니라 참조/핸들로 반환한다 (동일 지오메트리 다중 배치 시 메모리 절감을 별도 알고리즘 없이 자동 확보). 스레드 안전성 확보 필요.
- `MeshManager`의 캐시 정책은 전략 패턴(`IMeshCachePolicy`)으로 구현하며, `RefCountingCachePolicy`/`HotReloadCachePolicy`/`LruCachePolicy` 중 생성 시점에 하나를 선택해 주입한다 (런타임 교체 없음). `Unload(path)`는 정책과 무관하게 항상 제공.
- `HotReloadCachePolicy`의 파일 변경 감지는 `IFileChangeDetector`로 추상화하고, 이번 사이클엔 `Win32FileWatcher`(`ReadDirectoryChangesW`, 전용 워커 스레드)를 구현한다. `PollingHashFileWatcher`(Unity식)는 인터페이스만 열어두고 백로그로 미룬다.
- 서로 다른 파일(Model) 간 기하 합동 탐지는 `IMeshDeduplicator` 인터페이스 + `NaiveSignatureDeduplicator`(근사 휴리스틱, 정확한 형상 정합 아님) 기본 구현으로 이번 사이클에 포함한다. 중앙 Mesh 풀은 `MeshManager`에만 존재하며, `ModelLoader`를 직접 호출하면 이 중복 제거는 적용되지 않는다. 목적은 미래 "mesh 전처리" 프로젝트/submodule의 인터페이스 경계 확정이며, 정확도·메모리 절감 규모는 이번 사이클 우선순위가 아니다.
- 절차적 프리미티브(Sphere/Cube/Cylinder) 생성기 자체는 스코프 제외하되, `MeshManager` 캐시 키를 고유 식별자 문자열로 일반화해 향후 재사용 가능하게 해둔다.
- `Mesh` 필드 확정: 정점/인덱스/노멀/UV(최소 1채널, 최대 8채널 확장 가능)/머티리얼 참조(인덱스/이름만) 포함. 탄젠트는 저장 안 하고 필요 시 런타임 계산. 본 가중치·인덱스는 이번 사이클 제외(향후 필요 시 정점당 최대 4개로 추가). 상세 학습 자료: `docs/algorithm/10_Bone_가중치_스키닝.md` (신규 작성, README 인덱스 갱신 완료).
- 라이브러리 3종(`tinyobjloader`/`ufbx`/`cgltf`)의 CMake 통합은 `googletest`/`nlohmann_json` 사례와 동일하게 `FetchContent`로 진행한다.
