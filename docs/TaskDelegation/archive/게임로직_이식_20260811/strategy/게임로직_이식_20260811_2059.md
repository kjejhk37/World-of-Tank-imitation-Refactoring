# Strategy: WOT-master 게임 로직 레이어 이식 (아키텍처 뼈대)

## 목표 (브레인스토밍 결론 요약)

이번 사이클에서 이식하는 건 원본 `WOT-master`의 GameManager/SceneManager/Scene/Objects 코드 자체가 아니라, 그 **역할**(씬 등록·전환·생명주기, 씬이 매 프레임 갱신하는 오브젝트)이다.
원본 코드는 단일 스레드에서 D3D를 직접 호출하는 구조였고, 이 프로젝트는 이미 engine(로직)/renderer(렌더링) 스레드를 분리했으므로 원본 코드를 그대로 옮기지 않는다.
대신 이미 있는 `src/projects/engine/InstanceUpdateWorker`(engine 스레드) + `IFrameDataPublisher<InstanceSnapshot>`(스냅샷 파이프라인) + `IRenderer`(렌더 스레드 소비자) 구조 안에, **SceneManager가 관리하는 Scene들이 Entity-Component로 표현한 오브젝트를 매 프레임 갱신하고, 그 결과를 InstanceSnapshot으로 변환해 넘기는** 로직을 채워 넣는다.
모델/충돌 디테일(Tank01_Body/Gun/Turret, BoxCollider 등)은 이번 사이클에서 옮기지 않는다 — Entity 하나당 `TransformComponent` 하나만 갖는 최소 형태로 씬 전환·생명주기·EC 통합이 실제로 동작하는지 검증하는 것이 이번 사이클의 범위다.

## 레이어링 제약 및 파일 배치 방침

`CMakeLists.txt`에 이미 다음 규칙이 명시되어 있다 (라인 115, 145 주석).

- `platform_lib`: 다른 어떤 레이어도 몰라선 안 됨.
- `graphics_lib`: `platform_lib`엔 의존해도 되지만 `projects`(`app_lib`)는 몰라야 함.
- `app_lib`(`src/projects/`): `platform_lib`+`graphics_lib` 둘 다 의존 가능. 역방향 금지.

처음에는 `Scene`/`SceneManager`/`TransformComponent`가 WOT 특정 내용을 모르는 범용 코드라는 이유로 `src/platform/` 안에 새로 추가하려 했으나, 사용자 피드백에 따라 방침을 바꾼다.

> "projects 안에서 작성 후 필요시 platform 및 graphics로 승격을 하는 방향으로 진행하는게 현재 submodule의 아키텍처야"

즉 이 프로젝트(및 `agent_harness` submodule)의 확립된 원칙은 **먼저 `src/projects` 안에서 구체적으로 작성하고, 여러 곳에서 재사용할 필요가 실제로 생겼을 때 `platform`/`graphics`로 승격(promote)한다**는 것이다 — 처음부터 범용성을 예측해 `platform`/`graphics`에 새 파일을 만들지 않는다. 이번 사이클은 그 원칙을 그대로 따른다.

- `Scene`/`SceneManager`/`TransformComponent`/`GameManager`/`PrototypeScene`/`SceneSnapshotBuilder` → 전부 `src/projects/game/` (`app_lib`)
- 이 배치는 레이어링 규칙과도 충돌하지 않는다 — `app_lib`는 `platform_lib`+`graphics_lib`를 자유롭게 의존할 수 있으므로, `TransformComponent`가 `platform/entity_component::ComponentBase`를 상속하고 `platform/math::Transform`을 멤버로 갖는 것, `SceneSnapshotBuilder`가 `graphics/renderer::InstanceSnapshot`을 다루는 것 모두 정상적인 방향의 의존이다.
- 나중에 다른 프로젝트에서도 씬 그래프가 필요해지는 등 재사용 필요가 실제로 생기면, 그때 `Scene`/`SceneManager`를 `platform`으로 승격하는 걸 별도 사이클로 고려한다 (YAGNI — 지금 미리 옮기지 않는다).

## 기존 코드 재사용 계획 (platform/graphics 최대 활용 원칙 적용)

| 새 코드가 필요한 것 | 재사용할 기존 코드 | 비고 |
|---|---|---|
| 오브젝트의 위치/회전/스케일 | `platform/math/Transform`(`ToMatrix()` 포함, 이미 존재) | 새로 만들지 않음 |
| 씬이 오브젝트를 담는 방식 | `platform/entity_component`의 `EntityManager`/`Entity`/`IComponent`/`ComponentBase` | 원본 `GameObject` 상속 계층 대신 이걸 사용 (브레인스토밍 Q4 확정) |
| 엔진 스레드 스냅샷 발행 | `platform/engine/IFrameDataPublisher`+`DoubleBufferPublisher`(이미 존재) | 그대로 사용, 변경 없음 |
| 스냅샷 데이터 형태 | `graphics/renderer/InstanceSnapshot`(이미 존재, `worldMatrices`) | 그대로 사용 — 이번 사이클엔 새 필드 추가하지 않음 |
| 스레드 수명주기 | `projects/engine/InstanceUpdateWorker`(이미 존재, `Start`/`Stop`/`GetPublisher`) | 클래스를 새로 만들지 않고 내부 로직만 교체 |
| 렌더러 쪽 | `graphics/renderer/IRenderer`, `main.cpp`의 while 루프 | **변경 없음** — `RenderFrame(snapshot)` 시그니처 그대로 |

`EntityManager`에는 `CreateEntity`/`DestroyEntity`/`FindEntity(id)`만 있고 "가진 Entity 전부 열거"가 없다. 스냅샷을 만들려면 씬이 가진 모든 Entity를 순회해야 하는데,

> "graphics 랑 platform 안에는 submodule의 main을 기준으로만 존재해야해 만약 EntityManager가 main에 없다면 projects 안에 구현해야 하는 거고"

라는 사용자 피드백에 따라 `platform/entity_component/EntityManager`는 **일절 수정하지 않는다** (메서드 추가도 포함). 대신 열거가 필요한 쪽(`Scene`)이 자기 책임으로 해결한다 — `Scene`은 자신이 `CreateEntity()`로 만든 Entity를 만들 때마다 `std::vector<IEntity*>`에 같이 담아 직접 추적하고, 외부(`SceneSnapshotBuilder`)에는 `GetEntities() const`로 그 목록을 노출한다. `EntityManager`는 여전히 각 Entity의 생성/소멸 수명주기만 담당하고(원래 책임 그대로), 열거 책임은 `projects` 쪽 `Scene`이 진다. 이렇게 하면 `EntityManager` 자신의 기존 설계 철학("Component uuid로 전역 조회하는 별도 Registry는 두지 않는다 — YAGNI", `EntityManager.h` 자체 주석)과도 맞고, `platform`은 정말 한 줄도 바뀌지 않는다.

## 데이터 흐름 (이번 사이클 이후)

```
[engine 스레드 : InstanceUpdateWorker::Run()]
  GameManager::Update(dt)
    -> SceneManager::Update(dt)
         -> 활성 Scene(PrototypeScene)::Update(dt)
              -> 자신이 GetEntities()로 추적 중인 각 Entity의 TransformComponent 갱신
  SceneSnapshotBuilder::Build(gameManager.GetSceneManager(), snapshot)
    -> 활성 Scene들의 GetEntities()를 순회하며 TransformComponent::transform.ToMatrix()를 모아 InstanceSnapshot.worldMatrices 채움
  publisher.Publish()

[렌더 스레드 : main.cpp while 루프] (변경 없음)
  renderer->RenderFrame(worker.GetPublisher().AcquireReadSnapshot())
```

## 설계 결정 사항

1. **원본 `Scene`의 `PreRender`/`Render`/`PostRender`/`GUIRender`는 이식하지 않는다.** 렌더링은 이미 `IRenderer`/렌더 스레드가 전담하므로, 새 `Scene`은 `Start()`/`Update(float deltaTime)`/`End()`만 갖는다.
2. **원본 `SceneManager`는 `Singleton<SceneManager>`였지만, 새 `SceneManager`는 싱글턴으로 만들지 않는다.** 이 프로젝트는 `main.cpp`에서 보듯 전역 싱글턴 대신 명시적 조립(DI) 스타일을 이미 일관되게 쓰고 있고, `GameManager`가 `SceneManager`를 멤버로 소유하는 것으로 충분하다.
3. **`InstanceUpdateWorker`는 이름/공개 API를 그대로 유지한다.** 이 클래스의 기존 주석이 "이후 물리/애니메이션 시스템이 생기면 이 클래스를 그 시스템으로 교체한다"고 이미 명시하고 있어, 내부 로직만 `GameManager` 기반으로 바꾸는 것이 원래 설계 의도에 맞는다. 이름을 더 적합하게 바꾸는 건(예: `GameEngineWorker`) 이번 "꼭 필요한 아키텍처만" 범위를 벗어나므로 다음 사이클 정리 대상으로 미룬다.
4. **`PrototypeScene`(가칭)이 `TestScene`을 대체한다.** 원본 이름 `TestScene`을 그대로 쓰면 "테스트용이라 버려도 되는 코드"로 오해하기 쉽다는 점이 이번 대화에서 문제로 지적되었으므로, 실제 활성 씬이라는 의미가 드러나는 이름으로 새로 만든다. (이름 자체에 이견 있으면 이 문서 승인 전에 조정)
5. **`PrototypeScene`의 초기 콘텐츠는 기존 `InstanceUpdateWorker`가 만들던 격자 배치+상하 bob+회전 데모를 그대로 재현한다.** 새 시각 콘텐츠를 만드는 게 아니라, 기존 `InstanceUpdateWorkerTest`의 3개 회귀 테스트(개수 일치, 반복 안전, 시간에 따라 스냅샷 변화)가 그대로 통과하는지로 "로직이 Scene/Entity 경유로 옮겨졌어도 동작은 그대로"임을 검증하는 것이 목적이다. Tank 모델/충돌은 다음 사이클.
