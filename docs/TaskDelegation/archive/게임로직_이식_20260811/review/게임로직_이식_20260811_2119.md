# Code Review (Stage 1): WOT-master 게임 로직 레이어 이식 (아키텍처 뼈대)

사용자 요청에 따라 다음 두 가지를 중점적으로 확인했다.

1. `platform`/`graphics`를 건드리지 않았는지.
2. `WOT-master`에서 기능을 그대로 가져와서 중복되거나 불필요한 기능이 존재하는지.

## 중점 확인 1 — platform/graphics 무변경 확인

`find src/platform src/graphics -newermt "2026-08-11 20:50"`(Step 4 구현 시작 시각 이후 수정된 파일 검색)로 확인한 결과, **일치하는 파일이 0개**다.
이번 사이클에서 새로 만들거나 수정한 파일은 전부 `src/projects/game/`, `src/projects/engine/InstanceUpdateWorker.{h,cpp}`, `tests/`, `CMakeLists.txt`뿐이며, `platform`/`graphics`는 이번 사이클 동안 실제로 한 줄도 바뀌지 않았다.
전략 문서의 최종 승인 기준("`src/platform/`, `src/graphics/`는 새 파일도, 기존 파일 수정도 전혀 없음")을 충족한다.

## 중점 확인 2 — WOT-master 중복/불필요 기능 carry-over 확인

새로 작성한 6개 클래스(`TransformComponent`, `Scene`, `SceneManager`, `PrototypeScene`, `GameManager`, `SceneSnapshotBuilder`)를 `WOT-master`의 대응 원본과 대조했다.

- `Objects/Basic/GameObject`(Mesh/Material/WorldBuffer 소유), `Scene/WOT/TestScene`(naruto/outline/trail/renderTarget/depthStencil/body/gun/turret/collider), `GameManager::Create()`(Device/Environment/Audio/Font/ImGui 초기화), `GameManager::Render()`(ImGui 프레임 구성 + D3D Present) — 이 중 어느 것도 이번 코드에 들어오지 않았다. 전부 브레인스토밍/전략 문서에서 "이번 사이클엔 옮기지 않는다"고 명시한 항목과 정확히 일치한다.
- `SceneManager`가 `Singleton<SceneManager>`였던 원본과 달리 싱글턴이 아닌 것도 의도한 설계 결정대로다(전략 문서 설계 결정 사항 2번).
- `PrototypeScene`의 격자 배치+bob+회전 수식은 `WOT-master`에서 가져온 게 아니라, **이 프로젝트 자신의** 기존 `InstanceUpdateWorker.cpp`(2026-07-28 작성, 이번 사이클 이전부터 있던 코드)에 있던 데모 수식을 그대로 옮긴 것이다 — 회귀 테스트 기준선을 유지하기 위한 의도된 재사용이며, `WOT-master` 중복이 아니다. 코드는 원래 위치(`InstanceUpdateWorker.cpp`)에서 제거되고 `PrototypeScene.cpp`로 옮겨졌을 뿐 두 곳에 동시에 존재하지 않는다.
- `GameManager`/`SceneManager`라는 클래스 이름 자체는 원본과 같지만, 책임(생성자에서 씬 하나만 등록/활성화, 스스로 루프를 돌지 않음)은 원본과 크게 다르다 — "이식"이라는 사이클 목적상 이름을 재사용한 것으로, 실제 기능이 중복되진 않는다.

**결론: 이번 사이클 범위 안에서 `WOT-master`의 불필요한 기능이 그대로 carry-over된 사례는 발견되지 않았다.**

## SOLID / 라이브러리 격리 / 테스트 / 주석 규칙 전체 점검

- **SRP**: `Scene`(씬 생명주기+Entity 보유), `SceneManager`(씬 등록/전환), `GameManager`(씬 구성 조립), `SceneSnapshotBuilder`(InstanceSnapshot 변환)로 책임이 분리되어 있다. `GameManager::Update()`가 스냅샷 변환까지 하지 않고 `SceneSnapshotBuilder`를 별도로 둔 것이 이 원칙을 잘 지킨다.
- **LSP**: `Scene::Start()`/`End()`는 기본 no-op이라 `PrototypeScene`이 `End()`를 재정의하지 않아도 안전하게 치환된다.
- **DIP**: `SceneManager`는 구체 타입이 아닌 `Scene`(추상)에 의존한다. `GameManager`가 `PrototypeScene`(구체)을 직접 생성하는 건 조립 지점(composition root)의 정상적인 역할이라 위반이 아니다.
- **라이브러리 격리**: 새 코드 6개 파일 중 외부 라이브러리를 직접 참조하는 곳 없음 — 해당 없음.
- **테스트**: 신규 클래스 6개 중 `TransformComponent`/`Scene`은 별도 테스트 파일이 없지만, 각각 `PrototypeSceneTest`/`SceneManagerTest`를 통해 간접 검증된다 — 이 프로젝트의 기존 관례(`ComponentBase`도 별도 테스트 파일 없이 간접 검증됨)와 일치한다.
- **주석 규칙**: 6개 파일 모두 클래스 상단에 Author/Description/Input/Output/Notes/Date를 갖췄다 — `EntityManager.h`/`Entity.h`처럼 클래스당 하나의 블록으로 개별 메서드에는 따로 달지 않는 기존 관례와 일치한다.

## 발견 사항

- [RESOLVED] `src/projects/game/GameManager.cpp`의 `kPrototypeSceneKey`가 `constexpr`이 아닌 일반 `const char*`로 선언되어 있다.
  - 컴파일 타임 상수로 만들 수 있는 값인데 런타임 초기화 대상으로 선언됐다 — 기능상 문제는 없지만, 같은 패턴을 쓰는 `main.cpp`의 `kDefaultConfigFilePath`(`constexpr const char*`)와 관례가 어긋난다.
  - **[해결 방안]**
    - `const char* kPrototypeSceneKey` → `constexpr const char* kPrototypeSceneKey`로 변경.
  - **처리 결과**: `constexpr`로 수정, `tests` 재빌드 후 관련 17개 테스트(SceneManager 5 / PrototypeScene 4 / GameManager 2 / SceneSnapshotBuilder 3 / InstanceUpdateWorker 3) 전부 재통과 확인.
