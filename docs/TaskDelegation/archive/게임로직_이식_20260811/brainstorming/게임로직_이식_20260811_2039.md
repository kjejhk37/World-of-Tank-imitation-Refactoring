# Brainstorming: WOT-master 게임 로직 레이어 이식

## Details

이식 대상 4개 영역(GameManager/Objects/Scene/Algorith)의 실제 원본 코드를 확인한 결과, Task 문서 작성 시점에는 드러나지 않았던 사실이 하나 발견되어 먼저 정리한다.

- `Scene/WOT/WOT.h`, `WOT.cpp`는 완전히 빈 스텁이다 (총 30줄, 멤버 변수 없음, 모든 함수 본문이 비어 있음).
- 실제 "전차전" 프로토타입에 가까운 로직은 같은 폴더의 `TestScene.cpp/h`(159줄)에 있다 — `body`/`gun`/`turret` 3개 Model과 `BoxCollider` 2개로 전차를 몸체/포탑/포신으로 분리해 다루고 있어, WOT 게임의 핵심 구조(전차 부위 분리)를 보여주는 것은 이쪽이다.
- 따라서 Task 문서의 "Scene/WOT/(SkyScene, TestScene, WOT.cpp/h — 실제 전차전 게임 로직)" 서술은 정정이 필요하다 — 실제 게임 로직은 `WOT.cpp`가 아니라 `TestScene.cpp`에 있고, `WOT.cpp`는 앞으로 채워야 할 빈 진입점이다.

이 사실을 바탕으로 Task 문서의 3가지 확인 요청 사항에 대해 다음과 같이 제안한다.

**1. 이식 범위 — 4개 영역 전부 vs 좁히기**

`GameManager → SceneManager → Scene → (Scene이 들고 있는 Objects)` 순의 의존 관계상, `GameManager`/`SceneManager`만 옮겨서는 실행 가능한 결과물이 나오지 않는다.
반대로 4개 영역을 한 사이클에 전부 옮기면 review/build/test를 사이클 단위로 쪼개 진행한다는 프로젝트 원칙(Task-by-task, no full upfront plan)과 맞지 않는다.
따라서 "실행 가능한 최소 단위"로 범위를 좁힐 것을 제안한다.

- 이번 사이클: `GameManager` + `SceneManager` + `Scene` 기반 클래스 + `Objects/Basic` 중 씬 하나를 띄우는 데 필요한 최소 요소.
- 다음 사이클 이후로 분리: `Objects/Character`, `Objects/Particle`, `Objects/PostEffect`, `Objects/UI`, `Objects/Landscape`, `Algorith`(경로탐색 — AI 전차가 실제로 필요할 때).

**2. 기준 씬 — WOT.cpp vs TestScene**

빈 스텁인 `WOT.cpp`를 이식 기준으로 삼으면 이식할 내용 자체가 없다.
`TestScene`을 1차 기준 씬으로 이식하고, `WOT.cpp`는 이후 사이클에서 게임 진입점(실제 SceneManager에 등록되는 씬)으로 내용을 채워나가는 방식을 제안한다.

**3. 데모/튜토리얼 씬 포함 여부**

`Scene/` 아래 `AStarScene`, `BillboardScene`, `CollisionScene`, `GridScene`, `InstancingScene`, `LightScene`, `ModelAnimatorScene`, `ModelExporterScene`, `ModelInstancingScene`, `ModelRenderScene`, `ParticleScene`, `TerrainEditorScene`, `TerrainScene`, `TutorialScene` 12개는 원 저자가 기능 학습/검증 목적으로 만든 데모이며, 포트폴리오 목표물인 전차전 게임 자체와는 무관하다.
이식 대상에서 제외하고, 필요하면 `WOT-master`가 그대로 남아있는 참고 코드로만 활용할 것을 제안한다.

**4. Objects를 Entity-Component로 흡수 vs 원본 클래스 계층 그대로 이식**

원본은 `GameObject : Transform`을 루트로 `Cube`/`Sphere`/`ModelObject` 등이 상속하는 단일 계층 구조이며, `GameObject` 하나가 Mesh/Material/WorldBuffer/Transform을 전부 소유한다.
현재 리팩토링 프로젝트에는 이미 `src/platform/entity_component`(Entity/IComponent/ComponentBase, 2026-07-22 도입)가 있고, 렌더링·수학 레이어도 이미 별도 시스템(`src/graphics`)으로 분리되어 있다.
원본 `GameObject` 계층을 그대로 옮기면 이미 분리해둔 렌더링/수학 책임을 다시 하나의 클래스에 뭉치게 되어, 프로젝트가 명시한 SRP 원칙 및 기존 EC 인프라 투자와 충돌한다.
Objects를 EC 시스템의 Component(예: MeshComponent, ColliderComponent 등)로 흡수하는 방향을 제안한다 — 단, 이 경우 Component 종류 설계 자체가 작업량이 있으므로 Step 3 전략 문서에서 별도로 다뤄야 한다.

**5. GameManager/SceneManager와 기존 `src/projects/main.cpp` 진입점의 통합 지점 (신규 발견)**

`src/projects/main.cpp`를 확인한 결과, 진입점은 이미 존재하며 원본 WOT-master처럼 빈 상태에서 시작하는 게 아니다.

- 현재 `main()`은 `Win32Window` + `RendererFactory`로 만든 `renderer`를 직접 들고, `InstanceUpdateWorker`(엔진 스레드)가 매 프레임 `IFrameDataPublisher` 스냅샷을 만들면 `renderer->RenderFrame(snapshot)`으로 그리는 구조다.
- 즉 "게임 로직이 매 프레임 무엇을 갱신하고 무엇을 그릴지"를 결정하는 자리가 이미 `InstanceUpdateWorker`로 잡혀 있고, `main()`의 while 루프는 `renderer->RenderFrame(...)`만 호출한다.
- 원본 `GameManager`/`SceneManager`는 이 역할(각 프레임 Update→Render 호출 주체)을 스스로 맡는 구조였으므로, 그대로 옮기면 `InstanceUpdateWorker`와 책임이 겹치거나 충돌한다.

따라서 이식 대상 4개 영역 중 `GameManager`/`SceneManager`는 원본 그대로의 "자기 스스로 루프를 도는 매니저"가 아니라, 기존 `InstanceUpdateWorker`/`IFrameDataPublisher` 파이프라인 안에 씬 갱신 로직을 공급하는 형태로 재설계가 필요할 가능성이 높다.
이 통합 방식 자체가 Task 문서의 원래 3가지 질문에 없던 새 결정 사항이므로, Open Questions에 추가한다.

## Trade-offs

- 범위 축소(제안): 사이클마다 빌드/테스트로 검증 가능, 리뷰 부담 감소 / 단점: `WOT.cpp`가 실제로 동작하기까지 여러 사이클이 필요.
- 4개 영역 한번에: 왕복 횟수 감소 / 단점: 프로젝트의 "사이클당 소단위 위임" 원칙과 불일치, AI 구현 범위 통제가 어려워짐.
- 데모/튜토리얼 씬 제외(제안): 포트폴리오 목표(전차전 게임)에 집중, 불필요한 이식 작업 감소 / 단점: 일부 씬(`ParticleScene`, `LightScene` 등)이 이펙트 배선 예시로 참고할 만한 코드였는데, 이식하지 않으면 필요 시 `WOT-master` 원본을 직접 참고해야 함(다만 원본이 삭제되는 것은 아니므로 감수 가능한 손실로 판단).
- EC 흡수(제안): 기존 인프라·SOLID 원칙과 일치, 이후 재작업 위험 감소 / 단점: Component 설계를 먼저 해야 해서 착수까지 시간이 더 걸림.
- 원본 계층 그대로 이식: 빠르고 원본과 1:1 대응이라 이해하기 쉬움 / 단점: 이미 분리해둔 렌더링/수학 책임과 충돌, 조만간 다시 뜯어고쳐야 할 가능성이 높음.

- Q5 (main.cpp/InstanceUpdateWorker 파이프라인에 맞춰 재설계하는 방향에 동의하는가?): "현재 main.cpp를 기준으로 꼭 필요한 아키텍처를 가져오는 것으로 요청" → **확정.** GameManager/SceneManager는 원본을 그대로 옮기지 않고, 기존 `main.cpp`/`InstanceUpdateWorker`/`IFrameDataPublisher` 파이프라인에 맞춰 "꼭 필요한 최소 아키텍처"만 통합하는 방향으로 재설계.
- Q4 (Objects를 Entity-Component로 흡수하는 방향에 동의하는가?): "동의 이미 Entity-Component 구조로 가기로 정의 하였음" → **확정.** Objects는 원본 상속 계층이 아니라 기존 Entity-Component 시스템의 Component로 흡수. (프로젝트 전체 방향으로 이미 정의되어 있던 사항 재확인)
- Q2 관련 (TestScene의 개발 의미 확인 요청 + "기능테스트용 Scene이 필요하면 main.cpp가 아니라 별도 test_main.cpp에서 하자"): `WOT-master/D3DX_2209/GameManager/GameManager.cpp` 생성자를 확인함. → **TestScene은 원 저자의 일회성 기능 테스트 스크래치가 아니라, 원본 빌드에서 실제로 게임이 시작할 때 도는 활성 씬이다.** 근거: `SCENE->Create("Start", new TestScene())`로 등록되고 `SCENE->Add("Start")`로 `activeScenes`에 들어가 매 프레임 `Update()`/`Render()`가 호출됨. 반대로 `SCENE->Create("Start", new WOT())`는 바로 아래 줄에 주석 처리되어 있어 — 원 저자가 최종적으로는 `WOT` 클래스로 교체할 생각이었지만, 실제로 한 번도 활성화하지 못한 채 프로젝트가 멈춘 상태로 보인다. 그 외 `Sky`(SkyScene)만 `Grid`와 함께 상시 활성화되어 있고, 나머지 데모 씬(GridScene 제외 12개)은 전부 주석 처리되어 있음. → 결론적으로 "기능 테스트용이라 별도 test_main.cpp로 분리"가 필요한 대상이 아니라, 이름과 달리 사실상의 본편 콘텐츠(전차 body/gun/turret 배치 + 콜라이더)이므로 `main.cpp` 파이프라인에 통합하는 이번 계획 그대로 진행하는 것이 맞다고 판단됨 — 사용자 재확인 필요.
- Q2 최종 답변: "씬 전환·생명주기 뼈대만 먼저 가져오는 방향으로 진행해줘 단 아마도지만 현재 WOT를 그대로 가져오는건 의미가 없을 가능성도 있음 이번에 우리가 engine과 renderer를 다중 스레드 하기로 했기 때문에 이에 맞춰서 적당한 기능만 가져와야 할 꺼야" → **확정.** 1) 이번 사이클은 `TestScene`/`WOT`의 씬 전환·생명주기 뼈대만 가져오고 모델/충돌 디테일은 다음 사이클로 미룸. 2) 원본 `Scene`은 단일 스레드에서 `Update()`~`GUIRender()`를 전부 같은 스레드가 순서대로 호출하며 `Render()` 계열 안에서 D3D를 직접 호출하는 구조였는데, 이 프로젝트는 이미 engine(로직)/renderer(렌더링)를 스레드로 분리하기로 했으므로 그대로는 못 옮김. `src/projects/engine/InstanceUpdateWorker.h`의 클래스 주석("이후 물리/애니메이션 시스템이 생기면 이 클래스를 그 시스템으로 교체한다")을 확인 — 바로 이 자리가 SceneManager/Scene의 로직(Update)이 들어갈 자리로 이미 설계되어 있었음. → 이번 사이클 아키텍처 방향: `SceneManager`+`Scene::Update()`는 engine 스레드(현재 `InstanceUpdateWorker`가 하던 합성 데이터 생성 역할을 대체)에서 돌며 스냅샷을 만들고, 원본의 `PreRender()`/`Render()`/`PostRender()`/`GUIRender()`처럼 D3D를 직접 호출하는 코드는 그대로 옮기지 않고 렌더 스레드가 스냅샷을 소비하는 방식으로 재설계.
- 원칙 추가: "platform 과 graphics를 최대한 활용해서 개발을 진행해야해 가능하면 platform 과 graphics의 특정 함수를 상속 받아서 구현하는 방향으로 가야 한다는 이야기야" → **확정.** 이번 이식 전반에 적용되는 원칙으로 기록. `src/platform`(collision, engine, entity_component, geometry, logging, math, model_import, persistence, serialization)과 `src/graphics`(renderer, ui)에 이미 있는 클래스/인터페이스를 최대한 상속·재사용하고, 원본 WOT-master 코드를 새로 복제하지 않는다. 예: Transform/수학은 `platform/math`, 콜라이더는 `platform/collision`, 모델 로딩은 `platform/model_import`, Entity/Component는 `platform/entity_component`, 스냅샷 파이프라인은 `platform/engine`, 렌더링은 `graphics/renderer`를 상속·조합해서 구현 — 원본 `Objects/Basic`처럼 자체 Mesh/Material/Model 로딩을 새로 만들지 않는다.

- 이식 전반의 구현 원칙: `src/platform`/`src/graphics`에 이미 있는 클래스·인터페이스를 최대한 상속·재사용하고, 가능하면 그 함수를 상속받아 구현한다. 원본 WOT-master 코드(Objects/Basic의 자체 Mesh/Material/Model 로딩 등)를 그대로 복제하지 않는다. (사용자 확정)
