# Brainstorming: Component 패턴 기본 구조 구현

> Details 8(Unreal/Unity 구조 비교)에서 확정한 대로, "ECS"가 아니라 "Component 패턴"이라는 이름으로 정정했다.
> 이하 본문에서 "ECS"라는 표현이 남아있는 곳은 논의 당시 시점의 표현을 그대로 보존한 것이며(Q&A Log,
> Unity DOTS/Unreal Mass 같은 실제 데이터 지향 ECS 장르를 가리키는 경우 포함), 이 프로젝트가 최종적으로
> 채택한 아키텍처의 이름은 아니다.

## Details

### 1. Entity-owns-Component(OOP 컴포지션) vs 진짜 데이터 지향 ECS

사용자 초안(`IEntity`, `IComponent`를 두고 Entity가 Component를 저장·조회)은
문자 그대로 읽으면 **"Entity 객체가 Component 목록을 소유하는 컴포지션 패턴"** 이다.
이 구조 자체는 잘 알려진 유효한 패턴(Unity의 구 GameObject/MonoBehaviour 모델과 동일 계열)이지만,
게임 업계에서 "ECS"라는 용어가 가리키는 것은 보통 **데이터 지향 ECS**로, 다음과 같이 다르다.

| 구분 | Entity-owns-Component (초안 그대로) | 데이터 지향 ECS (EnTT/Unity DOTS/Bevy 계열) |
|---|---|---|
| Entity의 실체 | `IEntity`를 구현하는 객체, Component 컨테이너를 직접 소유 | 정수 ID 하나 (핸들). 저장소를 소유하지 않음 |
| Component 저장 위치 | 각 Entity 인스턴스 내부 | Entity와 분리된 중앙 Registry/World가 컴포넌트 타입별로 저장 |
| Component 접근 방식 | 가상 함수(`IComponent` 인터페이스) 호출 | 대부분 비가상 데이터 구조체, 타입별 연속 배열에서 직접 접근 |
| 캐시 지역성 / 순회 성능 | Entity마다 흩어진 힙 할당 + vtable 간접 호출 | 같은 타입 Component가 연속 메모리에 모여 있어 캐시 친화적 |
| 구현 난이도(1차 버전) | 낮음 — map 하나로 바로 동작 | 중간 — Registry, 타입별 저장소, Entity ID 발급/회수 로직 필요 |
| "ECS"라는 이름에 부합하는 정도 | 사실상 Component 패턴에 가까움 | 전형적인 ECS |

프로젝트 목적(포트폴리오, 실제 엔진에서 쓰이는 개념 학습)을 감안하면,
"ECS"라는 이름을 붙일 거라면 두 번째(데이터 지향) 쪽이 개념적으로 더 정확하고 배울 것이 많다.
다만 사용자 초안이 명시적으로 "Entity로부터 Component를 저장·조회"라고 표현했으므로,
이번 사이클에서 어느 쪽을 택할지는 사용자 결정이 필요한 지점이다 (Q&A Log 참고).

**제안:** 데이터 지향 방식을 택하더라도 `IEntity`라는 이름은 유지할 수 있다 —
다만 그 경우 `IEntity`는 "Component를 소유하는 존재"가 아니라
"Entity ID를 감싼 얇은 핸들 + 저장소(Registry) 참조" 형태가 된다.
반대로 진짜 컴포지션 패턴을 원한다면 `IEntity`가 Component 컨테이너를 직접 갖는 구조로 단순하게 간다.

### 2. Component 저장 방식 (두 방식 공통 하위 결정)

Component를 타입별로 구분해 저장/조회하려면 결국 "타입 → 저장소" 매핑이 필요하다. 후보:

- **`std::type_index` 기반 `map`** — `std::unordered_map<std::type_index, std::unique_ptr<IComponent>>`.
  구현이 가장 단순하고, 조회는 `GetComponent<T>()`처럼 템플릿으로 감싸면 사용자 입장에서 타입 안전.
  단점: Component 하나하나가 개별 힙 할당(`unique_ptr`) + 가상 소멸자 — 캐시 지역성 없음. 100~1000 단위 엔티티 규모에선 성능 문제 없음.
- **비트마스크 + 배열** — Component 타입마다 고정 인덱스를 부여하고 비트마스크로 보유 여부 판정.
  성능은 좋지만 "컴포넌트 타입 개수가 컴파일 타임에 고정되어야 함" 같은 제약이 생겨, 이후 컴포넌트가 계속 늘어날 이번 프로젝트 특성(탱크/투사체/AI 등)과 안 맞음.
- **Sparse Set (EnTT 방식)** — 타입별 sparse/dense 배열로 Entity ↔ Component를 매핑. 캐시 지역성과 순회 성능이 가장 좋음.
  다만 구현 난이도가 셋 중 가장 높고, "기본 형태"를 만드는 이번 범위에는 과함.

**제안:** 이번 사이클은 `type_index` 기반 map으로 간다.
저번 충돌 감지 사이클들처럼 "작게 시작해서 다음 사이클에서 발전"시키는 프로젝트 진행 방식과도 맞는다.
Sparse Set으로 교체하는 건 나중에 "ECS 성능 최적화" 같은 별도 사이클로 미룰 수 있다.

### 3. System 포함 여부

Task Purpose가 "Entity가 Component를 저장·조회 가능해야 하는 구조"까지로 명시되어 있어,
System(=매 프레임 특정 Component 조합을 순회하며 로직을 실행하는 주체)은 자연스러운 다음 단계이지 이번 범위는 아니라고 판단된다.

**제안:** 이번 사이클은 `IEntity`/`IComponent`/Entity의 저장·조회까지로 범위를 한정하고,
System은 "ECS 아키텍처 확장 — System" 같은 후속 사이클로 분리한다.
지금 System까지 욕심내면 Registry/World 설계가 System의 순회 방식(어떤 Component 조합을 순회할지)에 영향을 받으므로,
성급하게 두 개를 한 번에 설계하면 재작업 위험이 커진다.

### 4. 적용 대상

`src/app/main.cpp`를 확인한 결과 현재 프로젝트에는 게임 오브젝트/엔티티 개념이 아직 전혀 없다
(윈도우 생성 + 렌더러 초기화 정도만 존재). 즉 이번 ECS는 기존 무언가를 대체하는 리팩터링이 아니라
완전히 새로운 하부구조를 추가하는 작업이다. 향후 탱크/투사체 등 게임 오브젝트 사이클에서 이 ECS 위에 올라타게 될 것으로 예상된다.

**제안:** `src/entity_component/` 디렉터리에 독립 모듈로 둔다 (Details 8에서 "ECS"가 아니라 "Component 패턴"으로
정정하면서 디렉터리명도 이를 반영). 기존 `src/collision`, `src/geometry`처럼
다른 모듈에 의존하지 않는 순수 라이브러리 형태로 유지한다 (외부 라이브러리 의존 없음 — 래핑 원칙도 해당 없음).

### 5. 사용자 제안 설계 검토

사용자가 다음 4가지를 제안했다.

1. `IEntity`는 인터페이스이며 필수 요소만 가진다 (`entity_uuid`, `components`).
2. `IEntity`는 여러 개의 Component를 가지며, 저장 방식은 `unordered_map` 또는 `vector<Component>`.
3. `IEntity`와 `IComponent` 모두 반드시 `uuid`를 가진다.
4. `IEntity`와 `IComponent`를 관리하는 Manager가 하나 필요하다.

**동의하는 부분**

- (1) — Entity를 `entity_uuid` + `components` 정도의 최소 요소만 갖는 얇은 인터페이스로 두는 것은
  ISP(인터페이스 분리 원칙)에 부합한다. 이걸로 "1. Entity 모델" 질문은 (A) 컴포지션 패턴으로 결정된 것으로 본다.
- (4) — 생성/조회/파괴를 흩어놓지 않고 한 군데서 관리한다는 방향 자체는 맞다.
  다만 아래에서 "Manager를 하나로 합칠지, 둘로 나눌지"는 다르게 제안하고 싶다.

**이견/추가 논의가 필요한 부분**

**(A) Component 저장소 키 — "타입별 1개"인가 "같은 타입 여러 개 허용"인가**

이 질문이 (2)와 (3)을 실제로 갈라놓는 핵심 분기점이다.

- 한 Entity가 같은 타입의 Component를 **동시에 하나만** 가진다면 (예: `TransformComponent`, `HealthComponent`처럼 보통의 ECS 컴포넌트),
  키는 타입(`std::type_index`)이어야 조회(`GetComponent<T>()`)가 O(1)로 자연스럽다.
  이 경우 `IComponent`가 별도 `uuid`를 가질 이유가 약해진다 — (엔티티 uuid, 타입) 조합만으로 이미 유일하게 식별되기 때문이다.
- 반대로 한 Entity가 같은 타입의 Component를 **여러 개** 가질 수 있어야 한다면 (예: 상태이상/버프처럼 "같은 종류가 중첩"되는 경우),
  타입만으로는 서로 구별이 안 되므로 `uuid`가 키 역할을 해야 하고, 이 경우 (3)의 Component-uuid 요구가 필연적이다.
  다만 이 경우 "타입 T의 컴포넌트를 달라"는 흔한 조회가 선형 탐색이 되거나, 타입→uuid 목록의 보조 인덱스가 하나 더 필요해진다.

→ **질문:** 한 Entity가 같은 타입의 Component를 동시에 여러 개 가지는 케이스를 이번 "기본 형태"에 포함하고 싶은가?
포함한다면 `unordered_map<uuid, unique_ptr<IComponent>>` + 타입별 보조 인덱스,
포함하지 않는다면 `unordered_map<std::type_index, unique_ptr<IComponent>>` 하나로 충분하고 더 단순하다.
(`vector<Component>`는 두 경우 모두에서 저장 자체는 가능하지만 타입/uuid 조회가 항상 선형 탐색이 된다 — 조회 API를 자주 쓸 거라면 `unordered_map`을 권장.)

**(B) `IComponent`에 왜 `uuid`가 필요한가 — 구체적 사용처를 먼저 정하고 싶다**

"인터페이스는 원래 uuid를 가져야 한다"는 일관성 차원의 이유라면, 실제로 그 uuid를 쓸 곳(직렬화, 네트워크 동기화, 컴포넌트를 엔티티 밖에서 단독으로 참조하는 기능 등)이 아직 이번 범위엔 없다.
당장 안 쓴다면 지금 넣는 건 YAGNI(나중에 필요할 것 같아서 미리 넣는 설계)에 해당할 수 있다.
반대로 이미 염두에 둔 후속 기능(예: 저장/로드 시스템이 컴포넌트 단위로 참조를 저장해야 한다든지)이 있다면 지금 넣는 게 맞다.

→ **질문:** `IComponent.uuid`를 실제로 사용할 구체적인 시나리오가 있는가, 아니면 "혹시 몰라서"에 가까운가?

**(C) "uuid"가 정확히 무엇을 의미하는가**

코드베이스 전체를 확인했는데 UUID/GUID 생성 메커니즘이 아직 없다 (`docs/dependency/`에도 관련 라이브러리 없음). 두 가지 중 어느 쪽인지에 따라 작업 범위가 크게 달라진다.

- **진짜 UUID(RFC 4122, 128비트)** — Windows `CoCreateGuid` 같은 플랫폼 API를 쓰거나 외부 라이브러리를 도입해야 한다.
  후자라면 `agent_harness/CLAUDE.md`의 "외부 라이브러리는 반드시 내부 wrapper로 감싼다" 원칙에 따라 별도 `docs/dependency/` 평가와 wrapper 클래스가 필요해진다.
- **단순 유일 정수 ID** (예: 프로세스 내에서만 유일한 증가하는 `uint64_t` 카운터) — 별도 의존성 없이 몇 줄로 끝난다.
  실제로 EnTT 등 다수의 실전 ECS 구현체가 "entity handle"을 이런 정수(+ generation 비트)로 둔다. 저장/로드나 네트워크 동기화처럼
  "프로세스를 넘어서도 유일해야 하는" 요구가 없다면 이걸로 충분하다.

→ **질문:** 진짜 UUID가 필요한 구체적 이유(예: 세이브 파일 간 참조, 멀티플레이어 동기화)가 있는가,
아니면 "이름이 uuid일 뿐 실질은 프로세스 내 유일 ID"면 충분한가?

**(D) Manager를 하나로 합칠지, Entity/Component 책임을 나눠 둘로 쪼갤지**

Entity가 이미 자신의 Component를 직접 소유하는 구조(사용자 제안 (1)(2))라면,
"Component 하나하나의 생성/삭제"는 사실 Entity가 자신의 컨테이너를 통해 이미 하고 있는 일이다.
그런데 여기에 더해 `IComponent`를 관리하는 Manager를 따로 둔다면, 그 Manager의 실질적 역할은 아래 둘 중 하나일 것이다.

- Entity 생성/조회/파괴(=`EntityManager`)와, 여러 Entity에 걸친 Component 전역 조회/색인(=`ComponentManager`, 나중에 System이 "타입 T를 가진 모든 Entity"를 순회할 때 필요)을 각각 담당하는 **두 개의 클래스**로 분리한다.
- 하나의 `EcsManager`(가칭)로 합치되, 내부적으로는 여전히 두 책임(Entity 수명 관리 / Component 전역 색인)을 서로 다른 멤버·메서드 그룹으로 명확히 분리한다.

CLAUDE.md가 SRP를 특히 엄격히 요구하므로, 하나의 "Manager" 클래스가 "Entity 생성" + "Entity 파괴" + "uuid로 Entity 찾기" + "Component 타입별 전역 조회" 를 전부 떠안는 건 God Object가 될 위험이 있다.

→ **제안:** `EntityManager`(Entity 생성/파괴/uuid 조회 전담)와 `ComponentRegistry`(타입별 전역 Component 색인 전담, 이후 System이 쓸 조회 API 제공)로 **분리**하고 싶다.
동의하는지, 아니면 하나로 합치는 이유가 따로 있는지 궁금하다.

> **최종 결론(Q4 참고):** 실제 호출 패턴을 검토한 결과 "Entity를 모른 채 Component uuid만으로 전역 조회"하는 경우가
> 실제로 없다는 데 합의했다 — 모든 판단의 주체가 항상 Entity이므로, Entity를 먼저 거치지 않고 Component에
> 접근할 일이 없다. 따라서 `ComponentRegistry`는 이번 사이클에서 **만들지 않는다.**
> `EntityManager`(Entity 생성/파괴/uuid 조회) + `Entity`(자신의 Component 소유·생성·소멸) 구조만으로 충분.

### 6. Collider 다중 보유 — "상속 관계"가 아니라 "계층(부모-자식) 관계"

사용자가 "캐릭터 Entity가 팔/몸통/머리 각각의 Collider를 가져야 하고, 신체 부위별로 Entity를 나눠
Entity끼리 상속 관계로 둘지"를 물었다. 결론부터 말하면 **이건 상속(inheritance)으로 풀 문제가 아니다.**

- **상속(IS-A)**: `class 머리Entity : public 캐릭터Entity`처럼 "머리가 캐릭터의 한 종류"라는 뜻이 되어버려 의미가 맞지 않는다.
  C++ 클래스 상속은 여기서 쓸 도구가 아니다.
  머리/팔/몸통은 캐릭터의 부분(part-of)이지, 캐릭터의 종류(kind-of)가 아니다.
- **계층/부모-자식 관계(HAS-A, part-of)**: Unity의 `Transform.parent`, Unreal의 `USceneComponent` Attach,
  Godot의 Node Tree가 전부 이 방식이다. 부모 Entity(캐릭터)가 자식 Entity(머리/팔/몸통)들에 대한 참조를 갖고,
  자식은 부모 기준 상대 위치(로컬 Transform)를 갖는다. Entity 사이의 관계이지 클래스 상속이 아니다.

실제로 이 요구사항을 푸는 데는 두 가지 레벨의 해법이 있고, 어느 쪽이 필요한지는 "신체 부위가 캐릭터와
독립적으로 움직여야 하는가"에 달려있다.

| 구분 | (a) 한 Entity + Collider 여러 개 | (b) Entity 계층 구조(부모-자식) |
|---|---|---|
| 적합한 경우 | 신체 부위 Collider가 캐릭터의 단일 Transform을 기준으로 한 고정 오프셋일 때 (예: 히트박스가 애니메이션과 무관하게 대략적 위치로 고정) | 신체 부위가 캐릭터와 독립적으로 움직여야 할 때 (예: 스켈레톤 애니메이션에 따라 팔이 따로 움직이는 래그돌·본 충돌) |
| 구조 | 캐릭터 Entity 하나, `ColliderComponent`를 여러 개 부착 — 각 인스턴스가 "어디에 붙는지"(부착 소켓 이름 + 로컬 오프셋)를 데이터로 가짐 | 캐릭터 Entity(부모) + 머리/팔/몸통 Entity(자식) 각각 자신의 Transform + Collider 보유. 부모-자식 참조를 위한 별도 개념(예: `HierarchyComponent{ parent, children }`)이 필요 |
| 이번 사이클 범위 | 이번 "기본 형태"로 충분 — Component 다중 보유만 지원하면 됨 (아래 uuid 논의와 직결) | 계층 구조는 Entity와 Entity 사이의 새로운 관계 개념을 도입하는 것이라 사실상 별도 기능 — 이번 범위를 넘어선다 |

**제안:** 이번 사이클은 (a)로 간다 — 캐릭터는 Entity 하나, 신체 부위 Collider는 같은 타입(`ColliderComponent`)의
인스턴스를 여러 개 부착하는 것으로 해결한다. 각 Collider 인스턴스가 "어느 부위에 붙는지"는 Collider 자신의 데이터
필드(예: 부착 소켓 이름, 로컬 오프셋)로 표현하면 되고, 이를 위해서도 "같은 타입 Component를 여러 개 허용"하는
저장 구조(Details 5-(A) 참고)가 필요해진다 — 즉 사용자가 말한 멀티 Collider 요구가 그 자체로 uuid 키 방식을 뒷받침하는 근거가 된다.
신체 부위가 독립적으로 움직여야 하는 래그돌/스켈레톤 수준의 요구가 실제로 생기면, 그때 "ECS 계층 구조" 같은
후속 사이클로 부모-자식 Entity 관계를 별도로 설계하는 걸 제안한다.

→ **질문:** 이 방향(이번엔 한 Entity + Collider 여러 개, Entity 계층 구조는 후속 사이클)에 동의하는가?

### 7. 멀티스레드 접근 범위 — 지금 실제로 고려할 게 있는가

`src/app/main.cpp`를 확인한 결과 현재 프로젝트는 **완전히 단일 스레드**다 (창 메시지 펌프 → 렌더 프레임을
한 루프에서 순서대로 처리, 스레드 생성 코드 자체가 없음). 즉 지금 시점에는 ECS 저장소를 동시에 건드릴
두 번째 스레드가 아예 존재하지 않는다.

이 상태에서 "멀티스레드 접근 고려"가 실제로 의미 있게 할 수 있는 일은 둘로 나뉜다.

- **지금 해도 되는 것 (비용이 사실상 0에 가까움):** uuid 발급기(카운터)를 `std::atomic<uint64_t>`로 만드는 것.
  구현 난이도 차이가 없고, 나중에 실제로 여러 스레드에서 Entity/Component를 만들게 되어도 재작업이 필요 없다.
- **지금 하면 오히려 위험한 것:** `EntityManager`/`ComponentRegistry`의 컨테이너 변경(생성/삭제/추가) 자체에
  뮤텍스나 락-프리 구조를 미리 넣는 것. 아직 이걸 동시에 호출할 두 번째 스레드가 없어서
  "어떤 세분화(전체 락 vs Entity 단위 락 vs read-write lock)가 맞는지"를 검증할 방법이 없다.
  실제 소비자(예: System이 여러 스레드에서 병렬로 도는 미래 사이클, 또는 렌더 스레드가 Transform을 읽는 동안
  게임 로직 스레드가 쓰는 시나리오) 없이 지금 넣으면 잘못된 락 설계를 그대로 굳히거나, 테스트되지 않은
  코드가 방치될 위험이 크다 — CLAUDE.md의 "가상 요구사항에 대비한 설계 금지" 원칙과 정면으로 부딪힌다.

**제안:** uuid 발급만 원자적으로 만들고, `EntityManager`/`ComponentRegistry`는 이번 사이클에서 **단일 스레드 접근을 전제로 설계**한다
(주석의 Notes 항목에 "동시 접근 미지원, 단일 호출 스레드 가정"을 명시). 실제 동시 접근이 필요한 소비자가 생기는 시점
(가장 유력하게는 System 사이클)에 그때의 실제 접근 패턴을 보고 락 전략을 설계한다.

→ **질문:** 이 축소된 범위(uuid 발급만 atomic, 컨테이너 자체는 단일 스레드 가정 + 문서화)로 "멀티스레드 접근 고려"를 충족한 것으로 볼지 동의하는가?

### 8. Unreal / Unity 실제 구조와의 비교 검증

지금까지 확정한 설계(Entity가 Component를 직접 소유하는 컴포지션 패턴, `EntityManager` 단일 관리자,
같은 타입 Component 다중 보유 허용, 계층 구조는 후속 사이클로 분리)가 실제 상용 엔진의 구조와 비교했을 때
타당한지 짚어본다. 게임 엔진에는 사실 서로 다른 두 세대의 구조가 공존한다.

| 엔진 / 시스템 | Entity의 실체 | Component 소유 방식 | 같은 타입 다중 보유 | 계층(부모-자식) | 중앙 Registry |
|---|---|---|---|---|---|
| **Unity (Classic) GameObject/Component** | `GameObject` 클래스 (관리 객체, 내부 InstanceID 보유) | GameObject가 Component 리스트를 직접 소유 | **허용** (예: BoxCollider 여러 개를 한 GameObject에 부착 가능) | `Transform.parent`/`childCount`로 별도 관리 | 없음 — `GetComponent<T>()`는 항상 소유자 GameObject를 거쳐 조회 |
| **Unreal (Classic) AActor/UActorComponent** | `AActor` 클래스 (UObject 파생, 내부 고유 ID 보유) | Actor가 `OwnedComponents` 배열로 Component를 직접 소유 | **허용** (예: StaticMeshComponent 여러 개 부착 가능) | `RootComponent` + `SceneComponent` Attach 계층으로 별도 관리 | 없음 — `GetComponentByClass()`/`GetComponents<T>()`는 항상 소유자 Actor를 거쳐 조회 |
| **Unity DOTS (신형 ECS)** | `Entity` 구조체 = `{Index, Version}` (핸들일 뿐, 소유 없음) | `World`의 `EntityManager`가 타입별 연속 배열(Chunk)에 중앙 저장 | 기본적으로 **비허용** (타입당 1개, 다중 인스턴스는 별도 메커니즘인 DynamicBuffer로 처리) | 별도 컴포넌트(`Parent`, `Child` buffer)로 표현, ECS 밖 개념 아님 | 있음 — `EntityManager` 자체가 전역 저장소 |
| **Unreal Mass Entity (신형 ECS)** | `FMassEntityHandle` = `{Index, SerialNumber}` (핸들일 뿐) | `FMassEntityManager`가 Archetype Chunk에 중앙 저장 | 기본적으로 **비허용** (Fragment는 타입당 1개) | 별도 Fragment로 표현 | 있음 — `FMassEntityManager` 자체가 전역 저장소 |
| **이번 사이클 확정 설계** | `IEntity` 구현체 (uuid 보유) | Entity가 `unordered_map<uuid, unique_ptr<IComponent>>`로 직접 소유 | **허용** | 없음 (후속 사이클로 분리) | 없음 — 항상 Entity를 거쳐 조회 |

**검증 결과**

- 확정한 설계는 **Unity Classic(GameObject/Component)·Unreal Classic(Actor/ActorComponent)의 구조와 사실상 동일하다.**
  Entity가 Component를 직접 소유, 같은 타입 다중 보유 허용, 계층은 별도 개념으로 분리, 중앙 Registry 없이
  항상 소유자를 거쳐 조회 — 네 가지 특징이 모두 정확히 일치한다. 이는 두 상용 엔진에서 이미 수십 년간
  실전 검증된 패턴이므로, 확장성이나 설계 타당성 측면에서 위험이 낮다고 판단한다.
- 다만 이 패턴은 **Unity DOTS나 Unreal Mass Entity 같은 "요즘 말하는 데이터 지향 ECS"와는 다른 세대**다.
  데이터 지향 ECS는 Entity가 정수 핸들일 뿐이고 Component가 타입별 연속 배열에 중앙 저장되어,
  수만 단위 Entity를 매 프레임 순회해야 하는 대규모 시뮬레이션에서 캐시 지역성 이점이 크다.
  이 프로젝트(탱크 대전, 동시 활성 Entity가 수십~수백 단위로 추정)는 그 정도 규모가 아니므로
  데이터 지향 ECS의 이점이 절실하지 않고, 지금 확정한 구조로 충분하다고 본다.

**남은 것은 이름뿐이다.** "ECS"라는 이름은 업계에서 보통 데이터 지향 세대(Unity DOTS/Unreal Mass/EnTT)를
가리키는 데 더 자주 쓰이므로, 지금 만들 것은 정확히는 **"Component 패턴"**(Unity Classic/Unreal Classic과 동일 계열)에
더 가깝다. 포트폴리오 정확성을 고려하면 두 가지 선택지가 있다.

- **(가) 이름은 "ECS"로 유지하되, 코드/문서에 "Composition 기반 ECS(컴포지션 패턴)"라는 점을 명시** — 두 번째
  진화 단계인 데이터 지향 ECS로 나중에 발전시킬 수 있다는 여지를 남긴 이름이라고 설명 가능.
- **(나) 모듈/문서 이름을 "Component 패턴" 또는 "Entity-Component 아키텍처"로 명확히 하고, "ECS"라는 표현은
  실제 데이터 지향 구조를 만들 미래 사이클을 위해 아껴둔다.**

→ **질문:** (가)/(나) 중 어느 쪽으로 할지, 아니면 그냥 지금처럼 "ECS"로 부르고 넘어가도 괜찮다고 보는지?

> **최종 결론(Q5 참고):** 혼란을 줄이는 쪽이 낫다는 사용자 판단에 따라 (나)로 확정 — 문서/모듈 이름을
> "Component 패턴"(Entity-Component 아키텍처)으로 명확히 하고, "ECS"라는 표현은 실제 데이터 지향 구조를
> 만들 미래 사이클을 위해 아껴둔다. 이에 따라 이번 사이클의 task/brainstorming 문서 slug와 제목을
> `ECS_아키텍처_기본구조` → `Component_패턴_기본구조`로, `src/ecs/` → `src/entity_component/`로 정정했다.

## Trade-offs

| 결정 항목 | 선택지 A | 선택지 B | 비고 |
|---|---|---|---|
| Entity 모델 | Entity-owns-Component (컴포지션) | 데이터 지향 ECS (ID + Registry) | **확정: A.** 구현 쉽고 초안에 충실 |
| Component 저장 키 | `uuid` 기반 map + type_index 보조 인덱스 | `type_index` map 단독 | **확정: 좌측.** 같은 타입 Component 다중 보유(신체 부위별 Collider)를 지원해야 해서 uuid가 기본 키, 타입별 조회는 보조 인덱스로 해결 |
| Entity 간 관계 | 계층(부모-자식) 구조 도입 | 계층 없이 한 Entity + Component 다중 보유 | **확정: 우측(이번 사이클).** 신체 부위 독립 이동이 필요해지면 후속 사이클에서 계층 구조 별도 설계 |
| System 포함 여부 | 이번 사이클 포함 | 다음 사이클로 분리 | 포함 시 Registry 설계가 System 순회 방식에 종속되어 재작업 위험 |
| 아키텍처 명칭 | "ECS"로 유지 (Composition 기반임을 문서에 명시) | "Component 패턴"으로 정정 | **확정: 우측.** 실제 Unity/Unreal 구조 비교 결과 데이터 지향 ECS가 아닌 Component 패턴에 해당 — "ECS"는 실제 데이터 지향 구조를 만들 미래 사이클을 위해 아껴둔다 |

## Q&A Log

**Q1.** (사용자) IEntity는 인터페이스로 필수 요소만 가진다(entity_uuid, components), 저장은 unordered_map 또는 vector<Component>, IEntity/IComponent 모두 uuid를 가져야 한다, 관리하는 Manager가 하나 필요하다 — 이 설계에 대한 Claude의 의견은?
**A1.** (Claude) 전반적으로 동의하며 이걸로 "Entity 모델" 질문은 컴포지션 패턴(A)으로 확정. 다만 4가지를 더 짚었다 — (A) Component 저장소 키가 "타입 하나당 1개"인지 "같은 타입 여러 개 허용"인지에 따라 unordered_map의 키가 타입이어야 하는지 uuid여야 하는지가 갈린다, (B) IComponent.uuid의 구체적 사용처가 아직 불분명해 YAGNI 우려가 있다, (C) "uuid"가 진짜 128비트 UUID인지 프로세스 내 유일 정수 ID인지에 따라 외부 라이브러리 도입 여부(및 dependency 평가 필요 여부)가 갈린다, (D) Manager를 하나로 합치면 Entity 수명 관리 + Component 전역 색인이 한 클래스에 몰려 SRP 위반(God Object) 위험이 있어 EntityManager/ComponentRegistry로 분리하는 걸 제안. 상세는 Details 5번 참고.

**Q2.** (사용자) 캐릭터 Entity가 팔/몸통/머리 Collider를 각각 매칭해야 해서 같은 타입 Component를 여러 개 가질 필요가 있다 — 이때 신체 부위별로 Entity를 나눠 Entity끼리 "상속 관계"로 둘지 설명이 필요하다. Component uuid의 직접적 사용처는 없지만, Entity를 통해서만 Component를 생성·제거하고 Entity 소멸 시 Component도 자연 소멸한다면 uuid가 꼭 필요한지 의문이 들면서도, uuid로 복잡한 검사 로직을 대신할 가능성은 있다고 본다. uuid는 "구분 가능한 데이터"면 충분하고 name은 중복 위험이 있어 부적합하다고 본다. EntityManager는 SceneManager → Scene → Entity 계층에서 SceneManager가 대신하게 하면 오히려 SceneManager 쪽 SRP 위반이라고 본다.
**A2.** (Claude) ① 신체 부위 Collider 다중 보유는 "상속"이 아니라 "계층(부모-자식) 관계"로 풀 문제 — 상속(IS-A)은 "머리가 캐릭터의 한 종류"라는 뜻이 되어 의미가 안 맞고, Unity Transform.parent류의 부모-자식 Entity 관계(HAS-A/part-of)가 맞는 도구다. 다만 신체 부위가 캐릭터와 독립적으로 움직여야 하는 게 아니라면 계층 구조 자체가 필요 없고, 한 Entity에 Collider Component를 여러 개(부착 소켓/오프셋을 각 Collider의 데이터로) 붙이는 것으로 충분 — 계층 구조는 래그돌 등 실제 필요가 생겼을 때 별도 사이클로 미루자고 제안(Details 6). ② "같은 타입 Component 여러 개 허용" 요구가 확정되었으므로 Component 저장 키는 자연스럽게 uuid로 결정 — Component 자체의 안정적 식별자가 있어야 "이 Collider 인스턴스"를 가리킬 수 있다. ③ uuid는 진짜 UUID가 아니라 프로세스 내 유일 식별자면 충분하다는 데 동의 — 외부 라이브러리 불필요, 원자적 카운터로 구현. ④ EntityManager를 Scene 계층에 흡수시키지 않는다는 방향에 동의 — EntityManager는 이번 사이클에서 Scene 개념과 무관하게 독립적으로 두고, Scene/SceneManager는 이후 별도 사이클의 관심사로 남긴다.

**Q3.** (사용자) Details 6 방향에는 동의. `IComponent.uuid`의 용도는 "특정 Entity의 특정 Component가 시야에 들어왔을 때 그 Component를 추적해야 하는 경우" — id 없이는 여러 if문으로 어떤 Component인지 조사해야 하니, id로 그 검사 로직을 대신한다는 뜻. 멀티스레드는 범위에 고려해달라, 다만 지금 시점에 실제로 고려할 게 있는지 되물음.
**A3.** (Claude) uuid 용도는 "외부 시스템(추적/인식 시스템 등)이 특정 Component 인스턴스를 직접 가리키는 안정적 핸들"로 확인 — `ComponentRegistry`가 uuid로 O(1) 직접 조회(`Get(ComponentId) -> IComponent*`)를 제공하는 API가 필요하다는 뜻이므로 설계에 반영. 멀티스레드는 `main.cpp` 확인 결과 프로젝트 전체가 완전 단일 스레드라 지금 시점엔 실제 동시 접근 소비자가 없음 — uuid 발급 카운터만 `std::atomic`으로 만드는 건 비용이 없어 지금 하고, EntityManager/ComponentRegistry 컨테이너 자체의 락 전략은 실제 동시 접근 소비자(가장 유력하게는 System 사이클)가 생겼을 때 그 접근 패턴을 보고 설계하자고 제안(Details 7) — 지금 락을 미리 넣으면 검증 없이 세분화를 확정하는 위험이 있다.

**Q4.** (사용자) 멀티스레드는 제안대로 진행. 추가로 "ComponentRegistry가 없다면 uuid로 Component를 찾을 때 EntityManager → Entity → Component 순으로 탐색하는 게 맞는지" 확인 요청 — 이후 "그 시나리오는 그냥 예시였고, 일반적으로는 모든 판단의 주체가 항상 Entity이므로 지금 구조(EntityManager + Entity)로 충분하다"고 정리.
**A4.** (Claude) 탐색 경로 자체(EntityManager가 모든 Entity를 순회 → 각 Entity 내부에서 uuid로 O(1) 조회)는 맞다고 확인했고, 이 경로의 비용이 Entity 개수에 비례한다는 점, 그리고 이게 Q2에서 uuid를 두려던 이유("추적 시 조건문 나열 방지")를 사실상 무력화한다는 점을 짚어 `ComponentRegistry` 유지를 재차 권했다. 다만 사용자가 "Component uuid로 전역 조회하는 시나리오 자체가 실제로는 없고, 모든 접근은 항상 Entity를 먼저 거친다"고 확정하면서 이 우려가 해소됨 — 실제로 없는 호출 패턴을 위해 인덱스를 미리 만드는 건 YAGNI이므로 동의. **`ComponentRegistry`는 만들지 않고, `EntityManager` + `Entity`(자신의 Component 소유) 구조로 확정.**

**Q5.** (사용자) 혼란은 줄이는 게 좋으니, 확정된 설계가 Component 패턴에 가깝다면 문서도 "Component 패턴"으로 정정해달라고 요청.
**A5.** (Claude) Details 8의 (나)안대로 정정 — task/brainstorming 문서의 제목과 파일 slug를 `ECS_아키텍처_기본구조` → `Component_패턴_기본구조`로 변경(`docs/task/Component_패턴_기본구조_20260722_2211.md`, `docs/brainstorming/Component_패턴_기본구조_20260722_2217.md`, 아직 커밋되지 않은 상태라 히스토리 손실 없이 바로 변경), 향후 소스 위치도 `src/ecs/` 대신 `src/entity_component/`로 확정(Details 4 갱신). 문서 본문 중 "ECS"라는 표현이 남아있는 곳은 논의 당시 시점의 기록이거나 Unity DOTS/Unreal Mass 같은 실제 데이터 지향 ECS 장르를 가리키는 경우이며, 이 프로젝트가 채택한 이름이 아님을 문서 서두에 명시했다.

## Summary & Open Questions (사용자 결정 필요)

**최종 확정된 방향 — 열린 질문 없음, Step 3(전략 문서)로 진행 가능**

- Entity 모델: (A) 컴포지션 패턴 — `IEntity`가 `entity_uuid`와 Component 컨테이너를 직접 소유.
- 한 Entity가 같은 타입 Component를 여러 개 가질 수 있다 (예: 신체 부위별 Collider).
- Component 저장 키: `uuid` (Component 자체의 식별자).
  타입별 조회(`GetComponent<T>()`/`GetComponents<T>()`)를 위한 보조 인덱스(`type_index` → uuid 목록)를 Entity 내부에 함께 둔다.
- `IComponent.uuid`의 용도: 일반적으로는 항상 Entity를 먼저 거쳐 접근하므로 전역 조회용은 아니고,
  Entity 내부에서 특정 Component 인스턴스를 다른 것과 구분·재확인하기 위한 안정적 식별자.
- `uuid`(Entity/Component 공통)는 RFC 4122 진짜 UUID가 아니라 **프로세스 내 유일 식별자**로 충분 —
  외부 라이브러리 없이 원자적 카운터(`std::atomic<uint64_t>`)로 발급. dependency 평가 불필요.
- 신체 부위별 다중 Collider는 "Entity 계층(부모-자식) 구조"가 아니라 "한 Entity + Collider Component 다중 보유"로 해결.
  Entity 사이의 부모-자식 계층 구조는 실제 필요(래그돌 등)가 생기면 별도 후속 사이클로 분리.
- System: 이번 범위에서 제외, 후속 사이클로 분리.
- 아키텍처 명칭: "ECS"가 아니라 **"Component 패턴"**으로 확정 (Unity Classic/Unreal Classic 구조와 동일 계열,
  Unity DOTS/Unreal Mass 같은 데이터 지향 ECS와는 다른 세대 — Details 8 참고).
- 위치: `src/entity_component/` 독립 모듈, 외부 의존성 없음, 다른 모듈이 이 모듈에 의존하지 않아도 동작.
- Manager: **`EntityManager`만 둔다** (Entity 생성/파괴/uuid 조회 전담).
  `ComponentRegistry`(전역 Component 색인)는 만들지 않음 — Component uuid 전역 조회는 실제 호출 패턴에 없고
  모든 접근이 항상 Entity를 먼저 거치므로, 지금 만들면 YAGNI에 해당. Component 생성/소멸은 Entity가 전담.
  Scene/SceneManager 개념에는 흡수시키지 않고 이번 사이클에서 독립적으로 유지.
- 멀티스레드: uuid 발급 카운터만 `std::atomic`으로 처리. `EntityManager`/`Entity`의 생성·삭제·추가 자체는
  이번 사이클에서 단일 스레드 접근을 전제로 설계하고 그 사실을 주석(Notes)에 명시 — 실제 동시 접근 소비자가
  생기는 시점(가장 유력하게는 System 사이클)에 그때의 접근 패턴을 보고 락 전략을 설계한다.
