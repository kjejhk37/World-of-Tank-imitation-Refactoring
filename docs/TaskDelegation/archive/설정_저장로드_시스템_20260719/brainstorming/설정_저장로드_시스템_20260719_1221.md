# Brainstorming: Config 및 Save/Load 시스템 초안

## Details

### 1. 기존 코드와의 관계 — `LaunchConfig`

`src/config/LaunchConfig.h`, `LaunchConfigParser`, `LaunchConfigStore`가 이미 존재함 (`렌더러_분기` 사이클 산출물).

- 현재 역할: argv 파싱 결과(현재는 렌더러 백엔드 하나)를 담는 불변 값 모음.
- 이번 Task의 "Config"(：json/DB에서 읽어 여러 설정을 세팅)와 성격이 겹침 — 둘 다 "main 시작 시점의 설정값"을 다룸.
- 제안: `LaunchConfig`를 없애지 않고, 계층을 분리한다.
  - **파일 기반 Config**(신규, 이번 Task) — `.json`에서 기본값을 읽음. 해상도, 창 모드, 볼륨, 렌더러 백엔드 기본값 등.
  - **argv(LaunchConfig, 기존)** — 파일 기반 Config 위에 덮어쓰는 override 계층. 예: `--renderer=opengl`이 있으면 json의 renderer 값보다 우선.
  - 우선순위: `기본값(코드 내 하드코딩) → JSON Config 파일 → argv 순으로 override`.

### 2. 전체 아키텍처 제안

현재 `src/` 하위가 `main.cpp` / `renderer/` / `config/` 정도로만 나뉘어 있음.
이번 사이클에서 "영속 데이터 입출력"이라는 공통 관심사를 담을 계층을 신설 제안.

```
src/
  core/            # 엔진 공통 (수학, 유틸 등 - 기존/향후)
  renderer/         # 기존 유지
  config/           # 기존 LaunchConfig + 신규 파일 기반 ConfigManager
  persistence/      # 신규 - Save/Load 시스템
  serialization/    # 신규 - 데이터 저장소 인터페이스 + 구현체 (config/persistence 공용)
  app/              # main.cpp 및 조립(composition root)
```

**데이터 저장소 추상화 (신규 결정 사항)**

Config·Save/Load 모두 향후 JSON ↔ DB 전환 가능성을 열어두기 위해, 저장소를 인터페이스 뒤에 둔다.

- `IDataStore` (가칭) — Config/Save-Load가 실제로 의존하는 인터페이스. `ConfigManager`/`SaveLoadManager`는 이 인터페이스만 알고, 구현체(JSON인지 DB인지)는 모른다.
- `JsonDataStore` — 이번 사이클에서 실제로 구현·동작하는 구현체. `nlohmann::json` wrapper(`JsonFileIO`) 기반.
- `SqliteDataStore` — **스텁만 마련.** 클래스 골격(헤더, 생성자, 인터페이스 메서드 시그니처)만 만들고 내부는 미구현 상태로 둔다. 후보 엔진으로 SQLite를 선정한 이유: 서버 불필요, 파일 하나로 배포 가능한 임베디드 DB라 로컬 싱글플레이 게임 구조와 잘 맞음. 실제 구현·`nlohmann::json`과 동일한 수준의 `dependency_eval`은 실제로 DB 전환이 필요해지는 시점의 별도 Task에서 진행.

- `serialization/`을 `config`와 `persistence`의 공용 하위 계층으로 분리하는 이유: 사용자가 제시한 "Config가 Save/Load에 녹아들 수 있지 않을까"라는 의견을 반영하되, SRP를 지키기 위한 절충안임.
  - Config와 Save/Load는 **읽고 쓰는 대상(설정값 vs 게임 진행 데이터)과 시점(시작 시 1회 vs 게임 중 수시)이 달라 책임을 합치면 안 됨** → 별도 클래스(`ConfigManager`, `SaveLoadManager`) 유지.
  - 다만 "JSON 파일을 열고, 파싱하고, 쓰는" 저수준 동작은 완전히 동일 → 이 부분만 `JsonFileIO` 같은 공용 wrapper로 공유.

### 3. Config 시스템 설계 초안

- 외부 라이브러리 후보: `nlohmann::json` (header-only, CMake `FetchContent`로 통합 가능 — `googletest` 도입 때와 동일 패턴).
- CLAUDE.md 원칙("외부 라이브러리는 반드시 내부 wrapper로 감싼다")을 그대로 적용 — `nlohmann::json`을 직접 참조하는 코드는 `JsonDataStore` 안에만 존재.
- `ConfigManager`는 `IDataStore`(구체적으로는 `JsonDataStore` 인스턴스)를 통해 값을 읽고, 타입-세이프한 접근자(`GetInt`, `GetString` 등 또는 구조체 역직렬화)를 상위 모듈에 제공. `ConfigManager`는 `IDataStore` 인터페이스만 알고 JSON인지 SQLite인지는 모른다.
- 로딩 시점: `main()` 시작 직후, 렌더러/윈도우 생성 이전 (기존 `LaunchConfig` 적용 시점과 동일한 위치).

### 4. Save/Load 시스템 설계 초안

- `SaveLoadManager`(가칭) — `IDataStore`를 통해 게임 진행 데이터를 직렬화/역직렬화 (Config와 동일하게 구현체를 직접 알지 못함).
- 저장 대상 객체는 `ISaveable` 같은 인터페이스(`ToJson()`/`FromJson()` 또는 이에 준하는 메서드)를 구현 — `SaveLoadManager`는 각 객체의 내부 데이터 구조를 몰라도 됨 (의존성 역전).
- 저장 데이터에 버전 필드(`saveVersion`)를 포함 — 이후 데이터 구조가 바뀌어도 이전 세이브 파일과의 호환성 처리 지점을 마련.
- 저장 포맷: 1차로 Config와 동일하게 `JsonDataStore` 채택 (가독성/디버깅 용이, 공용 구현체 재사용).

### 5. 저장 범위 — 아직 미확정 (Open Question)

"main이 실행되는 것에 대한 저장/로드"라는 요구가 아래 두 가지 중 어느 쪽인지에 따라 설계가 크게 달라짐.

- (A) 메타 진행 정보만: 해금된 탱크, 재화, 통계 등 — 매치 종료 후 갱신.
- (B) 인게임 미드매치 상태까지: 현재 맵, 탱크 위치/체력, AI 상태 등 — 훨씬 큰 범위, 엔티티 시스템이 어느 정도 갖춰져야 실질적으로 구현 가능.

현재 프로젝트에는 아직 게임 엔티티/월드 시스템이 없으므로, (B)는 지금 시점에 설계만 해두고 실제 구현은 엔티티 시스템이 생긴 이후로 미뤄야 할 가능성이 큼.

### 6. 멀티스레딩 적용 여부 — 확정

CLAUDE.md 리팩토링 범위에 "현재 싱글스레드 설계에 멀티스레딩 적용"이 포함됨.
Save 동작(특히 (B) 범위라면 큰 데이터)은 파일 I/O로 프레임 드랍을 유발할 수 있어 비동기 저장의 후보.

- 이번 사이클 범위: **인터페이스만** 마련. `SaveLoadManager`에 `SaveAsync(...)`(가칭) 같은 확장 지점을 시그니처로 열어두되, 내부 구현은 동기 처리로 두거나 미구현 상태로 둔다.
- 실제 스레드 구현(`std::thread`/`std::async`/자체 ThreadPool 선택 등)은 다음 Task로 완전히 분리.

## Trade-offs

| 항목 | 선택 | 장점 | 단점/리스크 |
|---|---|---|---|
| Config 데이터 소스 | JSON (`JsonDataStore`), DB는 `IDataStore` 뒤에 스텁만 | 당장은 별도 DB 엔진 불필요, 사람이 직접 읽고 수정 가능, 추후 DB 전환 시 `ConfigManager`/`SaveLoadManager` 코드는 변경 없음 | 인터페이스 계층이 하나 늘어나 초기 구조 파악 비용 증가 |
| DB 스텁 엔진 | SQLite 후보로 선정, 실제 구현은 보류 | 임베디드·서버 불필요라 로컬 게임과 궁합 좋음, 지금 결정해두면 이후 전환 시 설계 재작업 최소화 | 실제 붙일 때 SQLite C API 또는 래퍼 라이브러리에 대한 `dependency_eval` 별도 필요 |
| Config/Save-Load 공용 `serialization/` 계층 | 저수준 저장소 구현체(`JsonDataStore`/`SqliteDataStore`)만 공유, 매니저는 분리 | SRP 유지하면서 중복 제거 | 계층이 하나 더 늘어나 초기 구조 파악 비용 증가 |
| Save 데이터 범위 | 우선 (A) 메타 진행 정보만 설계, (B)는 인터페이스만 열어둠 | 현재 엔티티 시스템 부재 상태와 합치, 과설계 방지 | 추후 (B) 확장 시 인터페이스 재설계 필요할 수 있음 |
| 비동기 I/O | 이번 사이클은 인터페이스(시그니처)만, 실제 스레드 구현은 다음 Task | 스코프 과다 확장 방지, 스레드 안전성 검증을 이번 Task와 분리 | 인터페이스가 실제 구현 제약을 완전히 예측하지 못해 다음 Task에서 시그니처가 조정될 수 있음 |
| 외부 라이브러리 | `nlohmann::json` + wrapper | 표준적 선택, header-only로 빌드 간단, `FetchContent` 기존 패턴 재사용 | 정식 `dependency_eval` 절차 필요 (아직 미실시) |
