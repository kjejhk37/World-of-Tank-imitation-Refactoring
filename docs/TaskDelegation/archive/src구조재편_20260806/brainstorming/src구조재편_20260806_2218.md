# Brainstorming: src 구조 재편 (app → projects, platform/graphics 분리)

## Details

### 1. app → projects 이름 변경
- `src/app`에는 `main.cpp` 한 개뿐. `CMakeLists.txt`의 `add_executable(main src/app/main.cpp)` (L198) 한 줄만 경로를 바꾸면 되는 단순 rename — 리스크 낮음.
- `main.cpp` 내부는 `"platform/Win32Window.h"`, `"renderer/RendererFactory.h"` 등 절대 경로 include라 `app` 자체를 참조하는 코드는 없음 → 다른 파일에 파급 없음.

### 2. 기존 src/platform과의 명칭 충돌 여부
- 현재 `src/platform`에는 이미 `Win32Window.h/.cpp`가 존재.
- 확인 결과 충돌이 아님 — Win32Window는 OS 창 생성을 감싼 최소 단위 재사용 컴포넌트로, 사용자가 정의한 새 `platform/` 개념("최소 단위 기능을 모은 검증된 라이브러리")에 그대로 부합함. 이름을 바꿀 필요 없이 새 `platform/` 폴더에 자연스럽게 편입됨.

### 3. platform/ 이동 후보 — 의존성 검증
`src` 전체에서 `renderer/`, `ui/`, `config/`, `app/`를 include하는 파일을 grep한 결과, 아래 폴더들은 전혀 걸리지 않음(즉 그래픽스·프로젝트 계층에 대한 의존이 없는 순수 계층):
- `collision/**`, `entity_component/**`, `math/**`, `geometry/**`, `logging/**`
- `engine/**` (`DoubleBufferPublisher`, `IFrameDataPublisher`, `InstanceSnapshot`, `InstanceUpdateWorker`) — 서로만 include, 외부 의존 없음
- `serialization/**`, `persistence/**` — 요구사항 2 예시엔 없었지만 검증 결과 동일하게 깨끗함
- `platform/Win32Window` (기존 위치 그대로 편입)

→ 위 폴더들은 `platform/`으로 이동해도 안전.

- `model_import/**` (OBJ/FBX/GLTF 로더)도 renderer/config 의존은 없음. → (결정) `platform/`으로 확정. 아래 5번에서 확인했듯 graphics가 model_import의 Model/Mesh 타입을 직접 소비하므로, "데이터 타입은 platform에서 한 번만 정의" 원칙에 부합.

### 4. config/ — platform 후보에서 제외 권장
- `AppConfig.h`, `LaunchConfig.h`가 `"renderer/RendererBackend.h"`를 include.
- `ConfigManager.cpp`, `LaunchConfigParser.cpp`가 `"renderer/RendererBackendParser.h"`를 include.
- 즉 config 서브시스템 전체가 "renderer 종류"라는 프로젝트 스키마 필드 하나 때문에 그래픽스 계층과 얽혀 있음.
- 이 상태로 `platform/`에 넣으면 `platform → graphics` 역방향 의존이 생겨, 분리 목적(플랫폼은 그래픽스를 몰라야 함) 자체가 깨짐.
- 이번 사이클에서는 `config/`를 `projects/` 아래 유지하는 것을 권장. (범용 DataRecord 기반 config 코어를 platform에 두고, 프로젝트가 스키마만 주입하는 방식으로 재설계하는 건 더 큰 작업이라 별도 사이클로 분리하는 게 낫다고 봄.)

### 5. renderer/ + ui/ → graphics/ 분리 타당성 검증
- `renderer/**`(directx9/11/12, opengl 포함)와 `ui/**`(ImGuiManagerDX9/11/12)는 `math/`, `logging/`, `platform/`을 include — 즉 그래픽스가 플랫폼에 의존하는 방향은 이미 성립.
- 반대 방향(collision/math/entity_component 등이 renderer/ui/config를 참조)은 위 3번 grep에서 전혀 나오지 않음 → 의존 방향이 한쪽으로만 흐르고 있어, 요청하신 platform/graphics 분리는 구조적으로 타당함.
- 다만 순환 의존 1건 발견: `renderer/RendererFactory.h`가 `"config/LaunchConfig.h"`를 include하는데, `config/LaunchConfig.h`는 다시 `"renderer/RendererBackend.h"`를 include함. 지금은 전부 하나의 `app_lib` 타겟이라 문제없이 컴파일되지만, graphics를 별도 폴더(나중엔 submodule)로 분리하면 "그래픽스가 프로젝트 설정 타입을 알아야 하는" 역방향 의존이 그대로 두 폴더 경계를 가로질러 남게 됨.
- (결정) `RendererFactory::Create(const LaunchConfig&)` → `RendererFactory::Create(RendererBackend)`로 인자를 좁혀서, graphics는 자신이 정의한 `RendererBackend` enum만 노출/소비하게 하고, `LaunchConfig`에서 그 필드를 꺼내 넘기는 책임은 호출부(projects/main.cpp)가 지도록 변경. 이번 스코프에 포함하기로 확정 — platform→graphics→projects 레이어링 원칙상 graphics가 projects의 config 타입을 알아서는 안 되기 때문.

### 6. "submodule화"까지는 이번 Requirements보다 큰 스코프
- Requirements 1·2는 "레포 내부 폴더 재배치"이고, 최종 목표는 platform/graphics가 실제 **별도 git 저장소(submodule)**가 되는 것 — 크기가 다른 두 단계의 작업.
- Phase A (이번 사이클 후보): 폴더 재배치 + (그래픽스 분리를 포함한다면) `app_lib` 하나였던 CMake 타겟을 `platform_lib` / `graphics_lib` / `app_lib`(projects)로 쪼개, 폴더 관례가 아니라 빌드 시스템이 경계를 강제하게 함.
- Phase B (다음 사이클 후보): Phase A의 타겟 경계가 실제로 안정적으로 컴파일되는 걸 확인한 뒤, `platform`/`graphics`를 별도 저장소로 추출하고 `agent_harness`와 같은 방식으로 `.gitmodules`에 등록.
- 경계가 검증되기 전에 git history까지 뽑아버리면(Phase B를 먼저/동시에 하면), 5번에서 발견한 순환 의존 같은 문제가 새 저장소의 "공개 API" 안에 그대로 박제될 위험이 있음 — Phase A 없이 바로 Phase B로 가는 건 권장하지 않음.

## Trade-offs

**Phase A만 이번 사이클에 진행 (폴더 재배치 + CMake 타겟 분리, submodule 추출은 안 함)**
- 장점: 변경 범위가 작고 되돌리기 쉬움. 타겟을 실제로 분리해봄으로써 "경계가 정말 깨끗한지"를 컴파일러로 검증한 뒤 submodule 추출 여부를 판단할 수 있음.
- 단점: 아직 다른 레포에서 재사용은 불가능(진짜 재사용성은 Phase B부터) — 최종 목표엔 한 사이클 못 미침.

**Phase A + Phase B를 이번에 한 번에 진행**
- 장점: 최종 목표 상태에 한 번에 도달.
- 단점: 5번에서 발견한 순환 의존을 풀지 않은 채로 history를 추출하면 위험이 큼. 되돌리기도 더 어려움(별도 레포+서브모듈 설정까지 얽힘).

**config/를 그대로 platform/에 포함 (비권장)**
- 단점: `platform → graphics` 역방향 의존이 생겨 분리 취지 자체가 무너짐.

**RendererFactory 시그니처를 이번에 같이 수정 vs 다음으로 미룸**
- 지금 고침: 확인된 유일한 순환 의존을 폴더 분리 전에 제거 — graphics를 진짜로 독립시키려면 결국 필요한 작업.
- 미룸: 이번 요청 스코프(폴더명 정리)를 순수하게 유지할 수 있지만, graphics/ 분리를 이번에 같이 한다면 문제를 폴더 경계 너머로 그대로 옮기는 셈이라 실익이 적음.

## Q&A Log

**Q (태스크 원문, 확인 요청 사항):** DirectX, OpenGL과 같이 최소 단위 기능이 아닌 엔진 내 그래픽스적인 부분을 따로 모아 platform화(즉 `graphics/`로 분리)하는 것이 타당한가?
**A:** 타당함. `renderer/`, `ui/`는 `math/`, `logging/`, `platform/`(Win32Window)에 의존하지만 반대 방향(collision/math/entity_component 등이 renderer/ui/config를 참조)은 전혀 없음을 grep으로 확인함 — 의존이 한 방향으로만 흐르고 있어 분리가 구조적으로 자연스러움. 다만 `RendererFactory.h` ↔ `config/LaunchConfig.h` 사이에 순환 의존 1건이 있어, 분리를 이번에 진행한다면 `RendererFactory::Create`의 인자를 `LaunchConfig` 대신 `RendererBackend`로 좁히는 작업이 함께 필요함.

**Q (사용자, 결정 사항 회신):** ui는 renderer와 함께 graphics에 포함해야 하는가?
**A (사용자):** 그렇다. platform은 "검증된 추상화된 기능의 집합"이므로, UI의 기본형은 graphics 쪽에 있어야 한다. UI는 graphics에 의존적이기 때문.

**Q (사용자, 결정 사항 회신):** RendererFactory 시그니처 변경도 이번 스코프에 포함하는가?
**A (사용자):** 포함한다. 레이어링 원칙은 platform이 최상위(가장 기초) 데이터 정의 및 기능, graphics는 platform을 사용해 정의, projects는 platform과 graphics를 모두 사용하는 최하위 단. 이는 MeshData 등을 계층마다 다시 정의해서 발생하는 데이터 타입 변환 이슈를 막기 위함이다.
**(Claude 확인)** 이 원칙은 실제 코드로도 뒷받침됨 — `DirectX9/11/12Renderer.cpp`가 모두 `model_import/`의 타입(Model/Mesh 등)을 직접 include해서 쓰고 있음을 grep으로 확인. graphics가 platform이 정의한 데이터 타입을 그대로 재사용하고 있는 기존 패턴과 일치.

**Q (사용자, 결정 사항 회신):** model_import는 platform/projects 중 어디로?
**A (사용자):** platform. 위 레이어링 원칙(데이터 타입은 platform에서 한 번만 정의)이 전제라면 model_import가 만들어내는 Model/Mesh 데이터도 platform 소속이 맞다.

**Q (사용자, 결정 사항 회신):** git submodule 추출(Phase B)도 이번에 같이 하는가?
**A (사용자):** 아니다, 다음 단계로 미뤄도 된다. 다만 이번 Phase A에서 폴더를 "정확하게" 나누는 것이 중요하다 — submodule 추출 이후에는 Claude를 WOT/Graphics/Platform 3곳에서 각각 호출해 독립적으로 기능을 개발·최신화할 계획이기 때문에, 지금 경계를 흐릿하게 나누면 이후 3개 레포로 쪼갤 때 그대로 문제가 된다.

**Q (사용자, 결정 사항 회신):** `src/projects` 하위에 `main.cpp`만 둘지, `src/projects/WOT/main.cpp`처럼 한 단계 더 둘지?
**A (사용자):** `main.cpp`만으로 충분하다. 레포 자체가 이미 프로젝트 단위로 나뉘어 있으므로, 이 레포는 WOT 전용으로 유지한다. 만약 나중에 진짜 여러 프로젝트를 한 레포에서 관리할 필요가 생기면, projects만 따로 떼어 브랜치로 관리하는 방법도 있지만 비효율적이라 아마 레포당 프로젝트 하나 원칙을 유지할 것으로 예상.

## Summary & Open Questions (사용자 결정 필요)

**확정된 결론**
- `app → projects` 이름 변경은 단순 rename + CMakeLists 한 줄 수정, 리스크 낮음. `src/projects/main.cpp`로 flat하게 유지(하위 프로젝트 폴더 없음).
- 기존 `src/platform/Win32Window`는 새 `platform/` 개념과 충돌 없이 그대로 편입.
- `collision/`, `entity_component/`, `math/`, `geometry/`, `logging/`, `engine/`, `serialization/`, `persistence/`는 renderer/ui/config에 대한 의존이 전혀 없음(grep 검증 완료) → `platform/` 이동 확정.
- `model_import/`도 `platform/`으로 확정 — graphics(DirectX9/11/12Renderer)가 이미 model_import의 데이터 타입을 직접 소비하고 있어, "데이터 타입은 platform에서 한 번만 정의" 원칙에 부합.
- `config/`는 `renderer/RendererBackend`에 의존하고 있어 `platform/`으로 옮기면 역방향 의존이 생김 → 이번 사이클에서는 `projects/` 아래 유지.
- `graphics/` = `renderer/` + `ui/` 확정. UI는 그래픽스에 의존적이므로 platform이 아닌 graphics 소속.
- 레이어링 원칙 확정: **platform(최상위 기초 데이터/기능) → graphics(platform 사용) → projects(platform+graphics 모두 사용)**. 각 레이어는 데이터 타입을 재정의하지 않고 하위 레이어의 타입을 그대로 재사용한다.
- 이 원칙에 따라 `RendererFactory::Create(const LaunchConfig&)` → `RendererFactory::Create(RendererBackend)` 시그니처 변경을 이번 스코프에 포함 — graphics가 projects의 config 타입을 몰라야 하므로.
- git submodule 실제 추출(Phase B)은 다음 사이클로 이연. 단, 이번 Phase A(폴더 재배치 + CMake 타겟 분리)에서 경계를 정확히 긋는 것이 중요 — 추후 Claude를 WOT/Graphics/Platform 3개 레포에서 독립적으로 호출해 각자 개발할 계획이기 때문.
