# Strategy: src 구조 재편 (app → projects, platform/graphics 분리)

## 계층 정의 (platform / graphics / projects)

브레인스토밍 이후 engine/renderer 경계를 검토하며 정리된, 앞으로의 파일 배치 판단 기준.

**핵심 질문 — "이 타입/기능의 모양(shape)을 누가 결정하는가?"**

| 답 | 소속 |
|---|---|
| 누구든 재사용 가능한 일반 원칙 (수학, 알고리즘, 동시성 메커니즘, 파일 포맷) | **platform** |
| 특정 그래픽스 API/렌더링 파이프라인의 계약(인터페이스, 그 인터페이스가 주고받는 데이터 모양) | **graphics** |
| 이 프로젝트(WOT)의 콘텐츠·규칙·의사결정 | **projects** |

**platform** — 검증된, 완전히 추상화된 최소 단위 기능/데이터 라이브러리.
- graphics/projects 둘 다 몰라야 한다 (어떤 헤더도 include하지 않는다). `platform_lib`는 어떤 상위 타겟도 링크하지 않는 것으로 강제한다.
- 데이터 타입이라도, "특정 타입이 primitive해 보인다"는 것만으로는 platform 소속 근거가 안 된다 — 그 타입이 존재하는 이유가 특정 소비자(예: `IRenderer`)의 계약을 만족시키기 위해서라면, 필드가 아무리 단순해도 그 소비자 쪽 소속이다. (이번 사이클에서 `InstanceSnapshot`을 두고 확인한 기준.)
- `T`에 대해 완전히 무지한 제네릭 메커니즘(예: `DoubleBufferPublisher<T>`)은 `T`가 나중에 무엇으로 쓰이든 항상 platform.

**graphics** — platform을 사용해 DirectX/OpenGL 등 특정 그래픽스 API를 캡슐화하는 계층.
- projects를 몰라야 한다. platform에는 의존해도 된다.
- 자신의 공개 인터페이스(`IRenderer` 등)가 주고받는 데이터 타입의 모양은 graphics 자신이 정의하고 소유한다 — 그 타입이 지금 순수 데이터처럼 보여도, 모양을 결정하는 주체가 렌더링 파이프라인이면 graphics 소속.
- WOT 고유의 개념(탱크, 맵 이름 등)은 여기 있으면 안 된다 — graphics는 이 프로젝트가 아닌 다른 프로젝트에서도 재사용 가능해야 한다.

**projects** — platform과 graphics를 모두 사용해 이번 프로젝트(WOT)의 실제 동작/콘텐츠를 구현하는 최하위 계층.
- platform, graphics 어느 쪽도 projects에 의존해서는 안 된다(역방향 금지).
- 지금은 데모/자리 표시자로 보이는 코드(예: `InstanceUpdateWorker`)라도, 나중에 실제 게임플레이 시스템(물리/애니메이션)으로 교체될 성격이면 지금부터 projects 소속 — 나중에 다시 옮기는 왕복 비용을 피한다.
- **메커니즘과 스키마 인스턴스를 구분한다.** 어떤 폴더에 "범용 메커니즘"과 "그 메커니즘이 다루는 구체적 데이터"가 같이 있으면, 메커니즘만 platform/graphics로 가고 데이터는 projects로 남는다. (`ConfigManager`(메커니즘, platform 자격) vs `AppConfig`(WOT 스키마, projects) / `SaveLoadManager`+`ISaveable`(메커니즘, platform 자격) vs `PlayerProgress`(재화·탱크 ID를 담은 WOT 스키마, projects) — 두 사례 모두 "renderer/config를 include하는가"라는 검사만으로는 못 걸러내고, 필드 내용까지 봐야 발견된다.)

## 목표 상태

```
src/
  projects/            (구 app + config — WOT 전용, platform+graphics 사용)
    main.cpp
    config/
    engine/
      InstanceUpdateWorker.*        (WOT 데모 시뮬레이션 producer)
    persistence/
      PlayerProgress.*              (재화·탱크 ID를 담은 WOT 세이브 스키마)
  platform/            (Phase B에서 submodule 후보 — 최상위 기초 데이터/기능, graphics/projects를 모름)
    Win32Window.*
    math/
    collision/
    entity_component/
    geometry/
    logging/
    engine/
      DoubleBufferPublisher.h       (T에 무지한 제네릭 동기화 메커니즘)
      IFrameDataPublisher.h
    serialization/
    persistence/
      ISaveable.h                   (범용 저장/복원 계약)
      SaveLoadManager.*             (범용 저장/복원 메커니즘)
    model_import/
  graphics/             (Phase B에서 submodule 후보 — platform을 사용, projects를 모름)
    renderer/
      InstanceSnapshot.h            (IRenderer::RenderFrame의 계약 타입)
      IRenderer.h
      ...
    ui/
```

이번 사이클(Phase A)은 이 디렉터리 구조로 재배치하고, 그 경계를 CMake 타겟(`platform_lib` / `graphics_lib` / `app_lib`) 3개로 강제하는 것까지가 범위다.
git submodule 추출(별도 저장소화, `.gitmodules` 등록)은 Phase B로 다음 사이클에 넘긴다.

## #include 경로 치환 규칙

include root(`target_include_directories(... PUBLIC src)`)는 그대로 `src`를 유지한다 — 기존에 이미 `#include "platform/Win32Window.h"`처럼 최상위 폴더명을 접두어로 쓰는 관례가 있었고, 이 관례를 모든 폴더로 확장하는 것으로 충분하다(별도 include root 재설계 불필요, 향후 submodule 추출 시에도 "폴더를 통째로 새 저장소로 옮기고 include root만 그 저장소 루트로 잡으면 되는" 가장 단순한 형태).

`src/**/*.{h,cpp}`, `tests/**/*.cpp` 전체에서 아래 치환을 적용한다(대상: `#include "..."` 안의 경로만, 순서 무관하게 전부 적용 가능 — 접두어가 서로 겹치지 않음).

| 기존 include 접두어 | 신규 include 접두어 |
|---|---|
| `"config/` | `"projects/config/` |
| `"math/` | `"platform/math/` |
| `"collision/` | `"platform/collision/` |
| `"entity_component/` | `"platform/entity_component/` |
| `"geometry/` | `"platform/geometry/` |
| `"logging/` | `"platform/logging/` |
| `"serialization/` | `"platform/serialization/` |
| `"persistence/` | `"platform/persistence/` |
| `"model_import/` | `"platform/model_import/` |
| `"renderer/` | `"graphics/renderer/` |
| `"ui/` | `"graphics/ui/` |
| `"platform/Win32Window.h"` | 변경 없음 |

`"engine/` 접두어는 위 표처럼 일괄 치환할 수 없다 — 파일별 소속이 갈리기 때문에 예외 목록으로 처리한다(전체 프로젝트에서 `#include "engine/` 검색 결과 아래 6개 지점뿐임을 확인함).

## RendererFactory 순환 의존 해소

- `src/renderer/RendererFactory.h` (이동 후 `src/graphics/renderer/RendererFactory.h`)
  - `Create(const LaunchConfig& config)` → `Create(RendererBackend backend)`로 변경.
  - `#include "config/LaunchConfig.h"` 제거 (더 이상 필요 없음).
- `src/renderer/RendererFactory.cpp`
  - `switch (config.backend)` → `switch (backend)`로 변경.
- `src/app/main.cpp` (이동 후 `src/projects/main.cpp`) 호출부
  - `RendererFactory::Create(LaunchConfigStore::Get())` → `RendererFactory::Create(LaunchConfigStore::Get().backend)`.
- `tests/RendererFactoryTest.cpp`
  - 4개 테스트 케이스에서 `const LaunchConfig config{RendererBackend::X}; RendererFactory::Create(config);` → `RendererFactory::Create(RendererBackend::X);`로 단순화.
  - 더 이상 쓰지 않는 `#include "config/LaunchConfig.h"` 제거.

조사 결과 `LaunchConfig`는 현재 `backend` 필드 하나뿐이라 이 변경의 실질 위험은 낮다.

## CMakeLists.txt 재구성

현재 단일 `app_lib` STATIC 타겟을 3개로 분리한다.

- `platform_lib` — `src/platform/**/*.cpp` 전체 + `${ufbx_SOURCE_DIR}/ufbx.c`.
  - `target_include_directories(platform_lib PUBLIC src)`
  - `target_link_libraries(platform_lib PRIVATE nlohmann_json::nlohmann_json tinyobjloader)` (JsonDataStore/model_import 전용 — 기존과 동일하게 PRIVATE 유지, 외부 라이브러리를 wrapper 뒤로 숨기는 기존 원칙 유지)
  - cgltf/ufbx include 경로도 기존과 동일하게 PRIVATE.
- `graphics_lib` — `src/graphics/**/*.cpp` 전체 + imgui 관련 소스(`imgui.cpp` 등, backends의 win32/dx9/dx11/dx12 구현).
  - `target_include_directories(graphics_lib PUBLIC src)`
  - `target_link_libraries(graphics_lib PUBLIC platform_lib d3d9.lib d3d11.lib d3d12.lib dxgi.lib)`
  - imgui include 경로는 기존과 동일하게 PRIVATE.
- `app_lib` (projects) — `src/projects/config/**/*.cpp` + `src/projects/engine/InstanceUpdateWorker.cpp` + `src/projects/persistence/PlayerProgress.cpp` 포함.
  - `target_link_libraries(app_lib PUBLIC platform_lib graphics_lib)` (config가 `RendererBackend`를, `InstanceUpdateWorker`가 `platform::DoubleBufferPublisher`와 `graphics::InstanceSnapshot`을, `PlayerProgress`가 `platform::ISaveable`을 참조하므로 모두 필요)
- `add_executable(main src/projects/main.cpp)` → `target_link_libraries(main PRIVATE app_lib)` (전이 의존으로 graphics_lib/platform_lib까지 자동 연결됨)
- HLSL 셰이더 경로: `wot_add_hlsl_shader(...)` 호출부의 `${CMAKE_SOURCE_DIR}/src/renderer/directx*/shaders/*.hlsl` → `${CMAKE_SOURCE_DIR}/src/graphics/renderer/directx*/shaders/*.hlsl`로 전부 갱신.
- `tests` 타겟: `target_link_libraries(tests PRIVATE app_lib graphics_lib platform_lib gtest_main)`로 갱신(테스트가 `platform`/`graphics`의 심볼을 직접 참조하는 경우가 많아 명시적으로 링크).

의존 방향은 `platform_lib ← graphics_lib ← app_lib ← main`으로 고정되고, `platform_lib`는 어떤 상위 타겟도 링크하지 않는다 — 브레인스토밍에서 확정한 레이어링 원칙(platform은 graphics를 몰라야 함)을 빌드 타겟 수준에서 강제한다.

**알려진 리스크 (수용하고 진행, 조치는 아래 검증/체크리스트로 완화)**
- STATIC 라이브러리 3단 체인(`platform_lib`→`graphics_lib`→`app_lib`→`main`)에서 `tinyobjloader` 같은 PRIVATE 서드파티 링크가 최종 실행 파일까지 제대로 전파되는지는 이론상 되지만(CMake가 STATIC 라이브러리의 private 링크 의존성을 링크 단계에서 전이시킴) 실제 빌드로 확인 전까진 확신할 수 없다 — 실패하면 링커 단계에서 "unresolved external symbol"로 드러난다.
- include root가 모든 타겟에서 `src`로 공유되므로, `platform_lib` 소스가 실수로 `graphics/...` 헤더를 include해도 심볼을 실제로 안 쓰면(또는 header-only면) 컴파일·링크 둘 다 통과할 수 있다 — 이번 사이클의 타겟 분리는 "링크 시점 강제"이지 "include 시점 강제"가 아니다. 완전한 강제는 Phase B(별도 저장소)에서만 가능하다.

## 검증 기준

- [x] (파일 이동/include 치환 직후, CMake 3-way 분리 이전) 기존 단일 `app_lib` 구성을 소스 경로만 갱신해 1차 빌드 — 이동/치환 자체의 정확성을 CMake 타겟 분리와 분리해서 검증.
- [x] `cmake --build` 로 `main`, `tests` 두 타겟 모두 경고 추가 없이 빌드 성공(3-way 분리 후).
- [x] `ctest` 전체 통과 — 이번 재배치로 스킵되거나 새로 실패하는 테스트가 없어야 함(기존 실패가 있었다면 그 개수/목록이 재배치 전후로 동일해야 함).
- [x] `main.exe` 수동 실행 — 창이 뜨고 렌더러가 초기화되어 빈 화면(또는 기존 데모 도형)이 표시되는지 스모크 확인.
- [x] `platform_lib`가 `graphics_lib`/`app_lib`를 `target_link_libraries`로 참조하지 않는지 CMakeLists.txt 육안 확인(역방향 의존 재발 방지).
