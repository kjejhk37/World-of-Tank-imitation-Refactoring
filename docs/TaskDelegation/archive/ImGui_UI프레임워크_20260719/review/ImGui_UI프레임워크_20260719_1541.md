# Code Review: ImGui 기반 기본 UI 프레임워크

## Stage 1 — Quality Inspection

### 즉시 해결 가능 (이번 Task 범위 내)

- `[MEDIUM]` `DirectX12Renderer::RenderFrame()`의 null 가드가 `m_uiManager`를 포함하지 않아, 특정 초기화 실패 경로에서 null 포인터 역참조 크래시가 발생할 수 있다.
  - `Initialize()`는 `CreateDevice()` → `CreateSwapChain()`(여기서 `m_commandQueue`/`m_swapChain`이 이미 설정됨) → `CreateRenderTargets()` → `CreateCommandAllocator`/`CreateCommandList`/`CreateFence`/`CreateEvent` 순으로 진행하고, `m_uiManager`는 이 모든 단계가 성공한 맨 마지막에만 생성된다.
  - `CreateCommandAllocator`/`CreateCommandList`/`CreateFence`/`CreateEvent` 중 하나라도 실패하면 `Initialize()`는 `false`를 반환하지만, 이 시점에 `m_commandQueue`와 `m_swapChain`은 이미 non-null 상태로 남아있고 `m_uiManager`만 null이다.
  - `RenderFrame()`의 가드는 `if (!m_commandQueue || !m_swapChain) return;`이라 이 케이스를 걸러내지 못하고, 곧바로 `m_uiManager->NewFrame()`을 호출해 null `unique_ptr`을 역참조한다.
  - `DirectX9Renderer`/`DirectX11Renderer`는 우연히 안전하다 — DX9는 실패 지점이 `m_device` 하나뿐이고 그게 곧 가드 변수이며, DX11은 마지막 실패 지점(`CreateRenderTargetView`)이 가드 변수(`m_renderTargetView`)를 정확히 리셋하기 때문이다. DX12만 가드 변수(이른 단계에서 설정되는 `m_commandQueue`/`m_swapChain`)와 실제 널 위험 자원(`m_uiManager`, 늦은 단계)이 어긋난다.
  - 현재 `main.cpp`는 `Initialize()`가 `false`를 반환하면 `RenderFrame()`을 호출하지 않고 즉시 종료하므로 실사용 경로에서는 발현되지 않지만, 이 클래스의 암묵적 계약("Initialize 실패 후에도 RenderFrame이 안전해야 한다")이 DX9/DX11과 달리 DX12에서만 깨져 있다.
  - **[해결 방안]**
    - `DirectX12Renderer::RenderFrame()`의 가드에 `!m_uiManager`를 추가해 `if (!m_commandQueue || !m_swapChain || !m_uiManager) return;`로 만든다.
    - 이 실패 경로는 WARP 디바이스에서 결정적으로 재현하기 어려워(해당 API 호출이 정상 환경에서 거의 실패하지 않음) 자동화된 회귀 테스트는 추가하지 않고 방어적 가드로만 대응한다.
  - **[처리 결과]** `RenderFrame()` 가드에 `!m_uiManager` 추가 완료.

- `[LOW]` `ImGuiManagerDX12::Render()`(인터페이스 오버라이드)가 아무 것도 하지 않고 조용히 반환해, 향후 이 객체를 `IUiManager*`로 다루는 코드가 생기면 실제로는 아무것도 그려지지 않았는데 에러도 없이 넘어가는 함정이 된다.
  - 지금은 `DirectX12Renderer`가 구체 타입으로만 소유해 이 경로가 호출되지 않지만, 클래스 자체의 계약(LSP)만 놓고 보면 `IUiManager`의 다른 구현체(`ImGuiManagerDX9`/`DX11`)와 다르게 동작한다.
  - **[해결 방안]**
    - `Render()` 본문에 `assert(false && "ImGuiManagerDX12::Render()는 커맨드 리스트가 필요해 지원되지 않는다 - RenderWithCommandList를 사용할 것")`를 추가해, 디버그 빌드에서는 오용 시 즉시 실패하고 릴리스 빌드에서는 기존과 동일하게 조용히 무시되게 한다.
  - **[처리 결과]** `<cassert>` 추가 후 `Render()`에 `assert(false && ...)` 반영 완료 — 정상 경로(`RenderWithCommandList` 호출)는 이 함수를 전혀 거치지 않아 72개 테스트 전부 그대로 통과.

### 그 외 검사 결과 — 위반 없음

- **SOLID**
  - `IUiManager`/`ImGuiManagerDX9`/`DX11`/`DX12`가 각각 단일 책임(포맷 없음, UI 프레임 생명주기만)을 가진다.
  - `DirectX9/11/12Renderer`가 `IUiManager*`가 아닌 구체 타입(`ImGuiManagerDX12`의 `RenderWithCommandList` 등 인터페이스 밖 메서드 호출 필요)으로 소유하는 것은 브레인스토밍에서 이미 검토/승인된 의도적 설계다.
  - `Win32Window`/`main.cpp`/`RendererFactory`는 ImGui의 존재를 전혀 모른다(DIP 유지).
- **라이브러리 격리**
  - `<imgui.h>`/`<imgui_impl_win32.h>`/`<imgui_impl_dx9.h>`/`<imgui_impl_dx11.h>`/`<imgui_impl_dx12.h>`를 아는 파일이 각각 `ImGuiManagerDX9/11/12.cpp` 하나씩으로 격리됨을 grep으로 재확인.
  - `main`/`tests` 타겟의 include 경로 상 ImGui 헤더 노출 없음(`app_lib`에 `PRIVATE`로 격리).
- **주석 규칙**
  - 신규/수정된 헤더(`IUiManager.h`, `ImGuiManagerDX9/11/12.h`, `IRenderer.h`, `Win32Window.h`, `DirectX9/11/12Renderer.h`, `OpenGLRenderer.h`) 전부 Author/Description/Input/Output/Notes/Date 빠짐없음.
- **단위 테스트**
  - 위 2건을 제외하면 커버리지 공백 없음 — `ImGuiManagerDX9/11/12Test`(실제/WARP 디바이스), `Win32WindowTest`의 `SetMessageHook` 2개 케이스 포함 전체 72개 통과.

### 처리 상태

2개 항목 모두 `[RESOLVED]` — 재빌드/재테스트(72개 전부 통과) 완료.
