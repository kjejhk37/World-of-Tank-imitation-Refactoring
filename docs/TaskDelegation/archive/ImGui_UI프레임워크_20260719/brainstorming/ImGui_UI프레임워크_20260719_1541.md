# Brainstorming: ImGui 기반 기본 UI 프레임워크

## Details

### 왜 이 태스크가 단순하지 않은가

"간단하게 프레임워크만 확보"라는 목표와 달리, 이 프로젝트의 구조상 ImGui 통합은 아래 두 가지 이유로 단순하지 않다.

1. **이 프로젝트는 런타임에 DirectX9/11/12를 전환할 수 있다.** ImGui 공식 백엔드는 렌더러별로 완전히 분리되어 있다(`imgui_impl_dx9`/`imgui_impl_dx11`/`imgui_impl_dx12`) — 렌더러 하나마다 초기화/디바이스 타입이 다르다.
2. **`Win32Window`가 메시지 루프(WndProc)를 이미 소유하고 있다.** ImGui의 Win32 백엔드(`imgui_impl_win32`)는 `WM_MOUSEMOVE`/`WM_CHAR` 등 원시 Win32 메시지를 가로채야 하는데, 지금 `WndProc`은 `Win32Window`의 정적 콜백 안에 있고 리사이즈 콜백 하나만 외부에 노출한다.

### 렌더러 백엔드 범위 (확정 — DX9/11/12 전부 시도)

사용자 결정: 가능하면 DX9/11/12 세 백엔드 전부에 ImGui를 연결한다. 힘들면 구조까지만이라도.

`DirectX_초기설정` 사이클에서 세 백엔드를 동시에 다룬 전례가 있고, DX9/DX11은 사실 공식 ImGui 백엔드가 단순한 편(디바이스/컨텍스트 포인터 하나 넘기는 수준)이라 실제로 크게 어렵지 않다. DX12만 폰트 텍스처용 SRV 디스크립터 힙을 별도로 만들어야 해서 다른 두 백엔드보다 손이 많이 간다 — 이 부분만 구현 중 진짜로 막히면, DX12는 `IUiManager`를 구현하되 내부 로직 없이(혹은 최소한으로) "구조만 있는" 상태로 남기고 커밋 리포트에 명시하는 것으로 대응한다.

### 렌더러별 ImGui 자동 매칭 (사용자 제안 — 채택)

**제안**: `config.json`의 `renderer`에 맞춰 ImGui 버전도 자동으로 맞춰지면 되지 않나? (`ImGuiDX9`/`ImGuiDX11` 같은 식으로)

**검토 결과**: 이미 그렇게 되도록 설계하면 된다 — 별도의 "ImGui 버전" 설정 자체가 필요 없다.
`DirectX9Renderer`/`DirectX11Renderer`/`DirectX12Renderer`는 이미 `config.renderer` 값 하나로만 선택되는 구조다(`RendererFactory`). 각 렌더러가 자기 자신에 맞는 `ImGuiManagerDX9`/`DX11`/`DX12`를 내부적으로 소유하게 하면, ImGui 백엔드는 렌더러 선택에 자동으로 100% 종속된다 — 사용자가 별도로 맞출 일도, 둘이 어긋날 일(예: `renderer=directx11`인데 ImGui는 DX9 백엔드로 초기화)도 원천적으로 없다.
그래서 `AppConfig`에 ImGui 관련 필드를 추가하지 않는다 — 추가하면 오히려 "두 번째 진실의 원천"이 생겨 불일치 검증 로직이 필요해지는 역효과가 있다.

### 래퍼 설계 — `IUiManager` + 백엔드별 구현체

CLAUDE.md 외부 라이브러리 wrapper 원칙에 따라, `imgui.h`/`imgui_impl_*.h`를 아는 파일을 모듈별로 격리한다. 렌더러 폴더 구조(`src/renderer/directx9/` 등)와 동일한 패턴을 그대로 따른다.

```
src/ui/
  IUiManager.h                          # 공용 인터페이스, ImGui 타입 노출 없음
  directx9/ImGuiManagerDX9.h/.cpp        # <imgui_impl_dx9.h> 아는 유일한 파일
  directx11/ImGuiManagerDX11.h/.cpp      # <imgui_impl_dx11.h> 아는 유일한 파일
  directx12/ImGuiManagerDX12.h/.cpp      # <imgui_impl_dx12.h> 아는 유일한 파일
```

- `IUiManager` — `Initialize`는 인터페이스에 넣지 않는다(DX9/11/12마다 필요한 파라미터가 완전히 다르기 때문 — `IDirect3DDevice9*` vs `ID3D11Device*`+`ID3D11DeviceContext*` vs `ID3D12Device*`+디스크립터 힙+프레임 수). 대신 공통으로 가능한 부분만 순가상함수로 둔다.
  - `virtual void NewFrame() = 0`
  - `virtual void Render() = 0`
  - `virtual void Shutdown() = 0`
  - `virtual bool HandleWin32Message(HWND, UINT, WPARAM, LPARAM) = 0`
- `ImGuiManagerDX9`/`DX11`/`DX12` — 각자 생성자에서 필요한 DX 타입(+`HWND`)을 직접 받아 `ImGui::CreateContext()` → `ImGui_ImplWin32_Init(hwnd)` → `ImGui_ImplDXn_Init(...)` 순으로 초기화한다. `IRenderer.h`가 이미 "DirectX 전용 타입을 인터페이스에 노출하지 않는다"는 원칙을 각 구현체 내부에서는 허용하는 것과 동일한 논리 — `ImGuiManagerDX11`은 자신을 소유하는 `DirectX11Renderer`가 이미 아는 `ID3D11Device*`를 받는 것뿐이라 계층 위반이 아니다.
- **소유 관계**: `DirectX9Renderer`/`DirectX11Renderer`/`DirectX12Renderer`가 각각 `std::unique_ptr<IUiManager> m_uiManager`를 멤버로 소유하고, `Initialize`/`RenderFrame`/`Shutdown`에서 위임 호출한다. 렌더러 자신은 "렌더링" 책임만, `ImGuiManagerDXn`은 "UI 오버레이" 책임만 가져 SRP 유지.
- `OpenGLRenderer`(스텁)는 `m_uiManager`를 두지 않고 새 인터페이스 메서드에서 `return false`/no-op만 한다 — 기존 스텁 패턴과 동일.

### `IRenderer` 확장

- `virtual bool HandleUiMessage(HWND, UINT, WPARAM, LPARAM) = 0;` 추가 — 각 렌더러가 `m_uiManager->HandleWin32Message(...)`로 위임.

### Win32 메시지 전달 — `Win32Window::SetMessageHook`

`Win32Window`가 ImGui를 알게 만들지 않기 위해, 기존 `SetResizeCallback`과 같은 패턴으로 범용 메시지 훅을 추가한다(채팅에서 상세 설명 완료, 아래는 요약).

- `Win32Window::SetMessageHook(std::function<bool(HWND, UINT, WPARAM, LPARAM)> hook)` 추가.
- `WndProc` 맨 앞에서 훅을 호출하고, `true`(처리됨)가 돌아오면 그 자리에서 `return true` — ImGui 공식 예제와 동일한 관용구.
- ImGui의 Win32 핸들러는 `WM_SIZE`/`WM_DESTROY`에는 절대 `true`를 반환하지 않으므로(마우스/키보드/커서 관련 메시지에만 응답), 기존 리사이즈/종료 처리가 스킵되는 일은 없다.
- `main()`이 `renderer->Initialize(...)` 이후 `window->SetMessageHook([&renderer](HWND h, UINT m, WPARAM w, LPARAM l) { return renderer->HandleUiMessage(h, m, w, l); })`로 연결. `Win32Window`는 여전히 `IRenderer`/ImGui를 전혀 모른다.

### "프레임워크 확보"를 어떻게 검증할 것인가 (확정 — 빌드까지만)

사용자 결정: 시각적 확인(데모 창 등) 없이 **빌드까지만** 진행한다. `AppConfig`에 ImGui 관련 필드(예: 데모 토글)를 추가하지 않는다.

- 검증 기준: `main`/`tests` 타겟이 정상 컴파일·링크되고, `ctest`가 전부 통과하며, `--renderer=directx9`/`directx11`/`directx12` 각각 실행 시 크래시 없이 창이 뜬다(눈에 보이는 ImGui 콘텐츠는 없음 — `ImGui::NewFrame()`/`Render()`는 매 프레임 실제로 호출되지만 그 사이에 위젯을 그리는 코드가 없으므로 화면상 변화는 없다).
- 단위 테스트는 각 `ImGuiManagerDXn`이 실제(또는 WARP) 디바이스로 `NewFrame`/`Render`/`Shutdown`을 크래시 없이 수행하는지 검증한다 — `DirectX9/11/12RendererTest`와 동일한 스모크 테스트 스타일.

### 빌드 통합 (CMake `FetchContent`)

Dear ImGui는 `nlohmann::json`/`googletest`와 달리 공식 CMake 타겟을 제공하지 않는다 — 저장소를 통째로 받아온 뒤 필요한 `.cpp`를 직접 골라 우리 쪽 타겟에 추가해야 한다.

- `FetchContent_Declare(imgui URL https://github.com/ocornut/imgui/archive/refs/tags/v1.91.x.zip ...)`
- `app_lib`에 추가할 소스: `imgui.cpp`, `imgui_draw.cpp`, `imgui_tables.cpp`, `imgui_widgets.cpp`, 백엔드 `backends/imgui_impl_win32.cpp`, `backends/imgui_impl_dx9.cpp`, `backends/imgui_impl_dx11.cpp`, `backends/imgui_impl_dx12.cpp`. (`imgui_demo.cpp`는 데모 창을 안 쓰기로 했으므로 제외.)
- `target_include_directories(app_lib PRIVATE ${imgui_SOURCE_DIR} ${imgui_SOURCE_DIR}/backends)` — `nlohmann_json`과 동일하게 `PRIVATE`로 격리해 `main`/`tests`의 include 경로에 ImGui 헤더가 노출되지 않게 한다.

## Trade-offs

- **DX9/11/12 전부 연결 vs DX11만**
  - 전부: 작업량은 늘지만 "가능하면 전부"라는 사용자 요구에 부합하고, 세 렌더러가 이미 대칭 구조(`IRenderer` 구현체)라 `IUiManager` 구현체도 같은 대칭 구조로 자연스럽게 들어간다.
  - DX11만: 더 빠르지만 이번에 DX9/DX12 쪽은 미확보 상태로 남음.
  - → 사용자 결정에 따라 전부 시도, DX12가 막히면 구조만.
- **범용 메시지 훅(`Win32Window::SetMessageHook`) vs `Win32Window`가 ImGui를 직접 아는 방식**
  - 범용 훅: `SetResizeCallback`과 동일한 기존 패턴 재사용, `Win32Window`의 SRP/재사용성 유지.
  - 직접 통합: 코드는 더 짧아지지만 `Win32Window`가 특정 UI 라이브러리에 종속됨.
  - → 범용 훅 채택(사용자 설명 요청에 대한 답변으로 채팅에서 상세 설명, 위 Details 요약 참고).
- **빌드까지만 검증 vs 데모 창 토글로 시각적 검증**
  - 빌드까지만: `AppConfig`에 아무것도 추가할 필요 없음, "main.cpp에 UI를 만들지 않는다"는 제약을 가장 단순하게 지킴. 대신 "정말 그려지는지"는 다음 사이클(실제 UI 제작)에서야 확인됨.
  - 데모 토글: 시각적으로 확실히 검증되지만 config 필드가 하나 늘어남.
  - → 사용자 결정에 따라 빌드까지만.
- **ImGui 버전을 별도 설정 vs 기존 `renderer` 설정에 자동 종속**
  - 별도 설정: `ImGuiBackend` 같은 새 enum/필드가 생기고, `renderer`와 값이 어긋나는 조합(예: `renderer=directx11` + `imguiBackend=directx9`)을 막는 검증 로직이 추가로 필요함.
  - 자동 종속(채택): 각 `DirectXnRenderer`가 자신에 맞는 `ImGuiManagerDXn`만 소유 — 두 번째 진실의 원천 자체가 존재하지 않아 불일치가 구조적으로 불가능. 새 설정 필드도 불필요.
  - → 자동 종속 채택(사용자 제안).

## Summary & Open Questions (사용자 결정 필요)

**확정된 방향**

- ImGui는 DX9/11/12 **세 백엔드 모두**에 연결을 시도한다 — DX12가 실제로 막히면(SRV 디스크립터 힙 등) 구조만 갖추고 커밋 리포트에 명시.
- `src/ui/IUiManager.h` + `ImGuiManagerDX9`/`DX11`/`DX12`(각 백엔드별 폴더) — 인터페이스에는 `NewFrame`/`Render`/`Shutdown`/`HandleWin32Message`만, `Initialize`는 백엔드별로 다른 시그니처라 인터페이스 밖에 둔다.
- 각 `DirectXnRenderer`가 자기 짝 `ImGuiManagerDXn`을 멤버로 소유 — ImGui 버전은 `config.renderer` 선택에 자동 종속, 별도 config 필드 없음.
- `IRenderer`에 `HandleUiMessage(HWND,UINT,WPARAM,LPARAM)` 추가, `Win32Window::SetMessageHook`(범용 콜백, `SetResizeCallback`과 동일 패턴)으로 연결.
- 검증은 **빌드까지만** — 컴파일/링크/`ctest` 통과 + `--renderer=directx9/11/12` 각각 크래시 없이 실행. 시각적 데모/위젯 없음, `AppConfig` 변경 없음.
- 빌드는 `FetchContent`로 ImGui 소스 직접 받아 필요한 `.cpp`만 나열, `PRIVATE` include로 격리.

**남은 질문 없음** — 전략 문서 작성으로 넘어가도 될지만 확인 부탁드립니다.
