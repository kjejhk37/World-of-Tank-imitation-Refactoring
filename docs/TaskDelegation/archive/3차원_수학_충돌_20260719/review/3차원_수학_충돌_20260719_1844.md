# Code Review: 기초 3차원 수학/충돌 데이터 클래스

## 사용자 요청 사항 — `math`/`geometry` 분리가 필요한지

**결론: 분리를 유지하는 걸 권장한다.**

- 실제 include 방향을 다시 확인한 결과, `geometry/*` → `math/*` 단방향 의존만 존재하고 역방향(`math`가 `geometry`를 아는) 의존은 전혀 없다 — `Vec3`/`Quaternion`/`Matrix4x4`/`Transform`는 "도형"이나 "충돌"이라는 개념을 전혀 모른다.
- 이번 사이클 브레인스토밍에서 이미 "`math`(`Vec3`/`Matrix`/`Transform`)를 안정화되면 별도 저장소로 뽑아 submodule화하겠다"는 계획이 확정되어 있다 — 이 계획의 대상은 `geometry`가 아니라 `math`뿐이다. 지금 두 폴더를 합쳐두면, 나중에 실제로 분리할 때 결국 다시 나눠야 하는 작업이 그대로 남는다.
- 폴더를 나눈다고 해서 실질적인 커플링이 늘어나거나 줄어드는 건 아니다(`geometry`는 원래도 `math`가 있어야 동작) — 하지만 "무엇이 재사용 가능한 순수 수학이고 무엇이 충돌 전용 로직인지"를 폴더 경계로 명확히 구분해두는 것 자체가, 나중에 실제로 도려낼 때 실수를 줄여준다.
- 지금 파일 개수만 보면(`math` 4개, `geometry` 7개) 굳이 나눌 만큼 크지 않다고 느낄 수 있지만, 분리 기준은 "지금 파일이 몇 개냐"가 아니라 "이 두 그룹이 서로 다른 이유로 바뀌는가"다 — 수학 공식이 바뀌는 이유(예: SIMD 최적화 도입)와 충돌 판정 로직이 바뀌는 이유(예: 새 도형 쌍 추가)는 실제로 다르다.
- **결론적으로 현재 구조를 그대로 유지**하고, 병합하지 않는 것을 권장한다.

## Stage 1 — Quality Inspection

### 즉시 해결 가능 (이번 Task 범위 내)

- `[MEDIUM]` `Matrix4x4::operator*`(행렬×행렬)가 항등행렬끼리 곱하는 경우만 테스트되어 있어, 실제 곱셈 루프의 정확성이 사실상 검증되지 않았다.
  - `Matrix4x4Test.cpp`의 `IdentityMultipliedByIdentityIsIdentity`는 항등×항등이라 행/열 인덱스가 뒤바뀌는 것 같은 버그가 있어도 통과한다.
  - `FromTRS`는 `operator*`를 호출하지 않고 값을 직접 계산해서 만들기 때문에, 다른 테스트들도 `operator*`의 곱셈 루프 자체를 우회한다.
  - **[해결 방안]**
    - 두 개의 임의(비항등) `Matrix4x4::FromTRS` 결과를 곱한 뒤, `(A*B).TransformPoint(p)`가 `B.TransformPoint(A.TransformPoint(p))`와 일치하는지 검증하는 테스트를 추가한다(행벡터 관례에서 `A*B`는 "A를 먼저 적용, B를 나중에 적용"을 의미 — Notes에 이미 명시된 관례와 일치하는지 동시에 검증됨).
  - **[처리 결과]** `Matrix4x4Test::MultiplyingTwoNonTrivialMatricesMatchesSequentialTransformPoint` 추가 — 비항등 TRS 행렬 2개를 곱한 결과가 순차 변환과 일치함을 검증(통과).

- `[MEDIUM]` `Capsule`-`AABB`/`OBB`에 쓰이는 alternating-projection(번갈아 투영) 반복 횟수(8회)에 대한 근거나 정밀도 경계 테스트가 없다.
  - 코드에 "8회면 충분히 수렴한다"고만 적혀 있고, 왜 8이 충분한지 분석이나 참고 없이 매직 넘버로 남아있다.
  - 현재 `CapsuleJustGrazingAABBCornerIntersects` 테스트는 여유 있는 반지름 마진으로 통과 여부만 확인해, 실제로 빡빡한 경계(거의 닿을락 말락한 경우)에서도 정밀하게 수렴하는지는 검증되지 않는다.
  - **[해결 방안]**
    - 반복 횟수를 8 → 20으로 늘리고(비용이 무시할 만한 수준이라 성능에 영향 없음), "두 볼록 집합 사이의 번갈아 투영은 기하급수적으로 수렴한다"는 근거를 주석으로 남긴다.
    - 축에 정렬되지 않은(각도가 있는) 캡슐-박스 배치에서, 반지름을 살짝 넘거나(비충돌) 살짝 못 미치는(충돌) 타이트한 경계 테스트를 추가한다.
  - **[처리 결과]** 반복 횟수 8→20으로 상향 + 수렴 근거 주석 추가. `CapsuleAABBAlternatingProjectionMatchesBruteForceSamplingAtTightMargin` 테스트 추가 — 대각선 세그먼트를 2000개 샘플로 브루트포스 대조해, ±1e-3 마진에서 충돌/비충돌이 정확히 갈리는지 확인(통과, 실측 수렴 정밀도 확보).

- `[MEDIUM]` `OBB`-`OBB` SAT의 분리축 9개(축끼리 외적) 중 실제로 어느 축이 분리축 역할을 하는지 구분해서 검증하는 테스트가 없다 — 현재 회전 관련 테스트 2개가 전부 같은 Z축 45° 회전만 쓴다.
  - SAT의 9개 교차축 블록은 서로 거의 동일한 형태의 코드가 반복돼(복붙 실수에 취약한 전형적인 지점), 그중 하나에 인덱스/부호 오류가 있어도 지금 테스트들이 우연히 그 축을 건드리지 않으면 통과해버릴 수 있다.
  - **[해결 방안]**
    - 서로 다른 축(X, Y) 회전을 쓰는 OBB-OBB 테스트를 추가해 더 다양한 축 조합을 실제로 행사한다.
    - `Intersects(a, b) == Intersects(b, a)`(인자 순서를 바꿔도 결과가 같아야 함) 대칭성 검증 테스트를 여러 배치에 대해 추가한다 — 대칭성 위반은 인자가 뒤바뀐 종류의 버그를 값싸게 잡아낸다.
  - **[처리 결과]** X축/Y축 회전 OBB-OBB 테스트 2건 + 서로 다른 축으로 각각 회전한 두 박스가 중심이 같으면 항상 겹쳐야 한다는 자명한 사실을 이용한 검증(손으로 좌표를 유도하지 않고도 신뢰성 있게 다양한 교차축 조합을 행사) + 대칭성 검증 테스트 1건, 총 4건 추가(전부 통과).
