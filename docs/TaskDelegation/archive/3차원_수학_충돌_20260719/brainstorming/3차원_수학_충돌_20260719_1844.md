# Brainstorming: 기초 3차원 수학/충돌 데이터 클래스

## Details

### 손수 구현 (확정) + submodule 여부 (확정 — 지금은 보류)

- `Vec3`/`Matrix`/`Transform`은 `glm`/`DirectXMath` 등 외부 라이브러리를 써도 무방하지만, 학습 목적(CLAUDE.md "이전에 공부한 C++/DirectX/수학 개념 복습")에 맞춰 **손수 구현**하기로 확정.
- 처음에는 "별도 git submodule로 만들고 싶다"는 의견이 있었으나, 논의 결과 **지금은 이 프로젝트 안(`src/math/`)에 그냥 구현하고, 안정화되면 그때 별도 저장소로 뽑아 submodule화**하는 쪽으로 확정 — 지금 당장 새 저장소를 만들거나 원격에 push하는 일은 하지 않는다.
- 다만 나중에 실제로 분리하기 쉽도록, 이 모듈은 **프로젝트의 다른 모듈(`config`/`renderer`/`logging` 등)을 전혀 참조하지 않게** 설계한다 — `src/math`/`src/geometry`는 순수하게 자기 자신과 표준 라이브러리(`<cmath>`, `<vector>` 등)에만 의존해야 나중에 폴더째로 떼어내 별도 저장소+submodule로 옮기기 쉽다.

### 디렉터리 구조 제안 (갱신 — GJK 폴더 제거)

```
src/
  math/
    Vec3.h            # 헤더 온리 — 연산이 전부 몇 줄짜리라 인라인이 자연스러움
    Quaternion.h       # 헤더 온리 — 회전 표현(축-각/오일러는 Degree 입력)
    Matrix4x4.h        # 헤더 온리 — TRS(이동/회전/스케일) 합성용 4x4 행렬
    Transform.h        # 헤더 온리 (Vec3 + Quaternion + Vec3 scale 조합, ToMatrix() 제공)
  geometry/
    AABB.h/.cpp
    OBB.h/.cpp
    Sphere.h/.cpp
    Capsule.h/.cpp
    Cylinder.h/.cpp
    Mesh.h            # 데이터만 — 헤더 온리, 충돌 로직 없음
    Intersections.h/.cpp   # 도형 쌍별 충돌/포함 판정 함수 모음 (자유 함수)
```

- `math`(순수 벡터/행렬/변환 연산)과 `geometry`(도형 데이터 + 쌍별 충돌 판정)를 분리 — `geometry`는 `math`에 의존하지만 역방향 의존은 없음.
- 쌍별 충돌 함수를 각 도형 클래스의 멤버 함수로 넣을지, `Intersections.h`에 자유 함수로 모을지는 전략 문서에서 확정(자유 함수 쪽이 "쌍마다 어느 쪽 클래스가 상대를 알아야 하는가" 문제를 피할 수 있어 유력).

### `Matrix4x4`/`Quaternion`/`Transform` 신설 (확정)

애초 "OBB는 축 3개(Vec3[3])면 충분, Matrix/Quaternion은 YAGNI"라고 제안했으나, 사용자가 `Matrix`(4x4 기준)/`Quaternion`을 신설하고 OBB를 그 기반으로 표현하길 원해 계획을 변경했다.

- `Quaternion` — `x,y,z,w`. 연산: 정규화, 켤레/역원, 곱셈(회전 합성), 벡터 회전(`Rotate(Vec3) const`), 단위 회전.
  - **회전 입력은 항상 Degree 단위**(사용자 확정) — `FromAxisAngle(Vec3 axis, float angleDegrees)`, `FromEulerDegrees(float pitchDeg, float yawDeg, float rollDeg)`. 내부적으로는 라디안으로 변환해 `sin`/`cos`에 사용하지만, 공개 API의 각도 파라미터는 전부 Degree로 통일.
  - 오일러 각 합성 순서를 명확히 고정해야 함(안 그러면 "피치/요/롤" 조합이 사람마다 다르게 해석되는 전형적 버그 지점) — Yaw(Y축) → Pitch(X축) → Roll(Z축) 순으로 합성(`q = qYaw * qPitch * qRoll`)하는 것을 제안, 일반적인 게임 엔진 관례와 유사.
- `Matrix4x4` — 4x4 동차 좌표 행렬(사용자 확정 — 3x3이 아니라 4x4). 연산: 행렬×행렬, 점 변환(`TransformPoint`, 이동 포함)/방향 변환(`TransformDirection`, 이동 미포함), 전치, `FromTRS(position, rotation, scale)`(이동+회전+스케일 합성).
  - 저장/곱셈 관례는 **row-major + row-vector**(`v' = v * M`)로 통일 — 이 프로젝트가 최종적으로 DirectX/HLSL 파이프라인에 값을 넘기게 될 걸 감안하면 이 쪽이 자연스럽다(HLSL 기본 관례와 일치, 변환 시 추가 전치 불필요).
  - 완전 일반 4x4 역행렬은 이번 사이클 범위에서 제외 — `Transform`이 만드는 행렬은 항상 아핀(affine, 마지막 행이 `(0,0,0,1)`)이므로, 아핀 전용 역행렬(회전 3x3 전치 + 이동 재계산)만 구현.
- `Transform` — `Vec3 position`, `Quaternion rotation`, `Vec3 scale`(기본값 `(1,1,1)`) + `Matrix4x4 ToMatrix() const`.
- **OBB 표현**: `Transform transform`(위치=중심, 회전=방향, scale은 OBB 목적상 항상 `(1,1,1)`) + `Vec3 halfExtents`(별도 필드). SAT 등에 필요한 3개의 정규직교 축은 `transform.rotation.Rotate(Vec3{1,0,0})` 등으로 그때그때 구한다.

### 각 도형의 데이터 표현 (갱신)

- `AABB`: `Vec3 min, max`
- `OBB`: `Transform transform`, `Vec3 halfExtents` (위 참고)
- `Sphere`: `Vec3 center`, `float radius`
- `Capsule`: `Vec3 pointA, pointB`(caps 중심을 잇는 선분), `float radius` (반구 캡) — 사용자 확인 완료
- `Cylinder`: `Vec3 pointA, pointB`(축 선분), `float radius` (평평한 캡) — 사용자 확인 완료
- `Mesh`: `std::vector<Vec3> vertices`, `std::vector<uint32_t> indices`(삼각형 리스트) — 데이터만, 충돌 로직 없음

### 충돌 감지 접근 방식 (확정 — 쌍별 특수 함수, GJK/BVH/FCL은 미래의 "외부 라이브러리" 후보)

애초 GJK 통합을 권장했으나, 사용자가 이번 사이클은 **쌍별 특수 함수로 직접 구현**하고, GJK/BVH/FCL(Flexible Collision Library) 같은 범용 알고리즘/라이브러리는 **나중에 외부 라이브러리로 도입**하는 쪽으로 방향을 정했다. 최종 목표는 BVH 또는 FCL 기반 시스템 위에, 이번에 만드는 쌍별 특수 함수를 "성능 최적화용 빠른 경로(fast path)"로 얹는 구조 — 즉 이번 작업은 미래 시스템의 성능 최적화 레이어를 먼저 만드는 셈이다.

사용자가 "성능/복잡도 문제가 있으면 해당 부분은 제외해도 무방"이라고 명시했으므로, 15개 쌍을 난이도별로 나눠 우선순위를 제안한다.

**Tier 1 — 반드시 구현(닫힌 형태 해가 잘 알려진 쌍)**
- `AABB`/`OBB` point 포함 여부
- `AABB`-`AABB` 충돌 여부 + 공통 공간(교차 AABB) 추리기
- `Sphere`-`Sphere`
- `Sphere`-`AABB`, `Sphere`-`OBB`
- `AABB`-`OBB`, `OBB`-`OBB` (분리축 정리, SAT)
- `Sphere`-`Capsule`, `Capsule`-`Capsule`(선분-선분 최단거리, Ericson의 *Real-Time Collision Detection* 표준 알고리즘)

**Tier 2 — 구현 시도(다소 복잡하지만 닫힌 형태 해가 있음)**
- `Capsule`-`AABB`, `Capsule`-`OBB` (선분-박스 거리)
- `Sphere`-`Cylinder` (축 선분 거리 + 캡 처리)

**Tier 3 — 시도하되 막히면 이번 사이클 제외 허용(사용자 사전 승인)**
- `Cylinder`-`AABB`, `Cylinder`-`OBB`
- `Capsule`-`Cylinder`, `Cylinder`-`Cylinder` (일반 방향에서 닫힌 형태 해가 사실상 없음 — 가장 유력한 제외/이월 후보)

제외되는 항목은 `Mesh` 충돌과 마찬가지로 커밋 리포트에 `[DEFERRED]`로 명시하고, 다음 사이클(GJK/BVH/FCL 도입) 대상 목록에 남긴다.

### 부동소수점 비교 처리

충돌/포함 판정은 경계에 걸친 케이스에서 부동소수점 오차에 취약하다 — 공통 `constexpr float kEpsilon`을 하나 두고 모든 경계 비교에 일관되게 적용(정확한 값은 전략 문서에서 확정).

## Trade-offs

- **쌍별 특수 함수(확정) vs GJK 통합**
  - 특수 함수(채택): 각 쌍의 수학이 눈에 보여 학습 가치가 높고, "나중에 BVH/FCL 위에 최적화 레이어로 얹는다"는 사용자의 최종 그림과도 맞음. 다만 15쌍 중 일부(Cylinder 관련)는 닫힌 형태 해가 없어 이번 사이클에서 빠질 수 있음(사전 승인됨).
  - GJK: 코드량이 적고 Cylinder 문제가 자연히 해결되지만, 사용자가 GJK/BVH/FCL을 "나중에 외부 라이브러리로 쓸 것"이라고 명시해 이번에 손으로 구현하는 건 중복 투자가 됨 — 폐기.
- **OBB를 `Transform`+`halfExtents`(채택) vs `Transform.scale`을 halfExtents로 재활용**
  - 전자: `halfExtents`라는 이름이 명확해 가독성이 좋음. 필드가 하나 더 있지만 의미가 분명함.
  - 후자: 필드는 줄지만 "OBB의 크기가 scale에 들어있다"는 게 코드만 봐서는 바로 안 보임 — 채택하지 않음.
- **쌍별 충돌 함수를 자유 함수(`Intersections.h`)로 모으기 vs 각 도형의 멤버 함수로 넣기**
  - 자유 함수(유력): `AABB::Intersects(const OBB&)`와 `OBB::Intersects(const AABB&)` 중 어느 쪽에 로직을 두고 어느 쪽이 상대를 include해야 하는지 애매해지는 문제를 피할 수 있음. 15쌍을 한 파일에서 일관되게 관리 가능.
  - 멤버 함수: 호출부(`a.Intersects(b)`)는 더 직관적이지만, 도형 클래스끼리 서로를 include해야 하는 순환 의존 문제가 생김.

## Summary & Open Questions (사용자 결정 필요)

**확정된 방향**

- `Vec3`/`Quaternion`/`Matrix4x4`/`Transform`은 손수 구현. Submodule 분리는 지금 하지 않고, 안정화 후 나중에 진행 — 그때를 대비해 `src/math`/`src/geometry`는 프로젝트의 다른 모듈에 의존하지 않게 설계.
- 회전은 `Quaternion`으로 표현하고, 각도 입력(축-각/오일러)은 전부 Degree 단위 — 오일러 합성 순서는 Yaw→Pitch→Roll로 고정.
- `Matrix4x4`는 row-major + row-vector(`v' = v * M`) 관례, `Transform`이 만드는 아핀 행렬 전용 역행렬만 구현(완전 일반 4x4 역행렬은 범위 밖).
- `OBB`는 `Transform`(위치+회전) + `Vec3 halfExtents`로 표현.
- `Capsule`/`Cylinder`는 "두 끝점(Vec3 A, B) + 반지름"으로 표현.
- 도형 쌍 충돌은 쌍별 특수 함수로 직접 구현하고 `Intersections.h`에 자유(유틸리티) 함수로 모은다. GJK/BVH/FCL은 이번 사이클에서 손으로 구현하지 않고 향후 외부 라이브러리 도입 대상으로 남김.
- 15개 쌍을 Tier 1(필수)/Tier 2(시도)/Tier 3(막히면 바로 다음 사이클로 이월, 주로 Cylinder 관련 어려운 쌍)로 나눠 우선순위대로 구현 — 이월된 항목은 `Mesh` 충돌과 마찬가지로 커밋 리포트에 `[DEFERRED]`로 명시.
